## 一、比赛要求原文（与开发直接相关的部分）

### 1.1 主题与总纲（通知 P2）

> 竞赛以"金融投研智能体构建"为主题……组织参赛团队设计并实现能够在受控数据环境中
> 完成信息检索、数据处理、逻辑核验、量化计算和报告生成等任务的智能体系统。
> 竞赛重点考察参赛作品对金融数据的准确处理能力、复杂任务的组织执行能力、
> 分析结论的准确性和专业性，以及运行过程的可验证、可追溯和可复现程度。

### 1.2 选题列表（通知 P2–P4，共 7 项，可选一项或多项）

| # | 选题 | 重点考察（原文） |
|---|---|---|
| 1 | 数据结构化提取 | 从非标准化公告、扫描文件和复杂表格中提取质押、中标、股权变动等关键字段。重点考察字段提取的完整性、格式规范性、表格解析准确性和结果一致性 |
| 2 | 上市公司财务报告分析 | 从年报/半年报/季报提取财务指标，分析业绩变化原因及异常信号。重点考察财务数据提取及同比、环比计算的准确性，以及对非经常性损益、会计口径变化和利润与现金流背离等问题的识别能力 |
| 3 | 产业链影响分析 | 围绕原材料价格、供需变化、政策调整或重大事件，分析沿产业链向中下游传导的路径及对企业经营和盈利的影响。重点考察产业分析逻辑、证据完整性、量化方法合理性和结论适用边界 |
| 4 | 自动化估值建模 | 根据财务数据、经营假设和可比公司信息，建立现金流折现或相对估值模型，形成估值区间并开展敏感性分析。重点考察模型结构、假设依据、财务勾稽关系、估值结果合理性和敏感性分析完整性 |
| 5 | 研究报告纠错核查 | 依据原始财务材料，对给定研究报告草稿中的收入、利润、估值倍数、单位、统计口径和引用等内容进行核查，识别错误并提出修改意见。重点考察错误识别的准确性和覆盖率、误报控制、来源定位以及修改建议的可执行性 |
| 6 | 买方投资备忘录编制 | 综合财务报告、公司公告、行业数据、新闻和估值信息，形成面向买方机构的投资备忘录。重点考察投资逻辑、事实依据、风险因素、反向验证条件和持续跟踪指标的完整性 |
| 7 | 研究报告质量评估 | 对多份候选报告/智能体生成报告进行质量评价，为报告筛选、修改、复核提供依据。重点考察评价指标的专业性、评分结果的稳定性、评估效率以及对人工复核和交互式分析的支持能力 |

> 本项目聚焦 1 / 4 / 5。选择理由：三者构成一条质量链（事实 → 模型 → 核查），
> 事实库同时是另外两者的唯一数字真源，工作量和深度都更集中。

### 1.3 技术要求（通知 P4–P5）—— 逐条都是硬约束

1. 至少使用一个大语言模型作为核心推理引擎，鼓励采用国产模型
2. 最终成果应以结构化数据、表格或分析报告等形式呈现，不得仅提交自然语言对话记录
3. 须在封闭或半封闭数据环境中运行
4. 完整记录文件访问、工具调用、计算过程和结果生成情况
5. 确保数据来源可核验、执行过程可追溯、运行结果可复现
6. 须同步提交与现场展示版本一致的完整源代码：智能体编排框架、Tool、Prompt、Skill、MCP、
   数据处理、日志记录等核心模块，并附依赖文件及运行说明，
   确保评审方能够在指定环境中复现核心任务流程和输出结果
7. 第三方模型权重及商业软件源代码可不提交，但须说明名称、版本、调用方式及使用范围
8. 使用第三方开源项目/模型/数据/代码的，须在项目说明中列明名称、版本、来源、许可证及使用范围，
   不得冒充自主开发

### 1.4 作品设计与评测要求（通知 P5）—— 评分维度原文

> 参赛作品应立足真实金融投研场景，突出金融专业性、分析严谨性和风险审慎性。
> 涉及估值或投资判断的，应说明主要假设、适用范围和风险因素，并明确区分事实、推论与观点。
> 竞赛将综合评估作品的任务完成度、数据与计算准确性、分析逻辑严密性、
> 证据支撑充分性、结果稳定性、方案创新性和实际应用价值，
> 并结合现场展示及答辩情况进行评价。

### 1.5 提交要求与赛程（通知 P6–P7）

| 阶段 | 交付物 | 硬性要求 |

### 5.1 一处已修复的严重问题：文档声称存在、代码里没有的模块

事实经过：`agent/__init__.py`、`README.md`、`THIRD_PARTY.md` 三处都声明了
`agent/mcp/`（MCP 客户端）与 `agent/skills/`（技能注册表），但这两个目录
当时并不存在 —— 技能只有一份 Markdown 文档，没有任何加载代码；MCP 一行都没有。

为什么危险：这类问题有几个共同特征，使它比普通 bug 更难发现 ——

- 运行期不报错（文档不是代码，不会被导入）
- 全部测试通过（测试不会去读文档）
- 本地开发看不出（写文档的人记得自己的意图）
- 但评审按图索骥点开目录，一眼就发现

而赛题恰好把 Skill 与 MCP 明文列进了「必须提交的核心模块」。
一旦被认定为「项目说明与实际不符」，损失远大于这两个模块本身的实现成本。

修复方式（两条都做了）：

1. 把模块补上（没有选择删掉那句话）：
   - `agent/skills/registry.py`：加载 `domain/skills/*/SKILL.md`，
     产出 `skill_id@version` + SHA256 指纹（写入 `manifest.json`，与提示词同一套纪律），
     并提供 `validate_bindings()` 校验技能声明的工具/提示词真实存在
   - `agent/mcp/client.py`：自研 MCP 客户端（零新增依赖）——
     `initialize` / `tools/list` / `tools/call`，工具接入本地注册表后与自有工具同构；
     子进程只继承白名单环境变量，拿不到 `DEEPSEEK_API_KEY`
   - `tools/mcp_demo_server.py`：仓库自带的演示服务器（纯标准库、离线），
     让「MCP 客户端可用」这句话在任何装了 Python 的机器上都能被复现
   - 新增 CLI：`agent skills`（含绑定校验）、`agent mcp --self-test`（真实子进程端到端）
2. 加体检，防止再次漂移（`tests/test_static_health.py` 三条）：
   - `agent/__init__.py` 的模块清单 ↔ 磁盘目录
   - `README.md` 架构图中的 `<目录>/<模块>/` ↔ 磁盘目录
   - `THIRD_PARTY.md` 引用的目录 ↔ 磁盘目录
   - 并且用 `tools/doc_truth_check.py` 注入不存在的模块名，证明这三条检查真的会失败
     —— 一条永远通过的检查等于没有检查（第一版 README 检查就因为
     「与手写白名单求交集」而漏检，被这个脚本抓了出来）

顺带修的同类问题：`agent/__init__.py` 还声明了一个从未存在的 `verify/`；
`README.md` 把 `skills/` 归在 `agent/` 下（实际是 `domain/skills/`）。

教训（已写进 README 与 `agent/__init__.py` 注释）：
**文档也是产物，也必须被测试。** 测试数由 385 增至 417。

## 八、本轮额外修复（"可复现"评分项的两处假警报）

核实赛题对照时，顺手用真实命令复核了复现链路，发现两次本可复现却被判不可复现：

| 复现命令 | 症状 | 根因 | 修复 |
|---|---|---|---|
| `agent run r1_extract --mock --limit 1` → `replay --strict` | 全部产物哈希不一致 | `--limit` 未写入 manifest，回放处理了全部文档 | manifest 新增 `doc_limit`，回放时恢复 |
| `agent run r4_valuation --mock --facts-run smoke` → `replay --strict` | 回放找不到事实库 | `--facts-run` 未写入 manifest | manifest 新增 `upstream_facts_run`，回放时按「绝对路径 → 项目内相对路径 → runs/<run_id>」三级解析 |

为什么这两条值得单独记一笔：它们的产物本身是稳定的，问题出在
回放用了不同的参数去重跑另一件事。而「结果可复现」是赛题明文评分项，
一份会误报的复现报告比没有复现报告更糟 —— 它会训练人忽略它，
等到真出现不可复现时也没人看了。

修复后两条命令均可复现，并加了带 `@pytest.mark.slow` 的回归测试
（`tests/test_harness.py::test_replay_reproduces_run_with_limit_and_facts_run`）。
测试总数 420 → 421（含 slow）。
