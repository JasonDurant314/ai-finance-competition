## 一、修复前的问题性质：数字读对了，标签贴错了

第一版在 943 页年报上的实测结果是 241 条事实、召回 14.3%、抽中准确率 25.0%。
但下钻之后发现问题的性质不是"读错了"：

| 基准真值 | 系统是否读到了这个数字？ |
|---|---|
| 湖南发展 营业收入 349,165,168.51 | 读到了 3 次（VLM），但 `entity` 被标成 `营业收入（元）` |
| 湖南发展 所有者权益合计 3,797,417,361.30 | 读到了（VLM），但 `metric` 被标成 `total_assets` |
| 中国石油 营业收入 2,864,469（百万元） | 完全没读到 |

**数字读对了，主体名与科目名错了。** 一个「数字正确、归属错误」的事实，
在金融场景里比"没读到"更危险：它过了 `quote` 回读闸门、置信度 0.95、
会一路流进估值模型和核查规则，而下游完全看不出它贴错了标签。

## 二、三个根因（已全部修复）

### 根因 1：财务报表没有主体列，而系统只会从表头找主体

公告表格的表头是「被担保方 | 金额」，主体名就在行里。财务报表现金流量表则是：

```
项目                | 2025年度        | 2024年度
经营活动产生的现金流量净额 | 246,931,681.41 | 185,187,778.45
```

报表主体（"湖南发展"）不在表内，它在报表标题上；而表头两列是期间。
系统于是把行标签当成了主体：

```
entity = '营业收入（元）'                    ← 实际是列标签
entity = '归属于上市公司股东的净利润（元）'
entity = '购建固定资产、无形资产和其他长期资产支付的现金'
```

后果：一份报表的数字被拆散到几十个伪主体名下，而且不报错。

修复：新增行导向抽取路径 `extract_statement_facts` ——
识别出财务报表后，主体取文档主体，指标取行标签，期间取列头。

### 根因 2：期间列没有被当作期间来源

事实库的期间分布（修复前）：

| 文档 | 期间分布 |
|---|---|
| 000722 湖南发展 | `{2025A: 197, 2019A: 1}` |
| 002716 湖南白银 | `{2025A: 38}` |
| 601857 中国石油 | `{2024A: 5}` |

三年报的 2024 年比较列全部丢失。利润表、现金流量表、资产负债表
都是"本期 + 上期"并排，系统把两列都打成了文档级期间（2025A）。

后果：多期估值（R4 的 DCF 需要至少两期）拿不到数据；同比分析（R5 的 E5）无从校验。

修复：`periods_of_columns` —— 列头显式年份（`2025 年度` → `2025A`）
+ 相对写法（`期末余额` → 文档期间、`期初余额` → 上一期）。
修复后 2024 期事实从 5 条增至 100+ 条。

### 根因 3：表格级货币单位没有下传 + 百万元量纲未处理

`build_stats.json` 显示：`rejected_no_unit: 377` ——
规则引擎的 398 个候选里，377 个因为"无单位"被拒收。

这个拒收逻辑本身是对的（本项目铁律：宁可拒收也不猜单位），
问题在于：单位的权威来源是表格标题行（`单位：元` / `金额单位为人民币百万元`），
而这个信息没有从表格层传到事实层。

修复（三个子问题）：

1. `find_unit_declaration` 原先要求 `单位：` 连写，匹配不上中国石油的
   `(除特别注明外，金额单位为人民币百万元)` —— 于是 273 页一个数字都没抽到。
2. 它还会把 `编制单位：湖南能源集团发展股份有限公司` 当成单位声明，
   让整表单位变成"湖南能源集团"而因量纲族不符被拒。
3. 单位声明只在报表首页印一次，续页直接是数据行 —— 需要按文档延续。

修复后表格路径的 `rejected_no_unit` 从 459 降到 0。

## 三、修复过程中额外发现并修掉的四个缺陷

| 缺陷 | 症状（都不报错） |
|---|---|
| `build_header` 用"别名命中最多"选表头行 | 报表的每一行标签都是指标名，数据行命中数超过真表头 → `data_start` 被推到第 3 行，前两行数据整行丢失；表头文本变成「2025 年度349,165,168.51」这种混合串 |
| PDF 把一格拆成多格 | `2024 \| 年 \| 2023 \| 年`；脚注编号 `( \| 2 \| )` 把后面所有列挤偏一位 |
| 列号被当成列表 | 合并格跨多列时 `col_maps` 存的是列表，下游当 dict 键用 → `TypeError: unhashable type: 'list'`，而且是在 judge 跑完 24 分钟后才炸 |
| 折行修复会修出位数不足的值 | `218,073,073.97` → `218,073,07`，位数少 4 位、置信度仍是 0.95，直接入库流向下游 |

最后一条催生了两个新防线（F4/F5）：

- `truncation_suspect`：`raw_text` 位数 / 千分位分组与解析值不一致 → 提升为 `needs_review`
- `unit_scale_outliers`：同表内同指标数量级差 10³ 以上 → 标记可疑

修复后本次运行有 3 条被这两个守卫标记（此前是静默通过）。

| # | 缺口 | 具体表现 | 性质 |
|---|---|---|---|
| 1 | 母公司列与合并列并列在同一页 | 000722 的 p77 上半是合并表、下半是母公司表，两者列结构相同 → 母公司表的 `所有者权益合计` 覆盖了合并数 | 需要按报表标题（「合并」/「母公司」）区分同页并列的两张表，并映射到 `statement_scope` |

| 3 | 2024A 比较期仍有零星漏抽 | 002716 的 `net_profit_parent 2024A`；601857 的 `revenue 2024A` | 同缺口 2 |
| 4 | 中国石油 2024 年报的 `total_assets 2024A` 被抽成 `2700000` | 取到了「期末总股本（亿股）」等相邻行 | 错行取值；`unit_scale_outliers` 只覆盖同表内比较，跨行错取需另加"指标-行标签一致性"校验 |

四条都是表格形态覆盖度问题，不是"读错数字"。共同修复方向：
支持「分组表头 + 多期并排 + 合并/母公司并列」这一形态。

## 五、修复过程中发现的第三个静默失败：运行状态没有反映失败

`agent replay --strict` 报『不可复现』时说不出原因。查下去发现：

- 一步表格裁决的 VLM 调用失败 1 次（偶发网络错误）
- judge 阶段已经计数了（`table_cells_failed`），也打印了警告
- 但阶段状态仍是 `success`、运行状态也是 `success`、产物照常落盘

后果：失败的那次调用没有响应缓存 → 离线回放无法重现它 →
回放报"不可复现"，而没有人知道原因（失败信息只在产物字段与 trace 里）。

修复：阶段返回值可带 `partial_failures` 标记，调度器据此把整次运行标为
`partial`，回放报告也会引用它说明"本次不一致是预期结果"。

> 这是本项目第三次遇到同一类问题："异常必须计数"已经做到了，
> 但计数没有传导到状态。计数只进产物，没人看；状态才是要被看见的东西。

## 六、那一轮验证的元结论

第一轮验证（77 份公告）让系统的确定性路径（表格网格 + 规则引擎）
成为主力，方向是对的。但那一轮的材料只有一种表格形态：
「主体在行、单期、单位在单元格内」。

真实年报带来了三种新形态：

1. 多期并排（本期 + 上期）—— 期间在列头，不在单元格
2. 表级单位（`单位：元` / `金额单位为人民币百万元`）—— 单位在标题行
3. 跨页续页（合计行在续页，而表头只在首页）—— 与公告表相反

系统对这三种形态的处理是缺失的，而且缺失方式是"静默降级"：
不报错、不警告，只是把数字贴到错误的主体/期间上、整表拒收，
或者用别处的同名指标顶上（子公司数顶替合并数）。

> **这正是真实数据验证不可替代的原因。**
> 合成样例与公告语料都无法暴露这类问题 —— 因为它们的表格形态恰好是被支持的那一种。
> 如果只用公告材料交付，R4 会在评审现场当场失效。

### 7.2 评测集：注入式错误 + 公开说明

### 7.4 第三轮评测结果（`runs/r5-final4`，评测集与基准已统一真值源）

统一真值源之后（`data/r5_eval/truth.py` 为唯一来源，基准 / 草稿 / 标注全部由它派生），
评测集不再自相矛盾。实测：

| 指标 | 值 |
|---|---|
| 参与评测草稿 | 3 |
| 真阳性 / 假阳性 / 假阴性 | 2 / 9 / 6 |
| 精确率 / 召回率 / F1 | 0.1818 / 0.2500 / 0.2105 |
| 错误类型覆盖率 | 0.2500 |

8 条发现里 6 条是假阳性，全部来自两个尚未修完的入口问题：

- 碎片段 `08.72`（`revenue = 8.72 元`）仍在参与比对 → 4 条假阳性
- 「10股」这类单位片段被当成数字主张去查来源 → 2 条假阳性

而 9 条注入错里 6 条没被报出。逐条对照后发现：漏报的原因不是规则不会查，
是事实库里没有可用的参考值，或者选错了行。

| 漏报的注入错 | 需要的参考值 | 事实库现状（`annual10`） |
|---|---|---|
| 000722 所有者权益（母公司数冒充合并数） | `equity_total 2025A` = 3,797,417,361.30 | 库里是 3,189,997,628.22（母公司数） |
| 000722 负债合计少一个数量级 | `total_liabilities 2025A` = 364,789,378.77 | 库里是 357,822,700.00 |
| 601857 资产总计误用 2024 年数 | `total_assets 2025A` = 2,828,017,000,000 | 比对到了 2,700,000（= `2.7` 那条漏换算） |
| 601857 分红占比算错 | 分红总额 / 归母净利润 | 受控语料里没有分红公告（见 §7.6） |

> **结论：R5 的规则在正常工作，卡住它的是 R1 的事实质量。**
> 权益 / 负债 / 资产总计这三条基准值我已人工读原页确认（§3.1），
> 而事实库里同期间的对应值是别的数 —— 说明报表抽取在多个候选行之间选错了行。
> 这与"抽不到"是两类问题：抽不到会让基准项显示"漏抽"，
> 选错行会让基准项显示"数值不符"（本次 000722 的三项全是这一类）。

### 7.5 因此下一轮的优先级变了

原计划是"先修评测集、再修 R5 守卫"。评测集修完之后瓶颈清楚了：

| 优先级 | 事项 | 为什么 |
|---|---|---|
| P0 | R1 报表抽取的"选行"准确性 | 000722 的权益 / 负债 / 资产总计三项都取到了邻近行的值。R4 的 DCF 与 R5 的比对都依赖这三个数 |
| P1 | R5 入口剔除形态缺陷事实 | `_fact_has_numeric_defect` 已写但未生效（6 条假阳性里 4 条来自它） |
| P1 | 单位片段不进"来源查找" | 「10股」「每 10 股」应排除（余下 2 条假阳性） |
| P2 | 受控语料补分红 / 股本类公告 | R5 的可核验边界由受控语料决定 |

### 7.6 一处需要说明的行为

`runs/r5-eval5` 对 601857 草稿报了一条 E4：分红总额 457.55 亿元在原始材料中
找不到来源。

经核对：该数字确实存在，出自中国石油 2025 年年度 A 股权益分派实施公告
（`data/drafts/_public/`），但 R1 的受控语料 `data/real/` 里只有年报、没有这份
公告。所以这条其实是"在给定受控材料里无法核验"。

这是赛题「在封闭或半封闭数据环境中运行」的预期行为：系统不声称某数字错，
而是声称"我手上的材料里找不到它"，并给出可执行建议。
但它也说明：受控语料的范围决定 R5 的可核验边界 —— 要核验研报里的分红、
股本、估值倍数，受控目录里就得有对应的公告与行情数据。

## 七之二、P0 追查结论：报表口径（合并 / 母公司）

### 结论一：不是"选错行"，是同一指标在同一期间有多个口径的值

用证据锚点逐条追出 `equity_total 2025A` 的真实出处，并用网格全文检索确认：

| 值 | 网格位置 | 行标签 |
|---|---|---|
| 3,189,997,628.22 | p75 r23 | 所有者权益合计 |
| 3,432,627,982.53 | p77 r24 | 所有者权益合计 |
| 3,797,417,361.30 | p76 r24 | 资产总计（= 负债和所有者权益总计，p77 r26 同值） |
| 364,789,378.77 | p77 r13 | 负债合计 ← 基准真值在这里 |
| 357,822,681.50 | p75 r8 | 负债合计 |

所以事实库同时存在不同口径的同名指标，全部标 `2025A`、都不区分口径。
下游（R5 的比对、R4 的 DCF）任取一个都可能取错，且不报错。

### 结论二：真正的难点是一页含两张不同报表的表

第一版按"上一页继承"实现，实测把合并表标成了母公司表；第二版改成
"全文档标题扫描 + 最近前置标题"，仍然错。全文扫描本身是成功的
（9 个标题，页码与口径全对）：

```
p73 y=74.2    consolidated  1、合并资产负债表
p75 y=447.8   parent_only   2、母公司资产负债表
p77 y=492.3   consolidated  3、合并利润表
...
```

错在归属。网格检索揭示了真实结构 —— 同一页同时有两张不同报表的表：

```
p73 ─ 74     合并资产负债表（前段）
p75 表0      母公司资产负债表（负债合计 357,822,681.50）
p75 表1      合并资产负债表（后段）
p76          合并资产负债表（资产总计 3,797,417,361.30）
p77 表0      合并资产负债表（尾段，负债合计 364,789,378.77）
p77 表1      合并利润表
```

于是两种朴素判据都会错：

* 按上一页继承 → p77 表0 会继承"合并利润表"口径
* 按最近前置标题 → p75 表0 会归属到 p73 的「1、合并资产负债表」，
  而它其实是母公司资产负债表

### 结论三：判据是矩形交叠；接入后合并口径已干净

按顺序试过并逐一否决的判据：

| 尝试的判据 | 实测结果 |
|---|---|
| ① 按上一页继承 | p77 表0 继承了"合并利润表"口径 —— 错 |
| ② 全文档标题扫描 + 最近前置标题 | p75 表0 归属到 p73 的「合并资产负债表」，但它其实是母公司表 —— 错 |
| ③ 按 ``(page, y0)`` 坐标先后配对 | 7/8 单测通过，接入管线后合并真值被标成 parent_only —— 错 |
| ④ 标题文本框 ↔ 网格表矩形交叠（`store.scope_by_overlap`） | 接入后合并口径干净 |

根因：表格的视觉顺序与报表的印刷顺序不一致。证据：
`p77 y=72.1` 的表在视觉上位于 p77 标题（y=492.3）之前，但它属于
p73 开始的合并资产负债表；`p77 y=533.2` 的表在标题之后，属于合并利润表。
仅凭坐标先后无法配对 —— 必须用空间关系（横向必须重叠、纵向间距最小）。

第 ④ 版在真实坐标上的配对结果：

```
p73  y=137.1 → consolidated     p76  y=72.1  → consolidated
p74  y=72.1  → parent_only      p77  y=72.1  → consolidated
p75  y=72.1  → parent_only      p77  y=533.2 → consolidated
p75  y=486.7 → parent_only      p79  y=535.7 → parent_only
```

接入管线后的核对（`annual16`）—— 下游需要的合并口径已经干净：

| 指标 | 结果 |
|---|---|
| 合并 资产总计 / 所有者权益（3,797,417,361.30） | 仅带 `consolidated` |
| 合并 负债合计（364,789,378.77） | 仅带 `consolidated` |
| 母公司 资产总计（3,547,820,309.72） | 两种标签混用 |
| 母公司 所有者权益（3,432,627,982.53） | 被误标为 `consolidated` |

口径分布从"全部 consolidated"变为 801 consolidated / 86 parent_only。

剩余精度问题：母公司的数值带混合标签，原因是同一数值在报表正文与附注中
多次出现，而附注的表被配到了别的标题上。它不影响合并口径（合并值已干净），
但会给"专取母公司口径"的下游带来噪声。下一步可用同一套矩形交叠思路处理附注区。

> 方法论收获：前三次失败都源于把问题当成"顺序"问题（谁在谁前面），
> 而它本质是空间归属问题（这个标题管哪块区域）。
> 判据选错方向时，再多单测通过也没用 —— 第 ③ 版单测 7/8，接入后照样错。

### 结论四：一处基准值需要复核（不影响上述结论）

基准表里 000722 的 `total_assets 2025A` 写的是 3,797,417,361.30
（标注为"由负债+权益勾稽推算"）。网格显示这个值在 p76 r24 是「资产总计」行，
因此数值本身是对的；但同一份表里 p75/p77 还有别的「负债合计」「所有者权益合计」，
说明我最初读页时把不同报表的合计读混了。这一点在下一次基准复核时要一并订正
（`data/r5_eval/truth.py` 已有单一真值源，订正只需改一处）。

这一步做完，000722 的权益 / 负债 / 资产三项才能只留合并口径的那一条，
R4 的 DCF 也才有干净的输入。

（后续复核已定位到成因：3,797,417,361.30 是母公司口径的勾稽结果 ——
母公司负债合计 364,789,378.77 + 母公司所有者权益合计 3,432,627,982.53。
合并口径应为资产总计 3,547,820,309.72、负债合计 357,822,681.50、
所有者权益合计 3,189,997,628.22。`verify_truth` 里 000722 的 5 条不符
全部源于此。真值文件尚未改动。）
