## 一、为什么需要第二轮验证

第一轮的验证对象是公告类材料（对外担保/质押/中标/股权变动/利润分配，77 份）。
那一轮暴露出的最重要问题是：R4（自动化估值建模）没有可估值的标的 ——
公告只披露子公司数据，没有披露主体自身的三大报表。

因此第二轮的材料是上市公司定期报告，直接对准 R4 的输入要求。

| 项 | 内容 |
|---|---|
| 目标公司 | 湖南白银（002716）、湖南发展（000722）、中国石油（601857） |
| 材料 | 3 份 2025 年年报 + 1 份 2024 年年报（跨报告一致性用） |
| 页数合计 | 185 + 205 + 273 + 280 = 943 页 |
| 存放位置 | `data/real/定期报告/`（不是 `data/raw/`） |
| 取数方式 | `tools/fetch_disclosure.py` —— 从证监会指定披露网站（巨潮资讯）取，每份留 URL + sha256 + 抓取时间 |
| 来源记录 | `data/real/定期报告/_SOURCES.json` |

> 注意：**为什么必须放 `data/real/` 而不能放 `data/raw/`**（踩过一次）：
> `data/raw/` 是自动化测试夹具的输入目录 —— `tests/test_web.py` 会以
> `--data data` 跑一次完整流水线。943 页年报放进去之后，
> 每次跑测试都会顺带处理它们，测试从 36 秒变成 10 分钟以上，
> 而且看起来像"测试变慢了"，不像配置错误。
> 受控材料与测试输入必须分开存放。

## 二、基准值的产生方式（不经过本项目管道）

```
① tools/_tmp_locate_statements.py   只定位页码，不读数值
        ↓
② 渲染关键页为 PNG（150 dpi）
        ↓
③ 人工/独立视觉直接看原图，记录数值
        ↓
④ 与 facts.json 比对（tools/validate_against_source.py）
```

第 ① 步"只定位不读值"是有意为之的：如果定位脚本顺手把数字打出来，
标注者就已经被自己的工具锚定了一次。

### 单位纪律

中国石油的年报全部以「人民币百万元」为单位。基准值一律换算成元再比对，
这样「系统是否正确处理了量纲」本身成为被测项。

> 为什么要专门测这个：量纲差 10⁶ 是金融数据抽取最典型的严重错误。
> 一个把「2,864,469 百万元」读成「2,864,469 元」的系统，
> 数字每一位都对、`quote` 也能回读成功，但整条下游链路（估值、核查）全废。
> 这类错误不会被常规的"字符准确率"指标发现。

## 四、判定标准（同样预注册）

| 层次 | 指标 | 通过线 |
|---|---|---|
| 抽取召回 | 命中数 / 基准项 | ≥ 80% |
| 抽中准确率 | 数值一致 / 命中数 | 100%（金融数字不接受"差不多"） |
| 量纲正确率 | 未出现 10ⁿ 倍数错误 | 100%（最严重的一类） |
| 跨报告一致性 | 两份年报对 2024A 的读数一致 | 必须一致 |
| 证据可回溯 | 每条基准事实都能定位到正确页 | 100% |

容差：相对误差 ≤ 0.1%（仅用于容忍"元/万元"换算的舍入，不容忍量纲错误）。

## 五、复用方式

```bash
# 取数（带来源留痕，默认写入 data/real/定期报告/）

# 与人工基准核对
```

## 六、已知的限制

1. 基准项数量有限（28 项）：只覆盖"主要会计数据"表与三大报表的头部科目。
   它验证的是准确性与量纲，不是全字段召回率。
2. 中国石油 2024 年报的基准值取自其 2024 年报的 p8，
   而 2025 年报的 2024 年比较数取自 2025 年报 p7 —— 两者本应相同，
   若不同则说明存在追溯调整，需人工判断而非直接判错。
3. 可比公司数据仍未接入：R4 的相对估值部分依然只有离线静态样本（占位）。
   本轮验证能让 DCF 跑在真实三表上，但相对估值仍需下一轮。
