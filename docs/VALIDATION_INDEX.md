## 一、总体结论（一句话）

在四份真实年报（中国石油 2024/2025、湖南发展、湖南白银，共 943 页）上，
R1→R4→R5 全链路跑通；关键科目与人工逐页核对的真值一致；
每一条估值参数与每一个纠错结论都能追溯到具体页、具体格；
十八轮验证共修掉 34 处缺陷（另留档 4 处被实测否决的改动），
还有 5 处未能解决的问题被明确记录并量化。

> （那会让 DCF 退化成把市价重算一遍）。

## 四、修掉的缺陷（按类型）

### 4.1 静默错误（数字看着对，实际错）

| 缺陷 | 后果 | 修复 |
|---|---|---|
| 行标签里的单位被漏看 | 现金放大 100 倍 → 净债 −20.4 万亿 → DCF 每股 ¥124.41 | 单位优先级补上 `row_label` |
| 列序回退把期间派给错误的列 | 同一期间出现两个值，污染 R4/R5 | 判据③ 收紧到"表内完全没有期间标签"才启用 |
| 标题行被当成数据行 | 真表头被吞 → 整表 0 候选 | `data_start_row` 排除年份与日期碎片 |
| `base_year` 硬编码 2024 | 报告年份锚点整体偏移一年 | 从事实期间派生 |
| `market_cap = pe × 目标公司净利润` | "可比公司市值"永远是错的 | 直接取真实市值，不再反推 |
| EBIT 率用净利润冒充 | DCF 每年 FCFF 被系统性高估 | 改用 `operating_profit` + 合理性闸门 |
| `capex < D&A` 未被检查 | 改用更准的 D&A 反而把 DCF 从 15.21 抬到 22.54；等于在永续经营假设下隐含"不重置资产"（清算） | 构造前一致性闸门 + 模型层硬校验（两道关） |
| 表头与数据按列号强行配对 | 拼出 `'12目'`／`'月2025'` 这类标签；数字对、标签全错、不报错 | 改按 x 区间重叠重建列结构 |
| 事实库不保存行标签 | 复核 capex 时只看到数值与"同表冲突"，无从判断该采信哪条 | `channel_readings[].note` 写入行标签与列期间 |
| 改进是否生效没有计数器 | 加在 `tstats` 里的计数被返回字典吞掉 → "从未触发的分支"与"一直在工作的分支"在产物里长得一样 | 计数汇入 `build_stats.json`；另加 `tools/grid_align_report.py` 做独立复核 |
| 新增枚举值被 if/elif 白名单静默丢弃 | "按列定口径"在表里算对了、产物里却仍是旧值，改动等于白做且不报错 | 映射抽成 `_SCOPE_OF_CANDIDATE` 表 + 护栏测试断言每个枚举都有归宿 |
| 同一个决策写在两处，第二处覆盖第一处 | 依据文字写"取中位数"，实际用的是最大值 —— 文字与取值不一致且不报错 | 删掉重复的 `best` 计算，注释说明为什么只能有一处 |
| 标签列判据只在一个样本上验证 | 标签缩进 20pt 时被算进数值列 → 数值与标签挤进同一格 → 现金流量表 D&A 整条读不出来 | 判据改为"不与数值列重叠"（对缩进不敏感）+ 丢值检查 |
| 流水线模块自报阶段名，报的是**单跑**计划的名字 | `full` 计划下 **482/935 条事件（51.6%）**挂在该计划里不存在的阶段名上（`ingest` 274 · `extract_ocr` 104 · `judge` 90 · `build_facts` 6 · `assumptions`/`audit`/`report`/`export`/`extract_text`/`extract_tables` 各 1–2）；三个真实 full run 实测 482 / 482 / 483，稳定复现。左栏按 `_` 切分取任务名所以**看不见**，右栏与 `trace.jsonl` 里全在 —— 同一份代码在两种计划下有两个名字 | 42 处自报阶段名全部删除，改由编排层定名（`__boot__`/`__loop__` 这类伪阶段必须显式传名）；端到端测试断言事件上的阶段名必须属于**本计划** |

### 4.2 被实测否决的改动（留档以免重犯）

| 「行内期间塌陷」守卫：同一行的多条候选落在同一期间就全部标为需复核 | needs_review 159 → 529、可用 `equity_parent` 16 → 0、R4 连净资产都取不到 —— 因为它把每一张财务报表的本期/上期两列都当成了塌陷 | 已删除并留档；判据抓到的现象是真的，但杀伤半径没有先量过 |

### 4.3 两次被自己的测量否掉的判据（最终收敛，留档）

| 判据版本 | 实测结果 | 处置 |
|---|---|---|
| 守卫「期间字典为空」 | 命中 50 张，但目标表不在其中（它的 `col_period` 非空） | 否掉 |

### 4.4 一条新确立的工程纪律

> 判据的杀伤半径必须在启用之前量出来。

第十三轮那守卫是"写完再量"，代价是一次 20 分钟抽取 + 一次推翻重来。
第十四轮先写了量测工具（`tools/year_sequence_report.py`），
在 987 张真实表上量出命中率与附带损害，据此两次否掉自己的判据，
第三次（期间碰撞）才收敛到 4/987 张、零误报 ——
最终启用的版本是量出来的，不是想出来的。

### 4.5 四条被实测否决的改进（都留档在代码注释里）

| 改进 | 推理 | 为什么被否决 |
|---|---|---|
| 「行内期间塌陷」守卫（第十三轮） | 同一行的多条候选落在同一期间就全部标复核 | needs_review 159 → 529、可用 `equity_parent` 16 → 0 —— 它把每一张报表的本期/上期两列都当成了塌陷 |
| 合计类指标「取最大值」并列打破键（第十五轮） | 合并 ≥ 母公司，所以最大值是集团数 | 000722 的总资产有 17 条候选，其中一条垃圾值比真值还大 → 加上这条键选中的正是它，比不改更糟 |
| 同期候选「取中位数」（第十四轮） | 分歧时避免被最大值带偏 | 只是「错得少」：真值是最小的那条，中位数取到了 2023 年的数 |
| 「整页高续表」改按文档顺序取口径（第十六轮） | 续表 bbox 整页高，标题必落在表内，纵坐标判据失效 | `needs_review` 179 → 177（只少 2 条），而 000722 的 2024A 从「有自洽三元组」变成完全没有数据 —— 净效果为负；口径与期间在续表上互相纠缠，改一个会把另一个带偏 |

> 三者的共同点：假定"数值的大小顺序有信息"。实测里错误值经常更大也更小，
> 唯一站得住的用法是先过会计恒等式过滤、再排序（第十五轮的联合选择）。

### 4.6 一个必须说清的区分

`tools/verify_truth.py` 测的是「库里有没有这个值」（抽取层），
而 R4 的 `_best_fact` / `_select_consistent_triple` 决定「选了哪一个」（选择层）。
两者是不同的问题 —— 第十五轮修好了后者，但前者的数字不会变。
不把这个区分写清楚，"数字没变"就会被误读成"没修好"。

### 4.4 工具自身的可用性缺陷

| 缺陷 | 后果 | 修复 |
|---|---|---|
| `fact_probe.py` 在 GBK 控制台崩溃 | 排查工具在最需要它的时候抛 `UnicodeEncodeError` 中断 | 显式 `reconfigure(errors="replace")` 降级 |
| `web_smoke.py::pick_runs()` 只挑"最新的 run"当回归夹具 | 任何人（包括评委）往 `runs/` 里跑一个新 run，它就自动顶掉夹具：跑到一半崩掉的 run 与 `--mock` 自检 run 都当过夹具，于是「双路互证」「勾稽断言」双双报 ✗，而**同一份代码**在旧夹具上两项都 ✓ —— 报的是被验那个 run 的毛病，读的人却去翻代码（实测：修前挑中崩掉的 run，修后挑中 partial 的正常 run） | 加两道坎：`status == "failed"` 与 `provider == "mock"` 都不当夹具（mock run 答不出「双路互证」——那条表格路是 VLM 走的）；筛空退回 `demo`，不留空串 |
| 空 `agent_log.jsonl` 的 run，右栏只留一片空白 | `Tracer.__init__` 一建就 append 打开这个文件（`tracer.py:202`），所以**每个** run 都有它，包括一次模型调用都没发生的 run —— 实测 21 个 run 里 `demo`/`cfg-test`/`prov-offline`/`prov-online` 四种 journal 是 0 字节（`trace.jsonl` 里只有 `stage` 事件，一条 `llm_call`/`tool_call` 都没有；`demo` 那份的材料有文本层，不需要 VLM）。它们与「右栏坏了」在屏幕上长得一模一样，而两种情形该做的事完全相反 | 只认**整个文件为空**（文件非空而筛选后一行不剩不算），后端补一句「该 run 没有记录到模型或工具调用」；同一次还发现 mock 那行「这些回答来自 mock provider」在零回答时是假话，改为有记录才说 |

>
> 同次实测的打包数字（文档原先写 318 文件 / 72.5 MB → 56.5 MB，已按实测改为
> **335 文件 / 72.9 MB → 压缩后 56.7 MB**）：多出来的文件里，`tests/` 与
> `web/` 是这半个月新增的测试与前端模块（`tests/` 25 个、`web/` 32 个），
> `data/` 多出的 2 个是下面这条。
> 密钥扫描通过（`scan_secrets` 名单里只有 `.env.example` 这个模板，它本来该在）。

**测试用的数据随包**（2026-10-16，用户的判词：「把测试用的数据附带上啊」）。
原先 `data/raw/` 整目录不进包（受控材料），而 9 条测试（`tests/test_harness.py`
6 条 + `tests/test_replay_resume.py` 3 条）靠 `data/raw/*.pdf` 做输入 ——
解压后跑 `pytest` 会看到 9 个「缺少 data/raw 下的测试材料」，像套件本身不完整。
那两份 PDF 其实是**合成样本**（`tools/make_sample_data.py` 生成，
22 KB + 13 KB，不含任何真实材料），与「受控材料不进包」这条并不冲突。
改法是**按文件名点名放行**（`DATA_FILE_ALLOW`），不是把整个目录开白：
谁往 `data/raw/` 里丢一份真实年报，它照样进不了包。
守卫同步收紧成三条：例外文件的**名字**必须在名单上、单个 < 64 KB、
**合计 < 256 KB** —— 原先那条「受控目录里不许出现 `.pdf`」是拿扩展名当替身，
现在换成了更贴题的名字判据（`sample_*.pdf` 本来就是 PDF）。

### 9.7 文件访问接入编排层（2026-10-17，非数据验证轮）

赛题要求「完整记录文件访问、工具调用、计算过程和结果生成」。前三条是真的，
第四条本仓一直**只建了通道没接线**，并把这句实话写在四个地方（README、
`docs/COMPETITION_FIT.md`、`docs/REVIEWER.md`、项目计划书）。

**先实测，再动手。** 查源码只能看到「类写得很好」，看不出有没有人调用它 ——
实测的是运行结果：`pipelines/` 与 `agent/runtime/` 里 `ctx.guard()` 零处出现，
`FileGuard` 只在 `tests/test_harness.py` 里被实例化过；连跑 5 次 full run，
每次 `trace.jsonl` 里 `file_access` 事件数都是 **0**。

**接入方式**：`RunContext.guard()` 懒构造一个 `FileGuard`（懒构造不是优化，
是必需 —— `build_context` 跑在 CLI 把 `--data` 摊进 `ctx.configs["paths"]`
**之前**，提早构造会让读根只剩兜底值，实测表现为 `inbox/raw/sample.pdf`
被自己判越权）。读根 = 材料目录 + `configs/` + 本 run 与上游 facts run 目录，
**故意不含 `PROJECT_ROOT`**。每个读写点位都从它走，出口是 `Tracer.file_access()`。

两个坑都是**跑出来才发现**的：

| 坑 | 实测症状 | 改法 |
|---|---|---|
| 路径记了绝对值 | `C:/Users/<用户名>/…` 被写进 `trace.jsonl` —— 那是交给评审的交付物 | `FileGuard._log` 统一转相对路径 |
| 阶段全是 null | 首批 71 条 `file_access` 的 `stage` **一条不差全是 null**，读者无法把一次访问挂到某一步上 | 与 `tool_call` 同一条规矩：不传就借 `Tracer._in_stage()` 取编排层当前阶段（`llm_call` 曾 400 条 null，同一课不犯第二次） |

**不代劳 I/O 的那一类**：PyMuPDF 的 `fitz.open` / `pix.save`、matplotlib 的
`savefig`、PIL、openpyxl 都在 C 扩展或第三方库里 open 文件，`FileGuard` 包不住，
也不该包 —— 改写这些调用可能让产物多一个字节，而一个字节之差就是哈希不匹配、
`replay --strict` 判「不可复现」。对这些点位用 `FileGuard.record()`：
**校验 + 留痕，不代劳读写**。

**顺手删掉最后一处绕开 guard 的读**：`table_facts.py` 的 `_default_alias_map()`
就地读 `configs/metrics.yaml` 再做进程级缓存 —— 那次读在 trace 之外。
它不是非读不可：调用链上 `alias_map` 本来就是现成参数
（`extract_table_facts` 的入参），传下来即可，代价为零。

**实测判据**（写进 `tests/test_harness.py::test_end_to_end_full_pipeline_mock`，
三层缺一层都挡不住）：

1. **有** —— 一次真实 full run 的 `file_access` 不为 0（防"接入被改回去"）
2. **对** —— 每条路径都是相对路径、`mode` 合法、带 `sha256`、归到计划里**真实存在**的业务阶段
3. **全** —— 盘上**每一个**产物都有对应的 `write` 记录（"完整"二字的唯一判据）

一次 mock 全流程实测：**71 条**（37 读 / 34 写），涉及 38 个文件，
盘上 34 个产物零遗漏，缺失 sha / 阶段 / 绝对路径者各 0 条。

**这套记录本身的代价（单独量过，别让它背锅）**：把该 run 的 71 条记录涉及的
文件全部重算一遍 sha256 是 **0.0195s**（723 KB，单条平均 0.275 ms）——
即每次 run 多花约 0.02s。同一轮里发现全库测试耗时在同一天从 170.65s 涨到
387.99s / 413.46s，先把"是不是新加的逐条记录拖慢的"排掉：按 0.02s/run 算，
套件里就算跑几十次全流程也只累加不到 1s，数量级对不上，那是本机负载。
（同机单次 `run full --mock` 墙钟三次为 9.47 / 9.46 / 9.33s，很稳，
也印证了慢下来的是**套件整体**而不是单次运行。）
**收尾时又跑了第四次，机器空闲，回到 177.60s** —— 这一条把"负载"从推测落成了
证据：同一个套件、同一份代码，只因为机器忙不忙就在 170–180s 与 390–415s 之间跳。

**同一类问题的第二处：`run` 会把一份好 run 写坏（同日一并修掉）**。
`Tracer` 以 `"a"` 模式打开 `trace.jsonl`，不带 `--resume` 对已有 run 重跑时，
新事件会追加在旧事件后面、`seq` 从 0 重来。实测：同 run 名跑第二遍后
`trace.jsonl` 从 146 行变 292 行、**146 个 `seq` 全部重复**，紧接着 `verify`
判「❌ 不可复现」。评审照文档把同一条命令敲两遍就会看到这条红字 —— 这不是台账
难看，是把一份能复现的 run 弄成不能复现的。所以 `run` 现在发现目标目录里已有
产物、又没带 `--resume` 时**拒绝执行**（`HarnessError`，退出码 3），并给出两条
出路：加 `--resume` 续跑，或删掉目录 / 换 `--run-id` 从零重来。
`tools/demo_run.py --warm` 撞上已有目录时自动改走 `--resume` —— 它的本意就是
复用缓存，而不带 `--resume` 重跑正是制造重复 `seq` 的那条路。
判据：`tests/test_harness.py::test_run_refuses_to_append_to_an_existing_run`，
不只断言退出码，还断言**被拒的那次一个字节都没写**、以及 `--resume` 不被误拦。

**打包核对时发现的第三处：仓库缺了 `agent/sample/`**。清单记的完整包是
335 文件 / 72.9 MB，实测只有 258 / 26.3 MB —— 差额（77 个文件、47 MB）正好是
README、项目计划书、`docs/P0_VALIDATION.md` 都当成存在的**77 份已分类真实公告**。
已从 `Downloads/1` 的留存副本恢复（77 个 PDF，文件名逐一核对、无多无缺），
完整包随之回到 335 文件。README 与项目计划书里关于 `agent/sample/_scratch/`
那 219 份临时件的"现状"描述一并改成与仓库一致（历史结论按注留存，不改）。

**连带的订正**（都属"文档在说自己没做的事"这一类）：

- `runs/demo` 按新代码重跑 —— 28 个产物逐字节不变，6 个（`facts.json` /
  `documents.json` / `evidence.html` / `valuation.json` / `audit.json` /
  `audit_report.md`）因为内嵌了运行起始时间而变；`verify` 与
  `replay --strict` 都仍判「✅ 可复现」。
- 页面上「文件访问」这一格**前后写过两版假话**：①「框架层统一记录，不会出现
  追溯断点」（写它的时候计数恒为 0）；②「未接入编排层」（接入之后对新 run 也是假的）。
  两版都钉进 `tools/web_pages_check.py` 的 `FORBIDDEN`，判据改为**本 run 自己的
  trace**：有几条报几条，0 就说 0（`runs/` 里更早的 `web-*` 因此照实显示 0）。
