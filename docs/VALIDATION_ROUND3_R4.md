# 真实数据验证报告（第三轮）— R4 自动化估值建模

> 输入：`runs/annual16` 的事实库（三家 2025 年报，合并口径已干净）
> 运行：`runs/r4-real5`（`agent run r4_valuation --facts-run annual16`）
> 估值对象：中国石油 601857（事实最全的报告主体）

---

## 一、结论：估值跑起来了，但输入假设被一个错误科目污染过

首次在真实年报上跑 R4 时，估值区间是 ¥10.38 ~ ¥105.19（中值 ¥58.37）——
10 倍宽的区间不是"模型分歧"，而是一个荒谬的假设：

```json
{"name": "ebit_margin", "value": "104.3809", "unit": "%",
 "basis": "...net_profit_parent = 157302000000 元；EBIT 率由该净利润与营业收入推导"}
```

EBIT（息税折旧摊销前利润）被拿归母净利润代替了。

### 为什么这个错误格外危险

它不是单位错误，因此所有量纲类闸门都抓不住：

| | |
|---|---|
| 数值本身 | 0.0549 = 归母净利润 ÷ 营业收入 —— 算式没错 |
| 隐含假设 | EBIT = 净利润 ⇒ 营业成本、期间费用、所得税全部为零 |
| 下游后果 | NOPAT = EBIT×(1−税率) 被系统性放大 → 每年 FCFF 都高估 → 每股价值虚高 |
| 可发现性 | 报告里每个数字都"看起来正常"，没有任何报错 |

这正是"读取了一个错误的科目"——本项目此前定义的失败类型里，
它属于最隐蔽的一类：静默的语义错误，不是静默的数值错误。

---

## 二、已修复的三处

| # | 缺陷 | 修复 |
|---|---|---|
| 1 | EBIT 率用 `net_profit_parent ÷ revenue` 推导 | 改用 `operating_profit`（营业利润）；拿不到时不猜 —— 回退模板值并把缺口写进 `gaps` |
| 2 | 无合理性闸门 | 新增：推导出的 EBIT 率必须落在 (-50%, 80%)，超出即判定取错科目并回退 |
| 3 | 假设的 `unit` 写成 `%` 但值是小数 | 改为 `比率（小数）`，并在注释里定死约定：比率一律以小数存放，报告层负责显示成百分比 |

第 2 条的实测效果（修复后 `runs/r4-real5`）::

    basis: 推导出的 EBIT 率 0.12 超出合理区间 (-50%, 80%)，
           判定为科目取错或量纲错误，回退模板值 12% 并列为缺口。
    is_judgment: True   unit: 比率（小数）

同时修掉了两处导致这个问题更难被发现的实现缺陷：

- 同一假设算了两遍：`ebit_margin` 在假设表与 DCF 输入里各算一次
  （`assumptions.py` 的 337 行与 404 行）。一处改了另一处没改，
  模型与假设表就会说两套话。现在只算一次、两处共用。
- 说明被兜底文案覆盖：`_make_assumption` 在 `basis_from_fact` 为空时
  用 `basis_from_template` 兜底，而当时只给了一路，于是
  "为什么回退模板值"这条最该被看到的信息被
  "主观假设（未标注具体依据）"覆盖。现在两路都给同一段说明。

## 三、跨期错配已修复（`runs/r4-real9`）

修复后的实测结果：

```
ebit_margin = 0.0819    is_judgment = False
basis: 来自事实库（evd_6941c32caebba8d0）：operating_profit = 234579000000 元
       （报告期 2025A，口径 consolidated，置信度 0.95）；
       EBIT 率 = 营业利润 ÷ 营业收入（会计准则口径的息税前利润近似）
区间: ¥10.3795 ~ ¥124.4143
```

分子分母现在同为 2025 年，8.19% 与人工核算
（234,579 ÷ 2,864,469 = 8.19%）逐位一致。

### 3.1 修了三处，其中两处是"取值与说明不一致"

| # | 缺陷 | 根因 | 修复 |
|---|---|---|---|
| 1 | 并排多期的期间判定 | 中国石油「主要会计数据」表把 6–7 期并排，列头只有 `本年比上年增减` 之类、没有 20xx 年份，前两条判据全不命中 → 两列都落到文档级期间，同一物理年份被标成两种期间 | `periods_of_columns` 新增第③条兜底：表头判不出、且表内有多列无期间时，按列序依次指派 `doc_period, prev_period, …`（中文财报恒为"本期在左、上期在右"） |
| 2 | 取值与依赖不同键 | `_fact_value` 按「期间 → 置信度」排序，而 `_fact_summary` 仍按「置信度」取 —— 于是假设的值来自 2025A（234,579），自动生成的文字依据却引用 2023A（255,286） | 抽出统一的 `_best_fact()`，取值与写说明共用同一个选择键：期间最新 → 置信度 → 合并+归母口径 → 信息更完整 |
| 3 | 无口径排序 | 同一指标同时存在 `consolidated/net_parent` 与 `parent_only` 多条，只按置信度取会拿到母公司口径 | 新增 `_caliber_rank()`：合并 + 归母 > 合并 > 母公司 |

第 1 条的实测效果（期间分布，修复前全挤在 `2025A`）：

```
2024A 293 条 / 2025A 261 条 / 2023A 224 条 / 2022A 70 / 2021A 19 / 2020A 15 / 2019A 5
```

`operating_profit` 的 2025A 从"混着 255,286(2024)、253,522(2023)"
变为只剩正确的 234,579。

### 3.2 为什么这类错误特别难发现

第 2 条那种"值与依据指向不同事实"的缺陷，数值本身完全正确 ——
被乘进 DCF 的 234,579 是对的，报告里的每个数字都能回读、单位也对。
但它让报告的可审性失效：读者照 `basis` 去核对，会对不上。

> 这与第 2 节"净利润冒充 EBIT"是同一类问题的两个层次：
> 前者是取错科目，后者是说错来源。两者都不触发任何数值类闸门。
> 可审性只能靠"取值与说明共用同一函数"这种结构约束来保证，
> 不能靠再加一条校验规则。

## 四、方法论收获

"数字对"与"科目对"是两件事，而后者更难守。

本项目的闸门大多针对数值：单位归一化、量纲族校验、quote 回读、算术重算、
量纲离群。这些闸门在"净利润冒充 EBIT"面前全部失效 ——
因为那个数字确实是从事实库里正确读出的、单位也是对的、quote 也能回读。

挡住它的是合理性判据（EBIT 率不该超过 80%）。
这类判据的特征是：依赖对指标语义的理解，不是对数据形态的检查。
R1 侧的 `metric_of_row_label` 排除词（"归属于母公司"不得映射到 `equity_total`）
属于同一类。后续凡是新增假设推导，都应配一条量级合理性闸门。
