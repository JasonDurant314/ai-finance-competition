## ① 图片 token 折算：1001 token / 页

### 测量方法

同一条 prompt 发两次，一次纯文本、一次带图，`prompt_tokens` 之差即为图片折算量。
这是唯一可靠的测法 —— DeepSeek 官方未公开图像 token 计算规则。

```
第 1 次：prompt_tokens=1046 (纯文本基准 45) → 图片折算 1001 token
第 2 次：prompt_tokens=1046                → 图片折算 1001 token
第 3 次：prompt_tokens=1046                → 图片折算 1001 token
```

三次测量方差为 0，说明折算规则是确定性的尺寸映射，可按页数线性外推。

### 成本推算

| 场景 | 成本 |
|---|---|
| 单页 VLM 裁决 | ¥0.0048 |
| 100 页全页裁决 | ¥0.48 |
| 一份 30 页扫描件（全部页面裁决） | ¥0.14 |
| 竞赛全程调试（按 3000 页次估算） | ≈ ¥14 |

### 决策

全页 VLM 裁决在经济上完全可行，无需为省成本而牺牲第三层。

这条结论很重要：原方案设计了「懒加载裁决」（只在冲突/关键字段/表格时触发）来控制成本。
实测后可以确认，即使对每一页都做裁决，成本也只有几毛钱量级。
因此实际策略可以更激进：优先保证准确性，成本靠缓存兜底
（重跑命中缓存后成本为 0）。

已回填 `configs/models.yaml` 的 `image_tokens` 段，并由
`tests/test_prompts_and_skills.py::test_image_token_estimate_is_measured` 守住。

```
第 1 次：✅ {"doc_type": "announcement", "has_table": true, "numbers_visible": 42, ...}
第 2 次：✅ {"doc_type": "announcement", "has_table": true, "numbers_visible": 42, ...}
第 3 次：✅ ... numbers_visible: 42 ...
第 4 次：✅ ... numbers_visible: 42 ...
第 5 次：✅ ... numbers_visible: 42 ...

▶ JSON 合法率：100%（5/5）
▶ 字段一致率：{'doc_type': 1.0, 'has_table': 1.0}
▶ 中位延迟：3346 ms
```

`numbers_visible = 42` 五次完全相同 —— 视觉读数在关闭思考后是稳定的。

### 一个必须记录的教训：0% → 100%

首次运行时 JSON 合法率是 0%。但原因与模型能力无关，问题出在提示词没给字段名：

```json
// 模型实际返回（合法 JSON，但用了中文字段名）
{"文档类型":"上市公司公告","是否含表格":"是","可见数字个数":38,"摘录原文":"..."}
```

只给 JSON Schema 而不在提示词中说明字段名时，模型会自作主张用中文键。
内容全对，结构对不上。

修正：在 system prompt 里内联完整字段名与枚举值，并给一个输出示例。
修正后合法率立即变为 100%。

由此确立的设计约束（已写入 `domain/prompts/r1_vlm_judge_field.md`）：

> 每个结构化输出提示词必须内联完整字段名、类型与枚举值，并附一个输出示例。
> 不能只依赖 API 的 `response_format` 或 JSON Schema —— 那约束的是格式，不是字段命名。

## ⑤ 思考模式会破坏可复现性 —— 必须默认关闭

这是本次验证中对方案影响最大的发现。

### 官方文档的原话

> "Thinking mode does not support the `temperature`, `presence_penalty`, or
> `frequency_penalty` parameters. Please note that, for compatibility with
> existing software, setting these parameters **will not trigger an error but
> will also have no effect**."

而思维链本身具有随机性。因此：

> 开着思考 + `temperature=0`，同一输入两次运行仍可能给出不同答案。

这直接违背赛题的「运行结果可复现」要求，而且不会有任何报错。

### 附带问题：max_tokens 被思考耗尽

思考消耗计入 `completion_tokens`。实测数据：

| 场景 | reasoning_tokens | answer_tokens |
|---|---|---|
| 「只回复两个字：可用」（extractor 档） | 29 | 2 |
| 「只回复两个字：可用」（critic/max 档） | 93 | 2 |
| 视觉 JSON 稳定性测试（开思考） | 3072（配额全烧光） | 0 |

第三行即故障现场：`content` 返回空字符串，而 `finish_reason` 仍是 `stop`
—— 表现为「模型没回答但不报错」，是最危险的失败模式。

### 采取的两项措施

1. 配置层：产出数字的角色一律关闭思考

| 角色 | thinking | 理由 |
|---|---|---|
| `extractor` | 关闭 | 本质是"读出页面上的字符"，不需要思维链；且必须可复现 |
| `vision` | 关闭 | 视觉感知不需要思维链；且必须可复现 |
| `default` / `writer` | 关闭 | 产物直接进入报告，需可复现 |
| `planner` | 开启（high） | 产出的是计划，不直接成为数字 |
| `critic` | 开启（max） | 产出的是判断，结论经确定性校验兜底 |

已由 `test_thinking_disabled_for_reproducible_roles` 与
`test_max_tokens_leave_room_for_reasoning` 两条测试锁住。

2. 网关层：显式检测空响应

`OpenAICompatProvider._extract_text` 现在会在「`content` 为空但消耗了推理 token」时
抛出带操作指引的错误，不再静默返回空串。空串会被下游当作「模型说没有」，
是这个系统里最危险的失败模式。

该守卫在验证过程中真实触发过两次（探针的 `max_tokens` 给得太小），
证明它有效。

## ④ OCR 准确性验证（赛题明确要求的扫描件与复杂表格）

> 赛题原文：「从非标准化公告、扫描文件和复杂表格中提取……重点考察
> 字段提取的完整性、格式规范性、表格解析准确性和结果一致性。」
> 用户明确要求：「必须通过其他的数据来单独验证一下 OCR 的准确性，这一步不可以省略。」

### 验证方法论：受控退化实验

问题：真实扫描件没有标准答案，无法直接评测准确率。

解法：用电子版 PDF 渲染成图像，文本层即为渲染源，因此标准答案已知。

```
电子版 PDF（有文本层）
    ↓ 渲染成图像            ← 图像内容 = 文本层内容，真值已知
    ↓ 可选退化（噪点/模糊/低对比/歪斜/低分辨率/印章）
"伪扫描件"
    ↓ OCR
识别结果
    ↓ 与文本层比对
字符准确率 / 数字召回 / 数字边界完整性
```

这样得到的是有真值的准确率数字，避免了"看起来还行"式的判断。

### 评测本身踩的两个坑（值得记录）

坑 1：表格读取顺序被误判为错误

文本层按「行」遍历表格（序号→药名→适应症→规格→价格），
而 OCR 按「列」（规格→药名→适应症→包装→价格→通用名）。
内容相同、顺序不同，但 Levenshtein 距离把每处错位都算成"删一个+插一个"，
于是一个实际只错了几处标点的页面，CER 被算成 8–23%。

修正：引入「字符多重集准确率」（对顺序不敏感）作为主指标，
并把顺序敏感指标作为对照。两者的差距本身就是诊断信息：

| 现象 | 含义 |
|---|---|
| 字符准确率高、序敏 CER 也高 | 内容读对了，只是顺序不同（表格页） |
| 字符准确率低 | 真的识别错误 |

坑 2：数字 token 多重集产生大量假漏识

文本层把 `1,300` 拆成 `1` 与 `300` 两个 token，而多重集在单字符层面比较时，
`300` 里的 `0` 会和页面上任意其他 `0` 混在一起。
实测一页报出「10 个数字漏识 5 个」，逐条核对后发现全是这种假象。

修正：改用「数字序列召回」—— 把真值与识别结果都压缩成纯数字串，
检查真值中的每个数字是否作为连续子串出现。既抗标点空格差异，
又不会把不同位置的数字混为一谈。

同时新增「数字边界完整性」指标：真值中相邻两个数字 token 在识别结果中
是否仍保持分离。粘连会让下游按 token 取值必然出错，这是真实风险。

### 实测结果

> 详细数据见 `docs/ocr_benchmark.json` 与本文件末尾的自动生成汇总。
> 完整报告由 `python tools/ocr_benchmark.py --all` 生成。

L1 无退化渲染（确定最优配置）

| DPI / 预处理 | 字符准确率 | 序敏 CER | 数字召回 | 数字边界 | 耗时/页 |
|---|---|---|---|---|---|
| 150 / 无 | 98.04% | 18.85% | 92.59% | 83.12% | 5.1s |
| 200 / 无 | 95.22% | 21.31% | 89.46% | 79.79% | 5.9s |
| 200 / 预处理 | 95.94% | 21.99% | 89.46% | 84.79% | 5.6s |
| 300 / 无 | 98.11% | 20.27% | 92.59% | 83.12% | 7.8s |
| 300 / 预处理 | 97.97% | 19.66% | 92.59% | 83.12% | 7.1s |
| 400 / 无 | 98.17% | 22.45% | 92.59% | 83.12% | 9.7s |

结论：

1. 字符识别准确率 95–98% —— RapidOCR 在金融公告上的基础能力是可靠的。
2. 数字召回 89–93% —— 有 7–11% 的数字未被正确识别，这是必须靠第三层兜底的部分。
3. 数字边界完整性只有 79–85% —— 相邻数字粘连是真实且普遍的问题。
4. 200dpi 是一个「坑」：各项指标均劣于 150dpi 与 300dpi。
   推测与检测阶段的图像缩放落在不利区间有关。
5. 预处理收益不稳定：仅在 200dpi 下对数字边界有明显改善（79.79% → 84.79%），
   在其他分辨率下无收益。不宜无脑开启。
6. 更高 DPI 边际收益递减：400dpi 相比 300dpi 仅提升 0.06 个百分点，但慢 24%。

### 对方案的直接影响

| 发现 | 应对 |

| 数字召回仅 ~92% | 第 2 层无法独立支撑金融数字提取，第三层 VLM 裁决是必需的 —— 印证了三层设计 |
| 数字边界 79–85% | 抽取时必须做数字边界校验：识别到连续数字时要与原文对照，可疑处转 VLM |

### L2 受控退化（模拟真实扫描件的劣化）

配置：300dpi、无预处理。每页施加一种退化后重新 OCR，与真值比对。

| 退化类型 | 模拟的真实问题 | 字符准确率 | 数字召回 | 数字边界 |
|---|---|---|---|---|
| clean（对照） | — | 97.96% | 90.30% | 90.32% |
| stamp（红色印章） | 财务章/公章遮挡 | 96.57% | 90.30% | 92.19% |
| noise | 复印噪点、灰尘 | 96.21% | 90.30% | 88.65% |
| blur | 扫描仪失焦、传真 | 97.53% | 88.74% | 90.53% |
| gray | 纸张泛黄、对比度不足 | 97.18% | 90.30% | 92.87% |
| lowres | 低分辨率扫描 | 97.59% | 88.74% | 90.53% |
| skew（+2°） | 进纸歪斜 | 97.36% | 88.74% | 90.53% |

结论：OCR 对真实劣化相当鲁棒。

- 最严重的退化（红色印章遮挡中部区域）只让字符准确率下降 1.4 个百分点
- 全部 7 种退化下字符准确率都保持在 96% 以上
- 歪斜 +2° 使序敏 CER 从 23% 升到 33%，但字符准确率几乎不变（97.36%）
  —— 说明歪斜主要影响阅读顺序，不影响字符识别；
  这提示纠偏对「结构化提取」比对「文本识别」更重要

### 还有三处潜伏缺陷（都在真实模型 + 真实材料下才暴露）

#### 潜伏缺陷 A：`offline` 悄悄换掉了 provider 最隐蔽

现象：真实模型跑出来的 run（27 次 VLM 调用）执行 `agent replay --strict`，
判定「不可复现」，且所有产物都不一致。

排查过程：
1. 先看 `trace.jsonl` → 回放的 `llm_calls` 为 0，但缓存文件有 27 行
2. 看到 error 事件：`离线模式下缓存未命中（role='vision', cache_entries=27）`
3. 缓存明明有 27 条却全部未命中 → 只能是缓存键变了
4. 缓存键 = `sha256(provider | model | params | messages | schema | prompt_sha)`
5. 查 `build_gateway` → 发现写成 `if use_mock or offline: provider = MockProvider()`

根因：`offline` 与 `use_mock` 被混为一谈。回放时 `offline=True`，
于是 provider 从 `deepseek` 变成了 `mock`，缓存键里的 provider 名一变，
27 条缓存全部失效 —— 回放实际是在用假模型重新跑一遍。

修复：
- `offline` 只禁止出网，不改变 provider 身份
- `manifest` 新增 `provider` 字段，回放据此选择同一个 provider

教训：`offline`（禁止网络）与 `mock`（换掉模型）
是两个正交的概念。把它们合并成一个条件判断，
会让「离线」这个语义产生未被预期的副作用。

#### 潜伏缺陷 B：回放不还原数据目录

现象：修好 A 之后，回放的 OCR/冲突结果仍与原始不同。

根因：`manifest` 没有记录数据目录。回放时 `build_context` 用默认的
`data/`，而原始运行用的是 `--data _realtest`。
输入不同，产物当然不同 —— 这是假警报，但足以让人误判系统不可复现。

修复：`manifest` 新增 `data_dir`（相对项目根目录），回放据此重建
完整的输入上下文。

#### 潜伏缺陷 C：产物里的耗时字段（前文已述）

这三处缺陷有共同特征：它们都不会报错，只会让「可复现」这个
机器校验失败，或让结论静默失真。而它们又都只在
真实模型 + 真实材料 + 完整回放这条最重的路径上才会暴露 ——
mock 模式、合成样本、单测都测不出来。

> **结论：端到端复现校验必须在真实配置下跑一遍。**
> 只做 mock 的 CI 会给出虚假的安全感。

修复后：真实模型运行（27 次 VLM 调用）执行 `agent replay --strict`
判定为可复现。

## 「可复现」的三层含义（本次验证最大的认知收获）

P0 验证过程中，「不可复现」这个警报出现了四次，但每一次的原因都不同：

| 层次 | 常见原因 | 本次实例 |
|---|---|---|
| 输入层 | 回放读的不是同一份输入 | 潜伏缺陷 B：`data_dir` 未记录 |
| 环境层 | 模型/provider/参数/prompt 版本不同 | 潜伏缺陷 A：`offline` 换掉了 provider |
| 产物层 | 产物里混入了运行过程属性（耗时、时间戳） | 潜伏缺陷 C：`elapsed_ms`；以及早先的 `utcnow()` |

只有三层同时对齐，`replay --strict` 才会判为可复现。

这解释了为什么「可复现」在工程上比看起来难得多 ——
仅仅加一个 `seed=0` 并不够，它要求
把一次运行的全部上下文（输入、环境、产物）都显式记录下来并可重建。

我们的 `manifest.json` 现在承担这个职责，字段包括：

```
input_files   输入文件哈希
data_dir      数据目录
provider      模型提供方
models        各角色的模型名
model_params  各角色的完整参数（含 temperature / thinking / max_tokens）
prompts       每个提示词的 id@version -> SHA256
skills        技能定义哈希
agent_config_hash  configs/ 全部配置的指纹
started_at    运行起始时间（产物中所有时间字段的唯一来源）
```

评审拿到 `runs/<id>/` 目录，用 `agent replay <id> --strict` 即可
在不联网、不调用任何模型的情况下逐字节验证这份记录。

## ⑥ 表格解析与单元格级 VLM 裁决

复杂表格是赛题点名的场景（「扫描件与复杂表格」），也是金融数字最密集的地方。
本节记录表格分支从结构重建 → 算术校验 → 单元格级视觉裁决的实测结果，
以及这条链路上修掉的三个缺陷 —— 它们的共同点是都不报错。

### 6.1 结构重建：连通分量取代全页凸包

早期实现取整页线段的凸包当表格区域。实测后果：一篇公告里的多个表格被合并成
一个 9×25 的网格，其中 15 列全空。改为连通分量后，两个互不相连的表格
被正确识别为两个。

随后又踩了一次：第一版连通判据要求"线段端点严格相接"，而很多 PDF 的框线是
逐段绘制的（端点差几个 pt），于是这类表格全部判不出来，整体退化成较弱的
坐标聚类 —— 比修复前更差。最终判据改为「近似共线 + 投影重叠」（容差 4pt）。

单元格取文本时也有一个隐蔽的坑：早期用 `" ".join()` 拼接同一格内的 span，
中文排版折行会在中间插入空格，「唐人神集团股份有限公司」变成
「唐人神集团股 份有限公司」，别名匹配立刻失效。现在按 CJK 不加空格、
数字前保留换行的规则拼接。

### 6.2 T1–T3 实测基线（55 张真实公告表格）

| 指标 | 实测值 | 说明 |
|---|---|---|
| T1 平均数值保真率 | 100.00% | 网格里的每个数字都能在页面文本中找到 |
| T1 伪造数字总数 | 0 | 网格里没有凭空多出的数字（幻觉的直接度量） |
| T2 碎格总数 | 422 | 格内仍残留换行 —— 文字被切开 |
| T2 空列总数 | 0 | 网格里没有混入不存在的列 |
| T2 合并格总数 | 33 | 相邻格被并成一格 |
| T2 结构可用比例 | 47.27% | 无碎格、无空行空列、无异常合并格 |
| T3 算术失败总数 | 0 | 见 6.3 —— 这个 0 是修出来的，不是天生的 |
| T3 真的校验过的比例 | 3.64% | 其余是无合计线、无从校验 |
| T3 含「合计」标签的表 | 2 / 55 | ← 这条决定了触发策略 |
| 平均耗时 | 0.01 s/表 | 纯确定性，无模型调用 |

### 6.3 关键发现：「算术优先」的触发策略在这批材料上失效

原方案打算用算术校验（合计行 = 分项和）作为单元格裁决的触发器：
算术不平本身就说明有格子读错，而且能定位到具体行列，比整表逐格调用便宜得多。
这个推理本身没错，但它依赖一个前提 —— 表里有合计行。

实测：55 张真实公告表格里只有 2 张带「合计」标签（3.6%）。
对外担保表、股权变动表这类"公司清单"根本没有合计概念。
也就是说，如果只靠算术触发，96% 的表格永远不会被视觉复核。

因此触发策略改为三档，并把主力放在几何特征排序上：

| 触发档 | 判据 | 预算 |
|---|---|---|
| `unbalanced` | 算术校验报出不平 | 6 格/表 |
| `balanced` | 算术校验通过（`checked > 0`） | 0 格/表（信任） |
| `no_total_line` | 无从校验（`checked == 0`） | 4 格/表 |

第三档是关键。这里有一个必须显式区分的语义陷阱：
`arith.ok` 对"没有合计线所以没查"的表也是 `True`。
若把两者混为一谈，就等于把"没查过"当成"查过且没问题"。
代码里因此同时保留 `ok` 与 `checked` 两个量，判据写成
`arith_ok and checked > 0` 才算"已校验"。

### 6.4 修复的缺陷（表格版）：三个都不报错

#### 缺陷 ①：算术校验既误报又漏报

旧实现把最后一行 / 最后一列无条件当作合计行，它有两副面孔：

* 假报：在 48 张真实公告表格上报出 40 处"算术不平"，逐条核对后
  全部是误报 —— 股权变动表的最后一行是另一家子公司，不是合计行。
  把误报写进审计报告，比不报更伤可信度。
* 漏报：若网格第一行是「项目 / 金额」这类文本表头，旧实现要求整列
  每个格都能解析成数字，于是 `checked_rows`/`checked_cols` 恒为 0，
  函数永远返回 OK —— 一张 `合计=999` 而分项和为 `300` 的表被判定为
  "算术自洽"。

修复：改为认标签。合计行看行标签（合计/小计/总计/Total），
合计列看表头；分项只取紧邻的连续数值段，这样「序号」列与文字列
不会混进求和（`1 | 项目 | 100 | 200 | 300` 只取 `100+200`）；
纵向/横向两个方向都试探，只要有一列纵向成立就按纵向判定，
只报不平的那几列。

另一个必须处理的现实：中文财报的分层结构（`一、营业收入 1000` /
`其中：A 600` / `B 400` / `合计 1000`）里，合计只覆盖部分分项。
这类"不平"是正常的。因此引入 `soft`（放过但留痕）——
放过是为了不误报，但"为什么放过"必须能查，否则等于把信息丢掉。

#### 缺陷 ②：裁决只比数字，碎格永远修不掉

单元格裁决原本用"数字串是否一致"判断模型读数与程序读数是否相符。
问题在于 `'583,96\n5.66'` 与 `'583,965.66'` 的数字串完全相同，
于是判定为 `agree`，那一格原样留下 —— 而下游 `_to_decimal` 因为换行
解析失败，这一格的值直接丢失。T2 实测有 422 个这样的碎格。

修复：新增 `normalized` 结论。数字一位不差、但原读法解析不出数值
而模型读法可以时，采用模型读法。这是格式归一化，不是改值 ——
不存在改错数字的风险，收益却是"这一格从取不到数变成取得到"。

判定逻辑同时从"调用模型"的代码里拆成纯函数 `decide_cell_verdict`，
使这张安全攸关的判定表可以被穷举测试，而不必靠真花钱的端到端运行验证。

#### 缺陷 ③：`except Exception` 把代码 bug 一起吞了 最隐蔽

现象：一次完整的真实运行，`judge` 阶段状态 = success，
但产物 `table_adjudications.json` = `[]`，报告里没有任何异常迹象。

排查：翻 `trace.jsonl` 才看到 10 条 error 事件：

```
vlm.adjudicate_table: NameError: name 'max_cells' is not defined
```

裁决循环里写了一个未定义变量（应为 `max_calls`），10 张表全部抛异常，
而 `except Exception: continue` 把它们全咽了下去。统计量
`tables_adjudicated` 还在自增 —— 因为计数写在 `try` 之前。

修复：

* 改正变量名；
* 区分 `tables_attempted` / `tables_adjudicated` / `table_adjudication_errors`，
  计数写在 `try` 之后；
* 阶段事件在有失败时置为 `warn`，并在控制台显式打印失败张数。

教训：`except Exception` 是健壮性的来源，也是可见性的黑洞。
凡是吞异常的地方，都必须配一个会被看到的计数器。

### 6.5 新增防线：静态体检（不必等运行期）

缺陷 ③ 是"运行期测试抓不到"的类型 —— 除非恰好跑到那条分支并断言产物非空。
因此新增 `tests/test_static_health.py`，用标准库 `symtable` 做未定义名体检：

* 遍历 `agent/ domain/ pipelines/ web/ tools/ tests/` 全部源码，
  检查每个作用域里"被引用、但既不是局部/自由变量，也不是模块级/内置"的名字；
* 实测立刻在这次改动中抓到 `decide_cell_verdict` 里的 `cell_number`
  未定义（函数内延迟导入导致）—— 在写测试的当下就抓到了；
* 另有一条测试断言 `except Exception` 之后必须紧跟失败计数，
  防止缺陷 ③ 复发。

### 6.6 安全闸门：什么情况下才允许覆盖原读数

#### 6.6.1 三道「模型自述」闸门 —— 实测不够

| 闸门 | 要求 |
|---|---|
| quote 回读 | 模型给出的原文引用必须能在整页文本中回读成功（精确或模糊 ≥0.86） |
| 位置确认 | 模型必须确认红框位置与所读格一致（`position_confirmed is not False`） |
| 置信度 | 模型自评 ≥ 0.7 |
| 非空 | 模型读数非空 |

任一条不满足 → 只标记、不改值。这套闸门看起来很稳妥，
直到一次真实运行把它的三个漏洞一次暴露出来。

#### 6.6.2 一次真实事故：80 次「改值」里 75 次是错的

跑完 48 张真实表格的单元格裁决后，统计显示：

```
复核单元格 184 个
  一致        57
  格式归一     35
  改值        80   ← 占复核量的 43%，可疑
  未采纳      12
```

程序读数的数值保真率是 100%（每个网格数字都能在页面里找到），
一个 100% 保真的读数源不该需要 43% 的"纠正"。于是逐条抽查。

抽查方法：不信任裁决结论，直接用几何做独立裁判 ——
把 PDF 里落在该单元格 bbox 内的文字取出来，看程序读数与模型读数
哪一个真的在那个格子里（`tools/adjudication_truth_audit.py`）。

结果：

```
被改写的单元格 115 个
  改错了                 75   ← 模型读数根本不在那个格子里，程序读数在
  无法区分（都在格内）      38   ← 格式归一属于此类，天然安全
  无数字可比               2
```

典型样例：

| 页 | 位置 | 程序读数 | 模型读数 | 格子里实际印着 |
|---|---|---|---|---|
| p2 | r1c2 | `501,000.00` | `179,000.00` | `501,000.00` |
| p17 | r3c3 | `50,202,000 阿联酋迪拉姆` | `1752,500,000` | `50,202,000 阿联酋迪拉姆` |
| p17 | r4c3 | `1752,500,000 美元` | `50,202,000` | `1752,500,000 美元` |

注意 p17 那两行：两个格子的读数正好互换了 —— 这是"裁图取错位置"的
指纹，与"模型看错数字"无关。

三道闸门为什么全部放行：

* quote 回读只校验"这段文字在整页某处存在"。模型读错格子时，
  它引用的仍然是这一页上真实存在的文字，回读当然成功。
  实测样例里模型的 quote 是 `JinkoSolar (U.S.) Inc.\t179,000.00` ——
  那是同一页第 22 行的内容，而它被用来"纠正"第 1 行。
* 位置确认用的是同一张错图渲染出的红框。图与框自洽，模型回答"位置正确"。
* 置信度自评恒为 `0.95`，184 个格子没有第二个取值 —— 毫无区分度。

> **结论：只靠模型自述的闸门等于没有闸门。**
> 校验必须引入模型无法影响的事实。

#### 6.6.3 根因：bbox → 像素的 y 翻转搞反了 代价最大的一个坑

裁图函数按「PDF 用户空间原点在左下」写成了
`pixel_y = (page_height - bbox_y) * scale`。
但 PyMuPDF 的 `page.rect` 与 `get_text()` 用的是同一套坐标：原点左上、y 向下。
于是每一次裁图都沿页面中线上下镜像：

* 第 1 行的格子裁出来是第 22 行的内容
* 模型读出的就是它看到的内容 → 与程序读数"不一致"
* 高置信度 + 图文自洽的位置确认 → 一路放行，覆盖掉正确的值

定位方式（不靠猜）：

1. 用 PyMuPDF 的 `search_for("501,000.00")` 拿到该数在页面上的权威位置
2. 发现它与单元格 bbox 完全一致 → bbox 没错
3. 把「直接 clip 渲染」与「从整页图按算出的像素框裁」两张图并排看：
   前者是 `501,000.00`，后者是 `179,000.00` → 问题在像素换算
4. 在整页图上按文本层坐标取横带，像素 y 越大内容越靠上 → 确认 y 轴方向搞反

修复：`cell_pixel_box()` 去掉翻转，并抽出这个函数专门加测试。

为什么它极难发现：镜像后的坐标依然是合法坐标 ——
图裁得出来、尺寸对得上、不抛异常、不报错。唯一的判据是
"裁出来的像素是不是那个格子"，因此回归测试也只能用内容比对：
拿 `get_pixmap(clip=...)`（与 `search_for` 同源）作为真值，
比较裁图与它的像素差（`test_crop_cell_matches_pdf_clip_render`）。
该测试在旧实现下必然失败，已实测确认。

#### 6.6.4 第四道闸门：几何佐证（不可配置）

新增 `corroborate_by_geometry(geometry_text, original, candidate)`：
取该单元格 bbox 内页面上真实印着的字，判定

| 情况 | 结论 | 处置 |
|---|---|---|
| 模型读数在格内、程序读数不在 | `corroborated` | 允许覆盖 |
| 程序读数在格内、模型读数不在 | `contradicted` | 拒绝覆盖（事故情形） |
| 两者都在 / 都不在 | `unknown` | 拒绝覆盖 |
| 没有文本层（扫描件） | `unknown` | 失败关闭，不覆盖 |

这道闸门不提供配置开关：能被关掉的安全闸门等于没有。
配置里只保留三条自述闸门，并注明它们单独使用是不够的。

离线重放这次事故的全部裁决（`tools/adjudication_truth_audit.py`，
不花一次模型调用）：

```
corrected → rejected     80   ← 全部拦下
agree     → agree        57
normalized→ normalized   35   ← 安全的格式归一，保留
rejected  → rejected      5
rejected  → agree         4
rejected  → unreadable    3
```

`normalized` 这一档不需要几何佐证：数字一位不差，采用模型读法
不存在改错数字的风险，收益却是"这一格从取不到数变成取得到"。

### 6.7 修复后的实测结果（48 张真实公告表格）

两次运行用的是同一批材料、同一套提示词、同一个模型，
差别只在裁图坐标与闸门：

| 指标 | 修复前 `table-vlm4` | 修复后 `table-vlm5` |
|---|---|---|
| 进入 / 成功裁决 | 48 张 / 48 张 | 48 张 / 48 张 |
| 复核单元格 | 184 | 184 |
| 一致（模型与程序读数相同） | 57 | 96 |
| 格式归一（数字未变） | 35 | 80 |
| 改值 | 80 | 0 |
| 未采纳（只标记不改） | 12 | 8 |
| 独立复核判定「改错了」 | 75 | 0 |
| 其中"归一前解析不出数值" | — | 80（全部恢复可用） |
| 运行成本 | ¥0.9010 | ¥0.9590 |

三个数字值得解释：

* 改值从 80 变成 0 是正确结果，不是功能退化。这批材料的文本层
  数值保真率本来就是 100% —— 一个 100% 保真的读数源不需要被"纠正"
  80 次。修复前那 80 次里 75 次已被独立复核证伪。
* 格式归一从 35 涨到 80：裁图取对之后，更多"数字一位不差、但被换行
  切断而解析不出数值"的格子被正确识别出来。这 80 个格子全部在归一前
  `cell_number() is None`（取不到数），归一后可解析 —— 这是实打实的
  提取收益，且不存在改错数字的风险。
* 未采纳 8 个保留为人工复核线索（模型与程序读数不一致，但缺少
  独立佐证）。它们既没被覆盖，也没被丢弃。

独立复核的方式（`tools/adjudication_truth_audit.py`）不看裁决结论，
只回 PDF 几何判断"模型读数在不在那个格子里"：

```
修复前：改错了 75 / 无法区分 38 / 无数字可比 2
修复后：无法区分 80（全部是数字一致的格式归一）/ 改错 0
```

### 6.8 这一节的教训

三个缺陷（算术误报、碎格漏修、`except Exception` 吞错），
加上这一次的镜像裁图，有一个共同点：

> 它们都不报错。阶段状态是 success，产物结构合法，数字看起来正常。

而在"数字看起来正常"这一层之下，正确与错误只差一次坐标换算。
因此本项目在这条链路上采取的立场是：

1. 凡是要用模型读数覆盖程序读数，必须有模型无法影响的事实来佐证
2. 凡是被吞掉的异常，必须配一个会被看到的计数器
3. 凡是"改了数据"的操作，都要留下改前值、改后值与结论
   （`channels/table_adjudications.json` 逐格记录，Web 上可逐条核对）
4. 凡是"没查过"，都不能说成"查过且没问题"（`ok` 与 `checked` 分开）

### 6.9 复现方式

```bash
# T1–T3 基线（无需 API Key）
python tools/table_benchmark.py --baseline --limit 60

# 算术校验「修复前 vs 修复后」逐表审计 + 裁决汇总（无需 API Key）
python tools/table_arith_audit.py --run table-vlm5 --dump 2

# 单元格裁决的**独立复核**：几何裁判，判定每一次改写是对是错（无需 API Key）
python tools/adjudication_truth_audit.py table-vlm5

# 裁图坐标诊断：模型"读到的不是这一格"时用它定位到具体是哪一层出错
python tools/crop_coord_diag.py --run table-vlm5 --page 2

# Web 演示台渲染核验（含单元格裁图是否真的取得到）
python -m web.app --port 8099 --runs-root runs --run table-vlm5
python tools/web_smoke.py http://127.0.0.1:8099

# 端到端（含单元格级 VLM 裁决，需要 API Key）
python -m agent.cli run r1_extract --data agent/sample --run-id tbl-demo --limit 3
```

`tools/table_arith_audit.py` 的做法值得一说：`channels/tables.json` 里
既存了每张表的网格，也存了当时的算术校验结论，因此可以对着同一批真实表格，
把旧实现的结论与新实现现场重算的结论摆在一起比对 ——
这是判定"这次修改到底是修好了还是改坏了"的硬证据，不靠感觉。

`tools/adjudication_truth_audit.py` 更进一步：它连裁决结论都不信，
直接回到 PDF 几何去判"模型读数到底在不在那个格子里"。
**能证伪自己的验证工具，才是真的验证工具。**

## ⑦ 处理「已知限制」：一次以测量为准的返工

这一节记录限制逐条被证伪或修好的过程。它的价值不在于结论，
而在于每个结论都是先量后改 —— 而两次量出来的结果直接推翻了原本的判断。

### 7.1 限制①的原始判断是错的

原判断：「表格修正结果未回灌事实库 → 被归一化的碎格不会改善同页事实抽取」。

于是先量化"碎格到底害了多少事实"：拿一次真实运行里 80 个已归一化的碎格，
去找事实库里有没有对应值。结果三条都是 0：那些页面产出的事实 0 条、
完整值命中 0 条、截断值命中 0 条。

但对照实验暴露了更根本的问题：

```
来源层: L3_vlm 161 条, L1_text_layer 61 条
```

73% 的事实来自 VLM 整页扫描 —— 而它读的正是已经用几何方法重建好的表格。
同一批数字明明有确定性来源，却在花模型调用去"看"，
而且肉眼在多列多行的表里做归属，天生比按行列取值更容易错配。

> 这条限制的准确表述是"该走确定性路径的数据走了模型路径"，与"修正没回灌"无关。

### 7.2 折行修复：以为能提分 → 量出来是 0 → 换个位置就有效

顺着上一条，先做一个看起来必然有效的修复：把被排版折行切断的数字接回去
（`15,234,63` + `8.42`）。

* 在 3 份材料上：修复 295 处，事实候选 104 → 104（+0）
* 在全语料随机 30 份 × 6 页上：修复 0 处，候选 14 → 14（+0）

两次都白干。但"这个修复没用"是错的 —— 换两个位置之后它产生了实质收益：

| 作用位置 | 效果 |
|---|---|
| 表格单元格文本 | 181 个碎格中 80 个（44%） 被零成本修好 |
| 页面文本的单位接续（`717,247.24 万` + `元`） | 文本规则抽取 115 → 171 条（+49%） |

单位接续那一条尤其关键：晶科材料的财务数据挤在一个单元格里
（`资产总额：…；营业收入：717,247.24 万\n元；…`），单位被折成两行，
正则跨不过去 —— 这正是那 28 页"一条事实都抽不出来"的原因。

> 教训：修复写在哪里，和修复本身对不对，是两件事。
> 同一条规则放在错误的位置上，量出来就是零收益。

### 7.3 表格网格抽取：把确定性路径扶正

新增 `pipelines/r1_extract/table_facts.py`，把表格网格当一等抽取来源：

    行主体（公司名） × 列指标（表头里的指标名） × 单元格数值

四条硬约束：单位必须明确、量纲族必须相符、主体必须来自行标签、
quote 必须回读成功（锚点落在单元格 bbox，比整页 quote 更精确）。

实现过程中被实测数据纠正了三次：

| 症状 | 根因 | 修法 |
|---|---|---|
| 只抽出 11 条 | 表头只取前两行，而指标行在第 3 行（上面还有分组行、数据声明行） | 改为在前 4 行里找命中指标别名最多的那一行 |
| 一张 7 行的表被算成"4 行表头" | 数据格里写着 `资产总额：312,460.60万元；…`，被当成了表头 | 表头单元格必须是标签式的（短、含量词冒号即判为数据） |
| 28 页的表只有第 1 页出事实 | 长表跨页时只在首页印表头 | 续表继承上一页的列映射（列数相同才继承） |

最终：389 条表内事实，全部为 L1 文本层、置信度 0.95、带单元格级锚点。

### 7.4 由"改得更多"引入的新风险：跨主体误归属

抽取量上来之后立刻暴露了一个此前看不见的问题：

```
rule_engine 事实 171 条
   原文不在任何单元格里   74
   该页没有表格索引       52
   主体本来就一致         45
```

文本层规则抽取把整页事实都挂在文档主体名下。这对正文叙述是对的，
但表格里常常一行一个其他主体。于是一份材料里 159 条子公司的财务数据
被记成了母公司（披露主体）的 —— 而且不报错，只会让"某某公司营业收入"
这个结论静默失真。

修法（`pipelines/r1_extract/entity_attribution.py`）：事实原文若落在某张表的
某个单元格里，就把主体改成该行的行主体；定位不到 / 判不出 → 保持原样。
每次改动都落盘 `facts/entity_reattribution.json`（改前、改后、依据的行列）。

顺带修掉一个更危险的误报：E5 的同比重算原本按"取两个不同期间的事实"配对，
完全不看主体。跨主体配对会拿 A 公司 2025 年与 B 公司 2024 年算出一个
根本不存在的增速，并作为「错误」报给用户。现在：只在同一主体内配对；
多个主体各自都有两期数据而草稿又没点名 → 跳过重算并记录说明。

这一条是被测试逼出来的：第一版按"期间数最多的主体"选，
测试立刻发现它选中了子公司，没选中母公司 —— 说明任何"挑一个主体"的做法都是猜。

### 7.5 处理后的实测对照

同一批材料（3 份、48 张表、47 个表格页）：

| 指标 | 改动前 | 改动后 |
|---|---|---|
| 事实总数 | 233 | 781 |
| 其中 L3_VLM（模型读数） | 161（73%） | 162（21%） |
| 其中确定性路径 | 72 | 619 |
| 表内事实（单元格级锚点） | 0 | 389 |
| 主体误归属 | 159 条 | 0 |
| VLM 读数被独立复现的比例 | 6% | 86% |
| 多期数据（可做同比重算） | 0 个指标 | 4 个指标 |

VLM 的那 162 条并没有被删除 —— 它们现在的作用变成了交叉验证：
确定性路径复现了其中 86%，剩下的 14% 已逐条定位到原因（见 §7.6.5），
属于主体归属漏挂而非数值分歧。

> 确定性优先指的是"让模型去做只有它才能做的事"，与"不用模型"是两回事。

### 7.6 双路互证：把"模型读到的东西"变成可核对的证据

前几节修的是抽取。这一节修的是验证 —— 而验证工具自己也犯了两次错。

#### 7.6.1 验证工具犯的两次错

(a) 过滤条件写错，报告"模型路径没有任何事实"

`cross_run_agreement.py` 里写成 `MODEL = ("vlm",)`，而真实的抽取器名是
`vlm_scan`。工具于是报告"这批材料没触发 VLM" —— 实际是过滤条件不匹配。
一个验证工具给出假结论，比没有工具更危险。

(b) 按目录名排序挑 run，验的是旧产物

`web_smoke.py` 用 `sorted(iterdir(), reverse=True)` 挑最新 run，
于是挑到 `table-vlm5`，漏掉了更新的 `table-grid7`（字母序 `v` > `g`），
报出「`table_grid` 未通过」的假失败。已改为按 manifest 的 `started_at` 排序。

#### 7.6.2 一个由"保留空格"引出的连锁修复

为了让主体名与 VLM 读出的一致，把单元格文本归一从 `replace(" ", "")`
改成分中英处理（中文折行直接相连、拉丁词之间补空格）。改完立刻掉了一大截：

```
表格网格事实  389 → 251（"值不合规"被拒的格子 49 → 187）
```

根因：折行落在小数点附近的格子，原先靠"把换行删掉"意外修好，
保留空格后暴露出来。三种形态都要处理：

| 形态 | 例子 | 处理 |
|---|---|---|
| 折行在小数点之后 | `5,787,118.`⏎`61` | 行尾允许以小数点结尾 |
| 折行在小数点之前 | `42,399,138`⏎`.44` | 下一行允许以小数点开头 |
| 小数位被截断 | `-860,467.9`⏎`8` | 两片段都是"规范数字"也要接（小数没写完） |

同时必须挡住误接：`Note 5.`⏎`2024` 不能变成 `5.2024`
（只在句点前确实是格式化数字时才接）。修完 389 → 389，
但这次靠的是正确的规则，不靠删空格。

#### 7.6.3 又一处"静默丢数据"：每页每指标只取 4 条

剩下的"仅模型读到"里，有几个值页面上明明有、别名也在旁边却没被抽出来。
追下去发现两个写死的上限：`max_hits=12` 与 `for hit in occ[:4]` ——
只用前 4 个。一页里有 3 家公司 × 2 个期间时同一指标有 6 个取值，
第 5、6 个被静默丢掉。上限改为配置项
`extract.max_facts_per_metric_page`（默认 16），`max_hits` 提到 32。

再往后还有一条规则过严：

```
营业收入：385,643.08 万元；净利润：
80,082.13 万元。
```

冒号后正好折行，别名与数值分处两行，被"跨行即拒"的边界规则挡掉。
现在改为：把空白与标签分隔符都去掉之后若什么都不剩，就允许跨行
（`净利润：`⏎`80,082.13` 放过；`项目`⏎`金额 100` 仍然拒）。

两处修完：确定性路径 560 → 619 条，双路互证 73% → 86%。

#### 7.6.4 主体名归一：只差空白的同一家公司必须合并

```
表格路径产出   JinkoSolar(U.S.)Inc.
VLM 读出       JinkoSolar (U.S.) Inc.
```

同一家公司在事实库里成了两个主体，三个后果都不报错：
虚增主体数（干扰 R4 选估值主体）、拆散 R5 同比分组、双路互证少算匹配。
现在按"去掉空白后同名"归并，规范写法优先取 VLM 那种（来自渲染图像，最接近真实排版）。

#### 7.6.5 残留

* 仅模型读到的 23 个值中，多数是主体归属没挂上：规则路径抽到了值，
  但主体仍是文档主体 —— 主体归属纠正只在"事实原文能落到某个单元格、
  且该行主体可判"时才生效。这类行定位失败的原因尚未逐条归类。
* 折行把单词从中间切断的主体名合并不了：`INTERNATI`+`ONA` →
  `INTERNATI ONA`，去掉空格是 `INTERNATIONA` ≠ `INTERNATIONAL`。
  靠删空格合并不了，硬做需要词形判断。已有测试锁住现状，
  避免以后误以为已经处理。

### 7.7 端到端复验：全流程 + 复现性

抽取链路改完之后，必须回答"下游还好吗"。跑一次完整流水线
（R1 → R4 → R5，同一批 3 份真实材料）：

```
11/11 阶段成功；勾稽断言 26 条（11 pass / 15 skipped，无 FAIL）
估值对象 118034    每股价值 ¥7.8648
R5 发现 1 条：E4 引用核查（报告值 2,557 万股在材料中无来源）
agent replay --strict → ✅ 可复现（全部产物逐字节一致）
```

15 条 skipped 不是失败 —— 它们是 A2/A3/A5 这类需要成本费用明细、
现金流明细、分红数据的勾稽关系，而这几份公告里没有这些表。
`SKIPPED ≠ FAIL` 的语义区分在这里正好派上用场（见 `docs/DESIGN_NOTES.md` §3.4）。

#### 7.7.1 由"改得更多"引入的高危风险：估值主体可能被换成子公司

这是本轮最值得记录的一处。表格抽取让一份材料里出现了 103 个主体
（一行一家子公司/被担保人），而 R4 选估值对象的判据是"事实条数最多"：

```
 118034（披露主体）                20 条
 JinkoSolar Middle East DMCC       20 条   ← 打平
 青海晶科能源有限公司                18 条
```

Python 的 `max` 在打平时返回先遇到的那个，顺序取决于事实入库顺序 ——
也就是说，再加一条子公司事实就可能把估值对象换成一家子公司，
而且不会有任何报错。这与当年"三家公司的数据混算出每股 0.028 元"
是同一类失败（静默失真），只是触发方式更隐蔽。

判据升级（三层，逐层收紧）：

1. 主体专属指标优先：持有总股本 / 每股收益 / 归母净利润的主体就是披露主体
   —— 子公司表里不会出现这些指标
2. 其次是证券代码形态（中文公告的披露主体通常是 6 位代码）
3. 最后才比事实条数，且打平也要有确定性次序（代码优先 → 名称短优先 → 字典序）

修完之后的实测（含反事实检验）：

```
选中估值主体：118034
排除 102 个主体（trace 里只列前 8 个，避免淹没重点）
歧义告警：无
给某个子公司**多加一条事实**后，仍选 118034  ✓
```

另加 `entity_selection_note()`：若两个主体在同一档打平且都不像代码，
就写一条"主体选择存在并列"的告警 —— 不假装确定。

### 7.9 扫描件的几何佐证：机制接上了，但真正的拦路虎在别处

#### 7.9.1 先把事实摆清楚

"扫描件表格无法几何佐证"这条限制，追下去发现前提不成立。实测：

```
语料 1533 页：A_text_only 1020 / D_table 263 / E_mixed 144 / B_scanned 106
106 个扫描页（来自 14 份文件）的表框线段密度 **全部为 0**
逐页打开看：是声明页、审计意见页、封面 —— **全是纯文字扫描，没有表格**
```

而且扫描页并不是"什么都抽不到"：

```
股权变动_h3_600768.pdf（11 页全扫描）
  OCR    11 页，rapidocr，平均置信度 0.86
  表格   0 张            ← 表格靠**矢量线段**重建，图片里没有线段
  事实   12 条（L2_OCR 1 条 + L3_VLM 11 条）
```

所以真实情况是：扫描页有事实、没表格。难点的落点不在"几何佐证"，
而在扫描件上的表格检测（要从像素里找出行列结构）——
那是另一个量级的工程，而且在这份语料里没有可验证的样本。

#### 7.9.2 该做的还是做了：OCR 行框接管几何裁判

限制里描述的那一步确实有价值 —— 当未来材料出现扫描表格时，
单元格裁决不能因为"没有文本层"就永远失败关闭。因此：

* `domain/tools/ocr.py::ocr_lines_to_words()`：把 OCR 产物的行框换算成
  页面点坐标的"单词"表，与 PyMuPDF 的 `get_text("words")` 同构
* `judge.py`：文本层 words 为空时自动改用 OCR 行框，并在 trace 里声明
  「几何佐证改用 OCR 行框（该页无文本层）」

换算方向必须记牢：`pt = px * 72 / dpi`，与 `cell_pixel_box` 互逆。
搞反了会得到"看起来合理但完全对不上"的几何，而且不报错 —— 因此单测直接钉死。

#### 7.9.3 顺带炸出的一个结构性事故（378 个测试全绿时发生的）

往 `OcrResult` 后面插新函数时，插入点落在了类的中间：
`text` / `mean_confidence` / `low_confidence_ratio` / `to_dict` 四段
被挤进了新函数的函数体（`@property` 在函数体内是合法的嵌套定义，
只是永远不会被调用）。于是 `OcrResult` 静默失去这些属性，
直到跑真实扫描件才炸：

```
❌ extract_ocr 未预期异常：AttributeError: 'OcrResult' object has no attribute 'text'
```

当时 378 个测试全绿 —— 因为没有测试直接用 `OcrResult`。
补了两道防线：

1. `test_no_nested_property_in_module_functions`：AST 扫模块顶层函数，
   凡函数体里出现 `@property def x(self)` 即判为"类体被切开"
2. `test_ocr_result_public_api_is_intact`：行为级底线

并用 `tools/verify_split_class_check.py` 验证了这道检查真的会失败
（注入事故 → 抓到；恢复 → 通过），排除了"一条永远为真的断言"。

### 7.10 双路互证加权：把"互相印证"变成置信度

置信度模型里原本只有一项"多路独立同值 +0.05"，而它比的是文本层与 OCR ——
这两路在多数页面上是同源的（同一份 PDF 的文本层与它的渲染图）。
彼此独立的是：

* 确定性路径：表格网格按行列取值 / 规则引擎按别名定位
* 模型路径：VLM 看图读数

两者用完全不同的机制得到同一个数。实测一次运行里 162 条模型读数有 139 条
（86%）被确定性路径独立复现，于是：

```
139 组（主体, 指标, 数值）被双路独立复现
→ 278 条事实追加「双路互证」+0.05（确定性与模型各 139 条）
   确定性侧 0.95 → 0.99（封顶）
   模型侧   0.80 → 0.85
```

三条设计约束：

1. 口径是三元组（主体, 指标, 数值），不按 (主体,指标) 打包 ——
   同一指标天然有多个取值，打包比会得出"要么全对要么全错"的假结论
2. 明细可复算：加分项写进 `confidence_breakdown.adjustments`，
   报告与 Web 上都能逐项看到"为什么加了这 0.05"，不做黑盒加分
3. 幂等：重复调用不会反复加分（否则"跑两次分更高"）

### 7.12 一次由"改得更好"引出的连锁事故：父公司名下的子公司数据

加权做完后跑全流程复核，发现每股价值在两次运行间从 ¥7.86 跳到 ¥1.21。
一路查下去，牵出五个各自独立、但叠在一起就静默失真的缺陷。

#### 7.12.1 第一环：估值输入其实是模板默认值

`_fact_value` 会跳过 needs_review 的事实。当某个指标一条可用事实都没有时，
`assumptions.py` 用显式标注的模板默认值兜底：

```python
revenue = Decimal("10000000000")   # 100 亿，仅用于让流程可跑通
```

于是 ¥7.86 这个"看起来很正常"的每股价值，其实建立在 100 亿收入、
10 亿股本的模板值上。报告末尾确实有「数据缺口声明」，但结论本身不带这个标记。

修法：核心输入有缺口时，估值结论必须自己说出来 ——
现在报告第一节上方就有横幅：

> **本结论仅为方法论演示，不构成对该公司的估值判断。**
> 以下核心输入未从提交材料中提取到……披露主体自身的财务数据、营业收入、总股本、归母净资产、归母净利润

并把 `illustrative_only: true` / `core_gaps` 写进 `valuation/assumptions.json`。

#### 7.12.2 第二环：为什么"一条可用事实都没有"

因为同主体指标冲突守卫把主体 118034 名下的营业收入事实全部标记了：
10 条收入互不相同（2.3 万 ~ 96 亿），比值最高 13.4×。

守卫本身没错 —— 错的是那 10 条事实根本不属于这个主体：
它们来自晶科公告里逐行列示子公司财务数据的附件表。

#### 7.12.3 第三环：主体归属纠正漏了 VLM 事实

重归属只处理 `rule_engine` 事实。但 VLM 事实的主体来自模型的 `entity_hint`，
而模型在密集的子公司表里同样会把子公司的数挂到母公司名下 ——
实测父公司名下 4 条营业收入全部来自 VLM。

更隐蔽的是执行顺序：重归属原本写在 `_ingest_table_grid` 里，
而表格网格抽取是阶段 5.15、VLM 补录是阶段 5.2 之后 ——
也就是说这一步跑在 VLM 事实入库之前，VLM 事实根本轮不到被纠正。
修法：重归属独立成 `_reattribute_entities`，挪到两条路径都跑完之后。
效果：父公司名下这类事实 8 → 0 条。

#### 7.12.4 第四环：跨页续行、数值当主体、表头行混入

把重归属扩到 VLM 事实后，匹配率仍上不去。逐层剥开是四个独立的判定缺陷：

| 缺陷 | 现象 | 修法 |
|---|---|---|
| 跨页续行 | 宽列（经营范围/财务数据）把一行撑高，财务列折到下一页，形成"只有财务列、没有公司名"的行；它们被挂到文档主体名下 | 标签区无文字标签、数据区有内容 → 继承上一行的主体 |
| 数值当主体 | `6,000.00元`、`100%`、`434,749.30万元` 含汉字/百分号，骗过 `_NUMERIC_CELL`；某个数值列靠"取值分散度高"当选主体列 | 新增 `looks_like_value()`，主体列与行主体都排除数值格 |
| 表头行混入 | 表头行有 10 个格子，而过滤条件写了"单元格数 ≤ 6"→ 漏判；"主体"变成字符串「公司名称」 | 去掉数量上限，改判"短标签 ≥3 个且占比过半" |
| 序号列污染 | 序号列（`26`）被 `looks_like_value` 判为数值 → 数据区起点算成第 0 列 → 续行判定失效 | 数据区起点改用"指标列，否则主体列 +1" |

外加一条兜底匹配：事实原文是"数值+单位"，单元格里写法可能不同
（空格、相邻格拆分），因此文本匹配不上时用纯数字串再找一次 ——
但必须配唯一性闸门：若多个不同主体的格子都含这个数字，
说明它区分不出主体，宁可不改（改错主体比不改严重得多）。

#### 7.12.5 第五环：修好之后，主体自己一条事实都不剩

重归属修好之后，118034 名下一条事实都没有了 —— 因为那份公告披露的
本来就是子公司的财务数据（对外担保公告的附件），
主体自身的财务数据根本不在材料里。

此时"选事实最多的主体"会退而选中事实库里另一个代码（300339，只有 1 条），
等于给一家毫不相干的公司估值，而且不报错。

修法：`subject_facts_note()` —— 主体自身事实少于 3 条时明确说明
「这份材料很可能只披露了子公司/被担保人的数据，不含披露主体自身的财务数据」，
并把这一条作为最重的核心缺口写进结论横幅与缺口声明。

## 对方案原始设计的验证结论

P0 验证不仅校准了参数，也确认或修正了方案的几个核心判断：

| 原始判断 | 验证结果 |
|---|---|
| 「需要三层解析引擎」 | 确认，且被强化。真实材料中扫描件占 6.9%（特定类型 15.7%）；OCR 数字召回仅 ~92%，单靠第 2 层无法支撑金融数字提取 |
| 「VLM 裁判必须强制 quote 回读防幻觉」 | 确认，机制在真实数据上生效。27 次裁决中 21 次被闸门拦下，通过的 6 条全部 quote 精确匹配 |
| 「cost 是三层架构的主要顾虑」 | 修正。实测 ¥0.005/页，30 页全流程 ¥0.14。成本不构成约束，应优先保证准确性 |
| 「200dpi 是合理默认」 | 修正。200dpi 是各档中最差的，改为 300dpi |
| 「预处理能提升 OCR 质量」 | 修正。收益不稳定，改为默认关闭、按需触发 |
| 「temperature=0 保证可复现」 | 修正。思考模式下 temperature 不生效；必须同时关闭思考才能保证可复现 |
| 「懒加载 VLM 裁决以控制成本」 | 可放宽。成本不是约束，触发条件可以更激进（已加入数字边界触发） |

最后一条尤其值得强调：原方案为控制成本设计了保守的 VLM 触发策略，
但实测表明成本比预期低一到两个数量级。因此实际策略应当反过来 ——
宁可多调用 VLM 换取准确性，因为准确性是评分项而成本不是。
