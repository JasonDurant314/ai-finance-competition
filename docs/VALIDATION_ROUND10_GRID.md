## 二、继续攻列结构：修掉三个缺陷

第九轮的结论是"卡在列结构不兼容"，需要按 bbox 重建网格。本轮没有做那个大改造，
而是先把三个有界的缺陷修掉 —— 每一个都是独立成立的错误。

### 缺陷 1：`data_start_row` 把标题行当成数据行

（第九轮已定位，本轮修完并补测试）

```
r0  截至或截止各年度 | 12 | 月 | 31 | 日        ← 标题（"12""31" 是日期碎片）
r1  项 | 目 | 2025 | 年 | 2024 | 年 | ...        ← 真表头
r2  营业收入 | 2,864,469 | ...
```

判据收紧到 `_is_data_number`：年份与日期碎片（≤31 的 1–2 位数）都不算数据。

### 缺陷 2：`build_header` 把不同列结构的表头行强行拼接

表头 9 格、数据 5 格 → 逐列配对拼出 `'截至或截止各年度项'`、`'12目'`、`'月2025'`。

修复：只拼接列数与数据行一致的表头行。实测效果：

```
修复前 header = ['截至或截止各年度项', '12目', '月2025', '31年', ...]
修复后 header = ['项', '目', '2025', '年', '2024', '年', '2023年', '2022年', '2021年']
```

### 缺陷 3：`looks_like_statement_table` 要求首格含「项目」两字

601857 的表头被拆成 `项 | 目 | ...`，首格只有 `项` 一个字、`目` 落在第 2 格。
旧判据判定"不是报表" → 走列导向 → `metric_columns=0` → 整表 0 条候选。

修复：改用 `_is_label_row` 的判据（首格是短汉字标签即可，允许拆字）。

### 三个修复的合计效果

p7「主要财务数据」表从 0 条候选 → 15 条候选，且抽出的是正确值：

```
p7  revenue 2025 = 2,864,469,000,000   ✓ 与人工核对真值一致
p7  revenue 2024 = 2,937,981,000,000   ✓
```

`revenue` 在 601857 年报上的候选从 1 张表（p8）扩展到 2 张表（p7 + p8）。

## 三、仍未取到 capex —— 但根因已收窄到一行

`capex` 与 `depreciation_amortization` 在全文档扫描里仍是 0 条候选。
但定位到了一个非常具体的原因：

```
p7 表 4  data_start=1     ← 应为 0
  header = ['资本性支出', '269,089', '275,849', '275,393', '274,494', '251,323', ...]
  r1 label='经营活动产生的现金流量净额' → 'operating_cash_flow'
```

`资本性支出` 那一行自己就是第 0 行 —— 它是这张表（在 PDF 里）的第一行数据，
却被 `data_start_row` 判定为表头，于是整行变成表头文本、数据丢失。

而映射本身是好的：直接调用 `metric_of_row_label('资本性支出')` → `'capex'` ✓。

结论：别名与映射都没问题，纯粹卡在网格结构。

### 但 `annual26` 的实测显示 capex 已经进来了

修完上面三个缺陷后重跑，601857 的 `capex` 从 0 条变成 24 条候选，
且包含正确的值：

```
269,089,000,000  2025A  p178  raw='269,089'   ← 与手工核算一致
275,849,000,000  2024A  p185  raw='275,849'   ← 与手工核算一致
```

全部 24 条都被标了 `needs_review` —— 同表冲突守卫发现
"同一张表内 capex 出现差异 68 倍的值"。这个标记是对的：
p178/179 是分部报告表（油气和新能源 / 炼油化工和新材料 / 天然气销售 /
总部及其他），各分部的资本开支本来就不同，而提取器把它们都标成了同一主体。

所以现状是：数据进来了、值是对的、但被冲突守卫整体标为"需人工判定"，
R4 因此取不到。这与第四轮记录的局限（"`_best_fact` 无法区分集团口径与同名明细行"）
是同一件事的另一个表现。

### 顺带修掉一个新增的误映射：EBITDA 被当成折旧摊销

重跑后发现 `depreciation_amortization` 里出现了 `49,356,400,000,000` ——
那是 EBITDA（493,564 百万元），不是折旧摊销（215,818 百万元），量级差 2 倍。

根因：中国石油的 EBITDA 行写作

```
息税折旧摊销前利润（EBITDA）（人民币百万元）
```

其中恰好含子串「折旧摊销」，被 `depreciation_amortization` 的别名命中 ——
而 EBITDA 是扣除折旧摊销之前的利润，语义正好相反。

修复过程本身踩了两次坑，都记在代码注释里：

| 写法 | 结果 |
|---|---|
| 字面词 `息税折旧摊销前` | 被否：`折旧与摊销` 也被拦掉（两者共享连续子串 `折旧摊`） |
| 字面词 `息税前` | 被否：`息税折旧摊销前利润` 反而不被拦（不含连续的 `息税前`） |
| 正则 `息税.{0,6}前` | 采用：必然命中所有"息税…前"写法，且不误伤 `折旧及摊销` |

### 又一个发现：别名表缺真实写法

统计 601857 年报的表格行标签，`depreciation_amortization` 的真实写法是：

```
折旧、折耗和摊销   5 次
折旧及摊销        3 次
折旧摊销          3 次
```

而 `configs/metrics.yaml` 里只有 `[固定资产折旧, 折旧与摊销, 折旧摊销]` ——
缺 `折旧及摊销` 与 `折旧、折耗和摊销`，而 `折旧与摊销` 在真实文件里
一次都没出现。已按实测补全别名。

> 测试也因此改了一处：原先的别名表是手写几个，与配置脱节（正是它漏掉了
> `折旧及摊销`）。现在改为从 `configs/metrics.yaml` 构建，
> 并加一条断言直接检查配置里有这个别名。

### 为什么不在本轮继续往下修

`data_start_row` 的判据已经连续改了三轮（第七、九、本轮），每改一次都要靠
既有测试挡住反向误伤（本轮就有一条测试拦下了"声明行"场景）。
再往下修必须用单元格的横向坐标判断行内列结构：

- 需要把 `cells` 的 bbox 传进 `build_header` / `data_start_row`
- 会影响所有表格路径，且大量现有测试假设"网格是矩形"
- 第六轮试过四条纯文本判据，四条都不成立 —— 这是"文本层已经不够用"的信号

因此这仍是一个独立课题，但本轮的收获是：它的边界已经收窄到
"需要用 bbox 判定列结构"这一条具体的技术判断，不再是"网格结构有问题"这种笼统描述。

## 四、意外收获：P4 落地了（第八轮被闸门拦下的那条）

改完表头缺陷后重跑，第八轮"被闸门拒绝"的真实增速通过了：

```
revenue_growth = -0.0250        is_judgment = False    ← 现在是**事实**，不是观点
basis = 由事实库两期收入算出：2024A 2937981000000 元 → 2025A 2864469000000 元，
        同比 -2.50%。两期均取自事实库（fct_tbl_6fba6c48ae8cc393 / fct_tbl_47d39cbfb7c88026）
gaps = （空）
```

两期收入与人工核对真值逐位一致，-2.50% 与年报里印的"下降 2.5%"吻合。

为什么第八轮不行、现在行了：第八轮 `_best_fact` 取到的 `2024A revenue`
是 52,221,000,000（分部收入明细行），与真值差 56 倍 → 闸门判为"取错候选"并回退。
表头修复让 p7「主要财务数据」表的收入行进来了，其中 `2937981000000` 的置信度/口径
排序高于那条分部行，于是选择键取到了正确的值。

### 对估值的影响

| | 第八轮 `r4-real26` | 第十轮 `r4-real30` |
|---|---|---|
| 收入增速 | 8%（模板，闸门拒绝） | −2.50%（事实） |
| `gaps` | 有（"已回退模板值"） | 空 |
| DCF 每股 | ¥19.9840 | ¥15.2090 |

差距从 60% 收窄到 30% —— 但仍未消除，因为资本开支占比（模板 6% vs 真实约 9.39%）
还是模板值：低估资本开支会高估自由现金流，这正是 DCF 仍然偏高的原因。
