> 本轮起点是一个具体任务：把 R4 的经营假设里的「资本开支 / 收入」从模板值 6%

## 二、为什么 capex 接不进来（三条证据，逐条实测）

上一轮（第九轮）的结论是「被分部表的口径歧义挡住，需要区分集团口径与分部明细行」。
这个结论只对了一半，本轮把三条路逐条走了一遍，全部走不通。

### 证据 1：候选值确实在库里，但 12 条全部 `needs_review`

```
$ python tools/fact_probe.py --run annual27 --metric capex --entity 601857 --period 2025A --show-reason
          275849000000 元  2025A  scope=consolidated  p179  raw='275,849'  REV
        ↳ 同一张表内主体（601857）的 capex 出现 85 倍的值：3,239,000,000 元 vs 275,849,000,000 元…
          两条都通过了 quote 校验，需人工判定
          269089000000 元  2025A  scope=consolidated  p178  raw='269,089'  REV
        ↳ 同一张表内主体（601857）的 capex 出现 89 倍的值：3,020,000,000 元 vs 269,089,000,000 元…
```

`store._check_internal_conflict` 的判据是「同文档 + 同主体 + 同指标 + 同期间 +
同口径 + 同一张表 + 相差 10 倍以上」。它在这里判对了：p178 表 1 的第 3 行是

```
资本性支出 | 205,094 | 47,772 | 8,216 | 4,987 | 3,020 | 269,089
                 ↑勘探与生产 ↑炼油化工 ↑销售 ↑天然气 ↑总部   ↑合计
```

集团合计（269,089）与五个分部明细同表同期，而事实库里没有"合计行 vs 明细行"的
结构信息，程序无法判断该采信哪条。守卫标 `needs_review` 是正确行为，
不是误报。

### 证据 2：期间也分不开 —— 2024 与 2025 都进了 `2025A`

我原本以为"按期间筛一下就行"（275,849 是 2024 年的值，剔除它即可）。
实测不成立：

| 页 | 值 | 真实年份 | 事实库期间 |
|---|---|---|---|
| p178 | 269,089 | 2025 | `2025A` |
| p179 | 275,849 | 2024 | `2025A` ← 错标 |

原因：分部报告在同一份年报里以两组印出 ——

```
(a) 2025年12月31日分部信息   ← p178
(b) 2024年12月31日分部信息   ← p179
```

两组的年份都在表体内的碎片行里（p178 表 1 的 r4 是 `2025 | 年 | 12 | 月 | 31 | 日`，
它落在数据区、被 `data_start_row` 判为数据），提取器因此把两组的列统一标成文档级
期间 `2025A`。

后果是致命的："同期间取最大值"必然取到 275,849（2024 年的数），因为它比正确的
269,089 大。也就是说，一旦把 capex 接进来并按现有的 `_best_fact` 权重选择，
拿到的会是一个错的值，而且不会有任何报错 —— 正是本项目最要避免的失败形态。

> 附带确认：两条候选都来自 `doc_840b15aa4dc3`（2025 年报），
> 不是"2024 年报串进来了"。这一点也排除了"按文档期间过滤"的修法。

### 证据 3：现金流量表里没有可用的资本开支行

12 条候选全部来自 p178 / p179（分部报告）。合并现金流量表的"购建固定资产…支付的现金"
没有被抽出来。因此没有第二条来源可以交叉验证。

### 结论

在能区分「集团合计行 / 分部明细行」之前，capex 只能保持模板值。
把 269,089 硬塞进来，等于让模型在一个自己已经标记为不可信的数字上做关键假设 ——
违反本项目「不把未核查伪装成已核查」的原则。所以本轮不做这件事，
而是把它留在缺口清单里。

## 三、★ 顺带查出的结构缺陷：低估 capex 时，更准的 D&A 会让估值更高

### 3.1 现象

第十轮把 D&A/收入 从模板 5% 换成事实库真值 7.53%（215,818 ÷ 2,864,469，
2025 年报合并现金流量表）。改完之后：

| 运行 | 收入增速 | D&A/收入 | capex/收入 | **DCF 每股** |
|---|---|---|---|---|
| `r4-real30` | −2.50%（事实） | 5%（模板） | 6%（模板） | ¥15.2090 |
| `r4-real31` | −2.50%（事实） | 7.53%（事实） | 6%（模板） | ¥22.5435 |

换成更准的数据，估值反而涨了 48%。这是必须解释的反常。

### 3.2 根因

自由现金流公式：

```
FCFF = EBIT×(1−税率) + D&A − capex − ΔNWC
```

代入 r4-real31 的数字（税率 25%）：

```
税盾收益（多计提折旧少缴税）  = +0.25 × 7.53% = +1.88%
税后加回（D&A 是非现金支出）  = +0.75 × 7.53% = +5.65%
                              合计            = +7.53%
capex 扣减                    = −6.00%
                              ─────────────────────
净效果                        = +1.53% 收入
```

关键在 `D&A − capex = 7.53% − 6.00% = +1.53% > 0`。

"折旧比投入多"被模型解释成了白赚的现金。这在会计含义上等于假设
公司不重置正在折旧的资产 —— 即清算，不是持续经营。
一个做 DCF 的模型允许自己在"永续经营"的前提下同时假设"不重置资产"，
是自相矛盾的。

### 3.3 为什么这类缺陷特别危险

1. 方向反直觉：数据质量提升（模板值 → 真值）通常是好事，
   这里却放大了估值。任何"改了更准的数据所以更可信"的直觉都会失效。
2. 不报错：所有量纲闸门、quote 回读、算术恒等式全部通过。FCFF 算式本身没有错，
   错的是两条假设之间的关系。
3. 会互相掩护：正因为 capex 取不到真值（第二节），模板 capex 会长期停在 6%，
   这个缺陷就会长期存在 —— 而且随着 D&A 越趋真实，估值越高。
   两个缺陷叠加后产生的偏差，比任何单独一个都大。
4. 它是"没查"被当成"查过没问题"的典型：模型从未检查过 capex 与 D&A 的关系，
   却一直输出看起来完整的估值。

### 3.4 修复：两道关，职责不同

第一道 —— 构造前的一致性闸门（`pipelines/r4_valuation/assumptions.py::_derive_capex_ratio`）

```python
if da_ratio_value > 0 and template < da_ratio_value:
    return da_ratio_value, f"{GATE_MARKER}由一致性闸门抬升至 {da_ratio_value:.2%}…", da_ratio_fid
```

把 capex 抬到与 D&A 相等，并在依据里写清三件事：为什么抬、抬的后果
（税盾 `+0.25×D&A` 与税后加回 `+0.75×D&A` 之和超过 capex 扣减）、
以及真实值 9.39% 仍高于本值，所以 DCF 依然偏乐观。

抬到「相等」、不抬到更高，是有意为之的：多出来的部分没有事实依据，只能是观点；
而「相等」是持续经营的最低要求，是本模型能自我辩护的下限。

第二道 —— 模型层的硬校验（`domain/tools/finance.py::DCFInput`）

```python
@model_validator(mode="after")
def _capex_must_cover_depreciation(self) -> "DCFInput":
    if self.capex_ratio_of_revenue < self.da_ratio_of_revenue:
        raise ValueError("…")
    return self
```

为什么不能只留闸门：闸门在 `assumptions.py` 里，而 `DCFInput` 是公开契约，
可以绕过闸门直接构造。自动修正的坏处正是本轮缺陷的形态 ——
调用方"悄悄拿到一个被改过的输入"。所以闸门负责改并说明，
模型校验负责确认它真的合规。两处职责不同，缺一不可。

### 3.5 修复效果

| 运行 | D&A/收入 | capex/收入 | **DCF 每股** | TV 占比 |
|---|---|---|---|---|
| `r4-real30` | 5%（模板） | 6%（模板） | ¥15.2090 | 0.790 |
| `r4-real31` | 7.53%（事实） | 6%（模板） | ~~¥22.5435~~ | 0.790 |
| `r4-real32` | 7.53%（事实） | 7.53%（闸门抬升） | ¥18.1080 | 0.790 |

闸门消除的 ¥4.4355 全部来自 `D&A − capex` 那一项的人为正值。

> 剩下的 ¥18.11 与相对估值区间（¥11.60 ~ ¥12.16）仍差约 49%。
> 这一差距不是本轮缺陷造成的：报告里的「市场参照」段落已经指出，
> 市场对该公司隐含的要求回报率是 `1 ÷ PE = 8.14%`，而 CAPM 算出的 WACC 是 6.22% ——
> 模型用了比市场更低的折现率，DCF 天然更高。
> 项目不用市价反向校准 WACC（那会让 DCF 退化成把市价重算一遍），
> 而是把差额作为"待解释的信号"呈现。加上 capex 仍被低估（本值 7.53% vs 真实 9.39%），
> 两个方向都指向"当前 DCF 偏乐观"，报告里逐条写明。

## 四、顺带修掉的两个可复现性问题

### 4.1 `tools/fact_probe.py` 在 GBK 控制台崩溃

诊断 capex 时工具直接抛 `UnicodeEncodeError: 'gbk' codec can't encode character '\u21dd'`
并中断 —— 排查工具在最需要它的时候挂掉。已改为显式 `reconfigure(errors="replace")`，
降级处理，不再崩掉。

### 4.2 事实库不保存行标签 → 复核时无从判断

这是本轮最值得记的工程教训。复核 capex 时我看到的是 12 个数值加一句
"同表冲突，需人工判定"，完全无法判断该采信哪条 —— 因为
「合计 / 明细」这个唯一能区分的信号（行标签）从来没有落盘。

`Fact.channel_readings[].note` 此前为空。现在写入：

```
note = "行：资本性支出｜列：2025A"
```

`tools/fact_probe.py` 一并显示。这把人工判定从"猜"变成"看"。

> 注意：这只改善诊断能力，不改变任何判据 ——
> capex 依然接不进来（第二节的三条证据不因此变化）。
> 但下一次有人查同类问题时，不必再从 PDF 里手工翻表格。

## 五、这一轮没有解决什么

| # | 未解决项 | 现状 |
|---|---|---|
| 1 | 无法区分「集团合计行」与「分部明细行」 | 守卫只能整体标 `needs_review`；需要抽取层保留行层级 |
| 2 | 分部报告 (a)/(b) 两组列被统一标成同期 | 年份在表体碎片行内，`data_start_row` 判为数据 |
| 3 | capex 仍为模板值（经闸门抬升后 7.53%） | 真实约 9.39%，DCF 因此仍偏乐观 |
| 4 | 合并现金流量表未抽出"购建固定资产支付的现金" | 无第二来源可交叉验证 capex |

前三条都指向同一个修法：按单元格 bbox 重建网格（README 已知限制第 13 条）。
本轮再次确认它是 capex 问题的同一个根因，不是三个独立问题。
