# 工程实现记录 —— 踩过的坑与设计决策

> 本文件记录开发过程中实际遇到并修复的问题，以及由此产生的设计决策。
>
> 为什么值得单独写一份：
> 1. 团队成员（以及协助开发的 AI）能避免重复踩同一个坑
> 2. 答辩时被问「为什么这样设计」，这里有真实的原因而非事后编造的理由
> 3. 它本身就是「工程严谨性」的证据 —— 这些都是真实项目才会遇到的细节

---

## 一、金融领域的专有陷阱

### 1.1 「占公司总股本比例」中的「总股本」不是总股本

现象：公告里写「占公司总股本比例：12.40%」，抽取结果把 `shares_outstanding`
（总股本，单位应为「股」）抽成了 `12.40 %`。

根因：别名表里有「总股本」，朴素做法（对每个别名做独立正则）会让它匹配到
后面那个百分比。

修复：把匹配算法从「以别名为中心」改为「以数值为中心，最近且最长的别名胜出」：

```
得分 = 别名长度² ÷ 与数值的距离
```

再加两道闸门：
- 边界闸门：别名与数值之间不得跨越句号/换行/制表符
- 量纲闸门：抽出的单位必须与指标声明的单位同族（金额/股数/比率/每股）

为什么长度要平方：只看距离会让「短别名紧邻」压过「长别名稍远」，
而语义上「更长 = 更具体」应当优先。

---

### 1.2 「归属于母公司股东的净利润」与「净利润」会互相抢值

现象：`net_profit_total`（净利润）抽到了 `net_profit_parent`（归母净利润）的值。

根因：文本里「归属于母公司股东的净利润 245,600.00」出现在「净利润 250,300.00」
之后。别名「净利润」做 `rfind` 时找到的是归母那一行。

修复：按别名长度降序处理各指标，并做全局区间仲裁。
「归母净利润」比「净利润」长，因此先声明其覆盖的原文区间；
后处理的「净利润」不得再声明与之重叠的区间。

推广：这是"最长匹配优先 + 区间互斥"的经典冲突消解，
任何别名体系（行业分类、实体识别）都会遇到。

---

### 1.3 「单位缺失」必须拒收，不能猜

现象：财务表格里「货币资金 680,200.00」，数值有了但单位在表头（「单位：万元」）。

决策：单位缺失时拒收该字段并记入 rejected，不做猜测或默认。

理由：猜错单位的代价远大于缺失 ——
一个错误的数字会在 R5 阶段制造误报（直接打击"误报控制"评分），
而缺失只会降低覆盖率，且我们会在报告中显式声明缺口。两者代价不对等。

代价与缓解：拒收率不低（实测 40 个候选中约 29 个因缺单位被拒）。
缓解手段是「文档级单位推断」——见 1.4。

---

### 1.4 报告期与单位需要「文档级回退」

现象：一份 5 页年报中，`period` 字段有 37/40 条是 `unknown`。

根因：续表页往往不重复印刷年份，只有表头的「单位：万元」。
页级推断必然失败。

修复：在 ingest 阶段做全文档期间识别（统计年份出现频次取众数，
结合「半年度/前三季度/年度」等词确定后缀），作为页级推断失败时的回退。

另一个坑：`infer_period` 最初取窗口内最后一个年份，
结果把「营业收入 X 万元，同比增长 Y%」中的基期年份当成了报告期。
中文财报的叙述结构是「本期在前、基期在后」，因此必须取第一个年份。

## 二、PDF 解析的陷阱

### 2.1 `get_text("dict")` 的顺序 ≠ 阅读顺序（最重要）

现象：抽取时 `period` 全部丢失，quote 定位漂移。

根因：`page.get_text("dict")` 返回的块顺序是 PDF 内容流的写入顺序，
与视觉阅读顺序不一致。而 `page.get_text("text")` 返回的是按阅读顺序整理的文本。
我们把前者的块按 bbox 排序后拼接，用于抽取与 quote 回读 ——
拼出来的文本与真实原文在换行/位置上都有差异。

修复：
- 权威页面文本一律取 `get_text("text")`，用于字段抽取与 quote 回读
- 块排序结果（含 bbox）只用于 Web 端高亮展示
- 通道记录里同时保留 `raw`（权威）与 `text`（展示）两个字段

教训：凡是要做「逐字子串校验」的场景，必须用文档库提供的原生权威文本，
不能自己拼接。

---

### 2.2 `insert_textbox` 放不下会静默丢弃内容

现象：合成的年报样本第 2 页 `get_text` 只返回 0 个字符。

根因：`Page.insert_textbox` 在内容放不下时返回负值并丢弃超出部分，
不抛异常。我们最初忽略了返回值。

修复：
1. 检查返回值，为负则报错
2. 用二分试排确定每页能容纳的最大行数（比估算行高可靠）
3. 生成后回读校验：任何一页内容少于 20 字符即报错

推广：任何"写入可能静默截断"的 API（textbox、缓冲区、日志轮转）
都必须检查返回值 + 回读校验。

---

### 2.3 `text_coverage` 不能用来判断「页面有没有文字」

现象：所有 5 页都被路由到 `E_mixed`，应该是 `A_text_only`。

根因：`text_coverage = 文本块 bbox 面积 / 页面面积`，
正常 A4 正文页只有 0.2–0.4（行距与页边距吃掉大部分面积）。
最初的阈值设为 0.60，永远达不到。

修复：判断「有没有文字」改用 `char_count`（有效字符数）；
`text_coverage` 阈值降到 0.12，仅用于识别极端情况。

教训：指标定义要与判定目标匹配。用几何覆盖率判断"内容有无"是错误抽象。

### 2.4 bbox → 像素的 y 轴翻转搞反了（代价最大的一个坑）

现象：单元格级 VLM 裁决"改值"了 184 个复核格中的 80 个。
而程序读数的数值保真率是 100% —— 一个 100% 保真的读数源
不该需要 43% 的"纠正"。抽查裁图发现：模型读的是对的，裁图是错的。

根因：裁图按「PDF 用户空间原点在左下」写成了
`pixel_y = (page_height - bbox_y) * scale`。
但 PyMuPDF 的 `page.rect` 与 `get_text()` 用的是同一套坐标：原点左上、y 向下。
于是每一次裁图都沿页面中线上下镜像：

* 第 1 行的格子裁出来是第 22 行的内容
* 模型读的是它看到的东西 → 与程序读数"不一致"
* 高置信度（自评恒为 0.95）+ 图文自洽的位置确认 → 一路放行，覆盖掉正确的值

定位过程（不靠猜）：

1. `page.search_for("501,000.00")` 给出权威位置 → 与单元格 bbox 完全一致
   ⇒ bbox 没错，排除表格重建
2. 「直接 `clip` 渲染」与「从整页图按算出的像素框裁」并排：
   前者 `501,000.00`，后者 `179,000.00` ⇒ 问题在像素换算
3. 在整页图上按文本层坐标取横带：像素 y 越大内容越靠上
   ⇒ 确认 y 轴方向搞反

修复：抽出 `cell_pixel_box()` 并去掉翻转；`_annotate_cell_on_page()`
（画红框的那个）有同一个 bug，一并修掉。

为什么极难发现：镜像后的坐标依然是合法坐标 —— 图裁得出来、
尺寸对得上、不抛异常、不报错。唯一的判据是"裁出来的像素是不是那个格子"，
因此回归测试也只能用内容比对：拿 `get_pixmap(clip=...)`
（与 `search_for` 同源）当真值，比较像素差。

教训：同一个库里的坐标约定未必是同一个。"PDF 用户空间"与
"PyMuPDF 页面空间"是两套东西。凡是跨库传坐标，都要用一个
自带真值的方式（这里是 `search_for` + `clip` 渲染）验一次，
不靠推导 —— 推导错了不会报错，只会静默地取错一整片区域。

连带收获：这次事故暴露了三道"模型自述"闸门（quote 回读 / 位置确认 /
置信度）全部无效，因为读错格子时模型的自述依然自洽。
因此新增了第四道几何佐证闸门：该 bbox 内页面上真实印着的字，
必须支持模型读数、且不支持原读数。详见 `docs/P0_VALIDATION.md` §6.6。

## 三、Harness 框架的陷阱

### 3.1 `__len__` 让空缓存变成 `False`（最隐蔽的 bug）

现象：模型响应缓存永远为空，`replay` 与成本优化全部失效，而且不报任何错。

根因：`ResponseCache` 定义了 `__len__`，Python 的真值测试退化为
`len(cache) != 0` —— 空缓存是 falsy。调用方写 `if self.cache:`，
第一次运行时缓存为空 → 静默跳过写入 → 缓存永远是空的。

修复：
1. 显式定义 `__bool__`，返回 `self.enabled`（表达"有没有配缓存"，而非"缓存空不空"）
2. 调用点改为 `if self.cache is not None:`

推广：定义了 `__len__` 的容器类，只要可能为空，就必须显式定义 `__bool__`。
这类 bug 不会崩溃、不会报错，只会让功能悄悄失效 —— 最难发现。

---

### 3.2 时间戳让「可复现」无法通过机器校验

现象：`agent replay --strict` 报「不可复现」，但数据明明一样。

根因：产物中的 `built_at` / `extracted_at` / `registered_at` / `checked_at`
各自调用 `utcnow()`，两次运行时间戳不同 → 文件哈希不同。

修复：
1. `RunContext.build_stamp()` 统一返回 `manifest.started_at`
2. 所有产物时间戳一律取自它
3. replay 时必须把原始 manifest 的 `started_at` 传回 `build_context()` ——
   否则回放用的是当前时间，哈希依然不一致

Excel 的额外坑：`openpyxl` 会在 `docProps/core.xml` 里嵌入当前时间，
且 zip 成员带本地时间戳。修复方式见 `domain/tools/xlsx.py`：
导出后重写 zip，统一 `dcterms:created/modified` 与 ZipInfo 时间。

概念澄清（重要）：可复现性有两个层次，不能混淆：

| 层次 | 判据 | 我们的做法 |
|---|---|---|
| 逐字节回放 | 同一次运行离线重放，产物哈希完全一致 | `agent replay --strict`，测试中作为硬断言 |
| 跨运行语义等价 | 不同次运行的结论一致（时间戳/run_id 必然不同） | 剔除易变字段后比对 JSON 结构 |

早期测试把「跨运行字节相同」当成判据，因此永远无法通过——
这是对可复现性概念的误解。

---

### 3.3 预算闸门超限必须「优雅降级」而非崩溃

设计：`Budget` 四道闸门（步数/token/时长/成本）。
超限抛 `BudgetExceededError`，由调度器捕获并转成 `status=partial`。

为什么：跑了一半的流水线崩掉，比产出一份「明确标注了缺口」的部分结果
差得多。评审看到 `status=partial` + 缺口清单，能理解发生了什么；
看到崩溃则只能认为系统不可靠。

---

### 3.4 断言 SKIPPED ≠ FAIL

现象：`is_usable` 返回 `False`，但一条断言都没失败。

根因：`all_passed` 最初实现为 `all(status == PASS)`，
而缺辅助数据时断言被标记 `SKIPPED` → `all_passed` 为 False →
`is_usable` 为 False → 得出「因为没数据所以模型不可用」的荒谬结论。

修复：区分三个概念，并在报告中同时呈现：

| 属性 | 含义 |
|---|---|
| `has_failures` | 有没有校验失败（SKIPPED 不算） |
| `all_passed` | 是不是全部都做了且通过了 |
| `is_usable` | 判据是 没有 FAIL（缺数据不等于模型错） |
| `verification_coverage` | PASS / 总数 —— 诚实度指标，如实告诉读者有多少勾稽关系没验证到 |

这一条与赛题的「证据支撑充分性」直接相关：
把"未验证"伪装成"已验证"是学术不诚实；披露覆盖率才是正确做法。

### 3.5 `except Exception` 把代码 bug 一起吞了（最隐蔽的失败模式）

现象：一次真实运行 `judge` 阶段状态 = success，
但产物 `table_adjudications.json` = `[]`，报告里没有任何异常迹象。

根因：裁决循环里写了一个未定义变量（应为 `max_calls`），
10 张表全部抛 `NameError`，而 `except Exception: continue` 把它们全咽了下去。
统计量 `tables_adjudicated` 还在自增 —— 因为计数写在 `try` 之前。

修复：

1. 改正变量名；
2. 区分 `tables_attempted` / `tables_adjudicated` / `table_adjudication_errors`，
   计数写在 `try` 之后；
3. 阶段事件在有失败时置为 `warn`，并在控制台显式打印失败张数。

教训：`except Exception` 是健壮性的来源，也是可见性的黑洞。
凡是吞异常的地方，都必须配一个会被看到的计数器。

附加防线：`tests/test_static_health.py` 用标准库 `symtable` 做
未定义名体检 —— 这类 bug 运行期测试抓不到（除非恰好跑到那条分支
并断言产物非空），静态检查却一抓一个准。写下它的当次改动中，
它立刻抓到了 `decide_cell_verdict` 里的一个同类错误。

### 3.6 只靠模型自述的闸门等于没有闸门

现象：单元格级 VLM 裁决把 80 个格子"改值"，独立复核后 75 个是错的，
而三道闸门（quote 回读 / 位置确认 / 置信度 ≥0.7）全部放行。

根因：三道闸门校验的都是模型的自述：

* quote 回读只校验"这段文字在整页某处存在" —— 读错格子时照样成立
* 位置确认用的是同一张错图渲染的红框 —— 图文自洽，必然通过
* 置信度自评恒为 0.95，没有区分度

修复：新增几何佐证 —— 该 bbox 内页面上真实印着的字，
必须支持模型读数、且不支持原读数；没有文本层时失败关闭。
这道闸门**不做成配置开关**：能被关掉的安全闸门等于没有。

教训：校验必须引入模型无法影响的事实。
"模型说它对"与"它是对的"之间，需要一条独立的证据链。

## 四、R5 核查的误报控制（评分关键）

核查系统最容易失败的地方不是"查不出错"，而是"报了太多不存在的错"。
以下三处误报都是实测出现并被修复的：

### 4.1 派生指标不适用「查来源」

现象：「同比增长 7.92%」「毛利率 48.33%」被报成「在原始材料中找不到来源」。

根因：E4（引用核查）的本质是「查找同名来源」，
但增速与占比是算出来的，事实库里本来就没有同名记录。

修复：识别「派生型上下文」（同比/环比/占比/比重/毛利率/…），
E4 直接跳过这类主张；它们的正确性由 E5（独立重算） 负责。

---

### 4.2 「归属于母公司」中的「母公司」不是「母公司报表口径」

现象：草稿里每一条「归属于母公司股东的净利润」都被报成「口径错误」。

根因：口径关键词表里有「母公司」，朴素子串匹配命中了「归母公司」。

修复：`detect_statement_scope()` 做三段判定：
1. 明确出现「合并报表/合并口径」→ `consolidated`
2. 明确出现「母公司报表/母公司口径」→ `parent_only`
3. 其余含「母公司」的表述一律不判定（尤其是「归属于母公司…」这类）

教训：中文金融术语里存在大量「包含关系陷阱」，
关键词匹配必须做否定上下文排除。

---

### 4.3 同一位置不该报两类错

现象：草稿把「净利润 2,456,000,000.00 元」误写为「…万元」，
结果同时报出 E1（单位错误）与 E4（无来源）—— 后者是前者的副作用。

修复：同位置优先级抑制。若同一字符区间已有 E1/E5 这类
确定性数值错误，不再重复报 E3/E4/E6。

重复报错会虚增问题条数并直接拉低精确率。

---

### 4.4 量纲不同族的数字不可比

现象：E1 把「同比增长 7.92%」拿去和「2,456,000,000 元」比较，
得出「相差 10^8 量级，属于万元/亿元单位混用」这种荒谬结论。

修复：引入单位量纲族（money / share / ratio / per_share），
跨族比对一律禁止。同时在"按数值反查事实"时增加量级闸门（至少差 10 倍）。

反过来也有坑：草稿写「万元」、事实库存「元」，
不加归一化会把正确的数字判成「无来源」。因此比对前必须换算到共同量纲。

---

### 4.5 误报回归基线

`tests/test_audit.py::test_no_false_positives_on_clean_draft`
断言一份完全正确的草稿产生零发现。

这是整个测试套件里最重要的单条测试：
任何规则改动引入误报，CI 立刻失败，问题在合并前就被拦住。

## 五、环境与工程适配

### 5.1 Windows 控制台 GBK 编码

输出 emoji 或部分 Unicode 字符会抛 `UnicodeEncodeError` 并中断整个流程。
统一用 `agent.console.enable_utf8_output()` 在入口处切换 stdout/stderr 到 UTF-8。

### 5.2 pytest 的 `tmp_path` 在受限沙箱下不可用

`TempPathFactory` 分配目录时会枚举 basetemp 下的已有目录以决定编号
（`root.iterdir()`）。受限环境下目录枚举被拒绝 → `PermissionError` →
23 个正常测试变成 ERROR。

修复：在 `tests/conftest.py` 中覆盖 `tmp_path` fixture，
用"唯一路径 + mkdir"实现，不枚举、不清理、不建符号链接。

### 5.3 YAML 中 `%` 开头需要引号

`unit: %` 会让 YAML 扫描器报 `found character '%' that cannot start any token`。
必须写成 `unit: '%'`。

### 5.4 测试辅助函数必须完整转发参数

`_gateway(**kw)` 最初没有把 `kw` 传给 `ModelGateway`，
导致传入的 `cache` / `budget` / `offline` 全部被静默忽略 ——
测试"通过"了，但实际什么都没验证。

这类 bug 比测试失败更危险：它制造虚假的安全感。
修复后立刻暴露了两个真实的缓存 bug（见 3.1）。

### 5.5 页面渲染正确 ≠ 页面能用：JS 层没有任何门看着

这是 5.4 的同类问题，只是发生在另一个层次。控制台右侧那栏（模型与工具的
原文流）一直显示 `未连接`，而**四个渲染门全绿**：`tools/web_smoke.py`、
`tools/web_pages_check.py`、`tests/test_web.py`、`tests/test_panel.py` 全部走
in-process 渲染 —— 它们拿到的是 HTML **字符串**，不执行任何 JavaScript。

根因是两条互不相干的决定撞在一起：

1. `web/static/trail.js::activeKinds` 内部 `.join(',')` 后返回**字符串**，
   而 `web/static/activity.js` 里**同名**的函数返回**数组**。
2. 控制台「运行」页把两个模块放进**同一个** `<script>` 元素，
   于是 `Trail.activeKinds(on).join(',')` 抛 `kinds.join is not a function`。

异常是**同步**抛出的，所以它掐掉的不只是自己那个 IIFE —— 同一段脚本里
后面的右栏 IIFE 一起没了。表现出来就是页眉那行停在初始文案 `未连接`，
而它要读的接口返回的数据完全正确。四个标签页里只有「运行」页如此：
另三页在那一行之前就 `return` 了。

两条教训：

- **同名的东西必须给同一个类型**。修的是这一类，不是那一个调用点 ——
  调用方各自 `join`，比让一个函数按调用场景返回两种类型安全。
- **初始文案恰好就是故障的样子**，所以测试断的必须是「离开了初始值」，
  而不是「接口返回了数据」。为此加了 `tests/test_panel_js.py` +
  `tests/js/panel_harness.js`：给一份最小 DOM，用 node 按页面里的顺序
  **真的执行**那些脚本，fetch 的响应由 `TestClient` 预先取好喂进去 ——
  不联网、不占端口。夹具的缺口（少实现了某个 DOM 属性）会抛 `StubGap:`，
  与页面自己的异常分得开：否则夹具的锅会看着像页面的 bug，实测踩过一次。

### 5.6 收起键把自己所在的房子一起拆了

右栏标题旁边有个「收起」。点一下，整条右栏消失 —— **包括那个按钮本身**：
`body.rail-off .rail{display:none}` 藏的是整条右栏，而 `#rail-toggle` 自己
就住在 `.rail-head` 里。按钮是唯一能把右栏收回来的东西，它把自己关掉的那扇
门一起拆了。`setRail` 又把这个状态写进了 `localStorage`，于是刷新也回不来，
只能去清站点数据。这一条是用户在真机上点出来的，任何门都没响：
**四个渲染门都不看 CSS**（`test_panel_js.py` 那个夹具也没有样式，那里测的是
JS 跑不跑得起来，不是元素看不看得见）。

第一版修法是让栏头活下来：收起只藏栏身，栏头压成一条 400px 的横条，停回右栏
原来的位置（拿无头 Chrome 真渲染验过往返：点一下变横条、再点一下原样恢复）。
**用户的裁决更干脆 —— 删掉这个键**，于是按钮、`rail-off` 规则、`localStorage`
那一路全删，右栏常驻。这个裁决是对的：这一栏就是控制台存在的理由（看 agent
在干什么），不是可以关掉的东西 —— 一个「收起」键要成立，得先有人需要收起它。

两条教训：

- **藏东西的规则不许藏掉它自己的开关**。第一版就是照这条修的，也正是照这条
  才看清这个键本来就不必存在。现在 `tests/test_panel.py::test_the_rail_cannot_be_hidden`
  把「右栏常驻」钉成结构：右栏还在、按钮不在、`rail-off` 在 CSS 与页面脚本里
  都不在 —— 少任何一条，这扇单向门都装得回来。
- **持久化界面状态，就是把一次误操作变成永久状态**。`localStorage` 本身没有
  写错（控制台是天天开着的页面，每次刷新重设一遍才是骚扰），但它把「点一下
  试试」的代价从一次刷新抬成了「去清 site data」。要持久化一个不可逆的状态，
  得先保证它是可逆的。

### 5.7 页面上和页面文件里都不该写「解说」

控制台第一版的标题长这样：

```
③ 每步在干什么   用时 / 模型调用 / 花费 / 这一步自己的计数 · 跑完后刷新看到全部
④ 事件流         正在跑就每 2 秒刷新
① 传入数据       放进收件目录，就是下一次运行的输入
```

用户的判词是「完全的大模型生产的狗屎」。这几句的共同毛病不是啰嗦，是
**句子的主语是写页面的人，不是屏幕上的数**：`每步在干什么` 是我对这张表的
介绍，`跑完后刷新看到全部` 是我在替读者预设他的疑问，`正在跑就每 2 秒刷新`
是我在自述轮询实现。读者打开控制台要的是读数，任何一句「我为什么这么设计」
都是在跟读数抢位置。改法不是缩短，是**换主语**：`③ 流水线状态`、`④ 事件`、
`① 传入数据` —— 标签只说这一块是什么，怎么用是读者的事。

同一件事还有第二种写法：注释。控制台的前端文件（`panel.html`、`panel.css`、
`trail.js`、`activity.js`、`_trail.html`）原先把上面这套解说又写了一遍，加上
大段「为什么这么设计」的段子，密度最高的 `panel.html` 是 38/668 行。注释与
页面文字是同一件事的两种写法：都是写给**假想的审阅者**看的辩解。用户的原话是
「谁他妈教你把注释写进前端的？」—— 前端文件现在只剩代码，理由搬到本文档。

搬过来的两条是真会被踩的，不许跟着注释一起丢：

- **右栏一律 `textContent`，`innerHTML` 一句都不许有。** 那里渲染的是模型输出
  与工具返回值，是任意的、不受我们控制的文本。`tests/test_panel.py::test_rail_renders_text_through_the_dom_not_html`
  静态扫`web/static/activity.js` 守着这一条。
- **`trail.js` 与 `activity.js` 里同名的 `activeKinds` 必须返回同一种类型**
  （数组，由调用方 `join`）。曾经一个返回字符串一个返回数组，控制台把两个模块
  放进同一个 `<script>`，`Trail.activeKinds(on).join(',')` 抛 `kinds.join is not
  a function`，**同步**异常掐掉了后面的右栏 IIFE（见 5.5）。

留一句 `/* ---- 分区名 ---- */` 也不行吗？不行。分区标记是在替文件目录说话，
而 `header.top` / `nav.tabs` / `ol.trail` 这些选择器自己就是目录。

## 六之二、真实年报带来的第二次返工（2026-09）

这一节的结论比具体修复更重要：只用公告材料做验证，会把「只支持一种表格形态」
误判成「系统已经可用」。

第一轮验证用的是 77 份公告，系统的确定性路径（表格网格 + 规则引擎）在那批材料上
表现良好，于是被当成主力。但真实年报的表格形态完全不同：

| | 公告表 | 财务报表 |
|---|---|---|
| 指标在哪 | 列头 | 行标签 |
| 主体在哪 | 行标签（被担保方） | 表外（报表标题） |
| 期间在哪 | 单元格内 | 列头（本期 / 上期并排） |
| 单位在哪 | 单元格内 | 表级声明（`单位：元` / `金额单位为人民币百万元`） |

943 页年报在修复前的实测结果：241 条事实、召回 14.3%、抽中准确率 25.0%。
但下钻之后发现问题的性质不是"读错了"：

| 基准真值 | 系统是否读到了 |
|---|---|
| 湖南发展 营业收入 349,165,168.51 | 读到了 3 次，但 `entity` 被标成「营业收入（元）」 |
| 湖南发展 所有者权益 3,797,417,361.30 | 读到了，但 `metric` 被标成 `total_assets` |
| 中国石油 营业收入 2,864,469（百万元） | 完全没读到（整表因"无单位"被拒） |

数字读对了，主体名、科目名、期间贴错了。这类「数字正确、归属错误」的事实
比漏抽更危险：它过了 `quote` 回读闸门、置信度 0.95、会一路流进估值与核查，
而下游完全看不出它贴错了标签。

> **2026-10-10 订正（上表第二行）**：那一行两边都写反了。
> 3,797,417,361.30 确实是**母公司**资产负债表的「资产总计」行
> （= 母公司负债合计 364,789,378.77 + 母公司所有者权益合计 3,432,627,982.53），
> 所以系统把它标成 `total_assets` 是**对的**，错的是当时的基准行 ——
> 它把母公司资产总计写成了「所有者权益」，而且取的是母公司口径。
> 合并口径的 2024/2025 资产总计是 3,441,060,747.63 / 3,547,820,309.72。
> 参见 `VALIDATION_ROUND2.md` §3.1 的订正与 `VALIDATION_INDEX.md` 第二节。

### 一条副产品教训

把 943 页真实年报放进 `data/raw/` 之后，测试从 36 秒变成 10 分钟以上 ——
因为 `data/raw/` 是测试夹具的输入目录（`tests/test_web.py` 会以 `--data data`
跑一次完整流水线）。症状看起来像"测试变慢了"，不像配置错误。
现在真实材料一律放 `data/real/`。

## 七、给 AI 辅助开发的经验

本项目大量借助 AI 生成代码，以下几条显著提升了产出质量：

1. 契约先行：先把 Pydantic 模型和 JSON Schema 定死，再生成实现。
   AI 拿着明确的结构定义，产出正确率远高于口头描述。
2. 测试驱动：先写测试（含期望的失败用例），让 AI 去通过测试。
   这是约束 AI 不跑偏的最有效手段。
3. 文件系统作为集成总线：模块间只传文件路径，不传内存对象。
   每个模块可独立跑、独立测、独立让 AI 重写而不影响别人。
4. 踩坑写进注释：把"为什么不能这样做"写进 docstring。
   AI 读代码时会看到，从而不再重犯同一个错。
5. 报错要带操作指引：`raise HarnessError("...", hint="pip install xxx")`。
   人和 AI 都能据此自行修复。
6. 警惕静默失败：本项目最重要的三个 bug（缓存不写、文本顺序错、
   textbox 丢内容）都是不报错的静默失败。凡是"降级/跳过/丢弃"，
   都必须留下痕迹。
