## 一分钟了解这个项目

一句话：我们用自研的 Agent Harness 把「原始材料 → 可信事实库 → 估值模型 → 报告核查」串成一条闭环流水线，
其中每一个数字都能回溯到原文片段，每一次运行都能逐字节复现。

三个需求不是三个功能，而是一条质量链：

```
受控材料（公告 / 年报 / 扫描件）
      │
      ▼  三层解析引擎（文本层 → OCR → 多模态裁判）
┌──────────────────────────────────────────┐
│  R1 事实库 Facts                          │   ← 唯一数字真源
│  每条数字带：原文锚点 + 置信度 + 来源层     │
└──────────────────────────────────────────┘
      │                    │
      ▼                    ▼
┌──────────────┐   ┌──────────────────┐
│ R4 估值建模   │   │ R5 报告核查        │
│ 事实→假设→DCF │   │ 数字→反查事实库    │
│ →区间→敏感性  │   │ →五类错误比对      │
└──────────────┘   └──────────────────┘
```

核心设计哲学：LLM 负责「提出」和「解释」，代码负责「确定」和「证明」。

## 命令行接口

| 命令 | 作用 |
|---|---|
| `agent run <pipeline>` | 执行流水线：`r1_extract` / `r4_valuation` / `r5_audit` / `full` |
| `agent run full --mock` | 端到端跑完三阶段（mock 模型，零成本） |
| `agent run full --data <目录>` | 用真实材料跑（`--limit` 支持小样本试跑） |
| `agent run r4_valuation --facts-run <id>` | 复用已有事实库跑估值 |
| `agent replay <run_id> --strict` | 离线重放并逐字节校验可复现性 |
| `agent verify <run_id>` | 校验 run 目录完整性（产物未被篡改） |
| `agent audit <run_id>` | 生成运行审计报告（过程可追溯） |
| `agent list` | 列出历史运行 |
| `agent prompts` | 列出全部提示词及版本哈希 |
| `agent skills` | 列出领域技能，并校验其绑定的工具/提示词真实存在 |
| `agent tools` | 列出全部工具及其副作用/确定性标注 |
| `agent mcp` | MCP 服务器状态；`--self-test` 走完整协议自检（真实子进程） |
| `agent contracts` | 导出数据契约 JSON Schema |
| `agent doctor` | 环境自检 |

### `web.panel` —— 控制台（一页，四个标签）

演示与自检用的最小界面：**运行 / R1 提取 / R4 估值 / R5 核查** 四个标签页，
一次只看一块，每块自己带完整的上下文。它能做三件事，也只做这三件事：

- **可以运行** —— 传 PDF 进收件目录（页面上传，或直接用命令行的 `inbox/`），
  在页面上**开始运行**；`离线自检` 勾选框不调模型、零成本，
  用来验证环境与编排；真实运行仍要勾「会产生费用」。
  运行页四块读数：① 传入数据 ② 运行 ③ 流水线状态 ④ 事件。
- **查看运行过程** —— 直接轮询该 run 的 `trace.jsonl`（按**字节偏移**增量读，
  只消费到最后一个完整换行），事件 + 阶段进度 + 日志每 2 秒刷新。
  正在跑的 run 也能看：**没有 `manifest.json` 就是「还在写」**。
- **看模型与工具在干什么** —— 右栏常驻，**四个标签页上都在**：模型这次收到的
  完整提示词与它答的原文、工具收到的入参与返回的原文，一条一条往下流，还在写的
  run 每 2 秒续读。它读的是 `agent_log.jsonl`（逐步记录），**不是** `trace.jsonl`
  —— 后者按契约只记载荷的哈希（`args_hash` / `payload_hash`），拿它画不出「说了
  什么、回了什么」。`.jsonl` 不在产物清单收集的扩展名里，所以这一路不参与、
  也影响不了逐字节复现。每个阶段开始还会落**一行边界**（`kind="stage"`，只记
  `start`）：没有它，右栏只是一列模型与工具行，看不出「这一段是哪个阶段说的」，
  更看不出 R4/R5 那两段**一个模型都没调**（它们是纯确定性计算，只发阶段事件）。
  老 run 没有这份记录（记录器是后加的）：那时退到回放缓存
  `cache/llm.jsonl`，只拿得到模型答了什么，页面上会明说少了提示词与工具调用。
  还有一类 run 一次模型调用都没有（回放、provider 探针），右栏本来就是空的 ——
  空列表配一句话说出来，不然「这个 run 没调过模型」与「右栏坏了」在屏幕上一样。
  载荷过大（VLM 的整页 base64 图）会整条换成一行指认、过长提示词留头留尾并注明
  中略了多少字符 —— 截断后的正文读起来是完整的，不说出来没人知道少了多少。
  `离线自检` 的 run（`--mock`）在这一栏里**长得和真实 run 一模一样** —— 结构、字段、
  流式追加全都相同，差别只在模型答的是罐头。所以页眉挂一颗 `离线自检` 药丸、右栏
  再写一行说明（一次模型调用都没有的 mock run，右栏那行由上面那句空态说明取代 ——
  没有回答可指认时不说「这些回答」）。判断依据是 manifest 的 `provider`，
  运行中的 run 读 `checkpoint.json`（manifest 跑完才落盘，而**运行中恰恰是
  右栏最在被看的时刻**）。
  这一栏能不能用，由 `tests/test_panel_js.py` 用 node **真的执行**一遍页面里的
  JS 来守 —— 页面渲染成正确的 HTML，不等于它在浏览器里活着；两者之间那一层，
  控制台此前没有任何检查看过。
- **查看运行结果** —— R1 / R4 / R5 各占一个标签页，**三页同一个形状**：
  这块跑了哪几步（用时 / 模型调用 / 花费 / 这一步自己的计数）、跑出了什么
  （事实表 / 估值读数含敏感性网格与可比公司 / 核查发现）、产物在哪（链接）。
  标签上各带一个数（几条事实 · 每股价值 · 几处问题），不点进去也知道那边有什么。
  每个阶段那几项读数都是从 `trace.jsonl` 现算的 —— `checkpoint.json` 只记
  「哪些阶段完成了」和 provider，没有时长、没有调用次数、没有钱。
  **两张明细表全量渲染**（实测一份年报 295 条事实、73 条需复核，一条不落，
  行数多了由滚动容器接住）：页面上写着「共 N 条」的地方，就得能在这一页上把
  N 条都看到 —— 早先只印前 25 条、末尾缀一句「全量见 `facts.xlsx`」，
  指到一个文件等于没给；抽样还会让人把「抽样里一条都没有」读成「没有」。
  同理，事件流从**第一个字节**读全（不是只取末尾一页）、日志给**全文**
  （不是「末 25 行」—— 而 `_analyze/logs/` 不是 run 产物，截掉的部分页面上没有
  第二条路能看到）。只有右栏是窗口：它一行就是 14 KB 的原文，一个 run 的
  journal 实测 4.7 MB，全量预载不划算，要补的是「滚到顶部取上一页」。

页面里**不放模型写下的推理长文**：假设的 `basis`、核查的 `reason` 这类
几百字的段落一律不进正文，它们属于 `valuation_report.md` /
`annotated_draft.html` 这些产物。控制台只印结论和读数。

### `web.app` —— 展示站（九页）

九个页面：一个写入口 + 八个只读展示页（含总览页 `/`）。**路由条数与从前一致**，
改的是导航的排法 —— 顶栏不再按「页面类型」平铺，而是按赛题分成 **5 组**：

| 组 | 指向 |
|---|---|
| 总览 | `/` |
| 运行 | `/analyze`（全流程）· `/process`（单文件解析）· `/runs`（复现） |
| R1 提取 | `/library`（材料）· `/extract`（解析）· `/facts`（事实库） |
| R4 估值 | `/valuation`（页内标签：结果 / 假设 / 报告） |
| R5 核查 | `/audit`（页内标签：清单 / 批注稿） |

页内子视图走 `?tab=`，**无参访问仍是各自的主视图**（`/valuation` 是结果，
`/audit` 是问题清单），所以旧书签与外部链接一律照旧。
每一页右侧另有一个 **Agent 运行轨迹抽屉**：直接轮询该 run 的 `trace.jsonl`
（按字节偏移增量读，只取到最后一个完整换行），运行中每 2 秒刷新 ——
工具调用、阶段推进、勾稽断言、模型调用与路由决策都在里面。
`trace.jsonl` 按契约只记载荷哈希，所以这里的工具调用只有入参指纹；
**要看原始入参与返回，去控制台的右栏**（读 `agent_log.jsonl`）。

> 最简用法（把材料丢进文件夹，点一次）：PDF 放进 `inbox/raw/` →
> 浏览器打开 `/analyze` → 勾选费用确认 → 点「开始分析」。
> 它跑的是真实模型的完整 R1→R4→R5（与命令行 `agent run full` 是同一条子进程路径），
> 页面上能看到 11 个阶段的实时进度与运行日志；跑完直接在对应的选题视图里看结果。
> 收件目录与任务状态都不入库（`.gitignore` 里有 `inbox/` 与 `_analyze/`）。

| 页面 | 回答的问题 | 定位 |
|---|---|---|
| `/` | 这次参赛做了哪三题、各自结果如何？ | 总览首页：三题各一张卡片，答辩第一屏 |
| `/analyze` | 材料放哪、怎么开跑、跑到哪一步了？ | 写入口：启动完整分析 + 阶段进度 + 日志 |
| `/library` | 这次演示用的是哪些材料？解析状态如何？ | 建立「处理的是真实材料」的信任 |
| `/extract` | 三层引擎是怎么工作的？为什么这一页走 OCR？表格被改成什么样、凭什么改？ | 展示重点 1：结构化提取能力 |
| `/facts` | 这个数字凭什么可信？原文在哪一页哪一行？确定性路径占多少？ | 展示重点 2：溯源核验能力 |
| `/valuation` | 估值算出了什么？哪些假设最敏感？ | 敏感性热力图 / 龙卷风图 / 区间可视化 |
| `/audit` | 报告里有哪些错误？正确值是什么？依据是什么？ | 五类错误清单 + 修订对照 |
| `/runs` | 这次运行能不能复现？环境指纹是什么？ | 一键给出复现命令 |
| `/process` | 现场喂一个新文件会怎样？ | 赛题要求的「现场可实时处理」（单文件限量预览，不落库） |

`/facts` 顶部的抽取路径构成回答一个评委一定会问的问题：
「这些数字是算出来的，还是模型读出来的？」—— 按抽取器逐项列出条数，
并把「确定性路径 / 模型路径」的占比摆在一起。
真实材料上这个比例曾经是 73% 靠 VLM（而它读的正是已经重建好的表格），
补齐「表格网格直取」后降到 29%；
本机现存的整语料真实运行 `ab-no4`（999 条事实）是确定性 80.3% / 模型 19.7% ——
其中 `table_grid` 776 条、`rule_engine` 26 条、`vlm_scan` 197 条。
更早的 `annual41-seg` 报 87.7%（`table_grid` 895 / `rule_engine` 26 / `vlm_scan` 129），
但那次运行的产物不在本机，要按下面的 B 组命令重建后才能核验。

紧随其后的双路互证是这套设计最直接的收益：

```
模型读到 N 个取值，其中 M 个被确定性路径独立复现（X%）
```

两条互不相干的路径给出同一个数，比任何单路置信度都硬。
仅模型读到的那部分被明确列出 —— 要么是确定性路径的漏抽（该补），
要么是模型看错了（该拦），必须逐类分清。

> 注意：实测这个比例只有 0.8%（1/120），而且原因是结构性的：
> 确定性路径已经覆盖了绝大部分事实，模型读的是剩下没有独立对照的那部分。
> 逐条核对出自 `annual41-seg`（1050 条事实，确定性 87.7%）。该运行的产物
> 不在本机，要按下面的 B 组命令重建后才能核验；本机能当场复算的是 `ab-no4`。
>
> | | 条数 |
> |---|---|
> | 模型取值与确定性路径相同（互证） | 1 |
> | 模型取值与确定性路径冲突（同主体同指标不同值） | 0 |
> | 确定性路径没有该指标，无从对照 | 128 |
>
> 所以正确的读法有两面：
> "零冲突"不能当作"模型读数已被验证" —— 分母只有 1，
> 一次比较里出现 0 次对撞，说明不了模型的准确率；
> 要盯的是那 128 条没有任何独立校验的读数，
> 它们才是必须人工抽检的部分。
> 把它讲成"双路互证保证质量"、或把"零冲突"说成实质性证据，都是过度声称，
> 这里写清。（`/facts` 页面对同一组数字给的是同一套读法。）

同一页还展示主体归属纠正明细：表格行里的事实原本会被记成披露主体的，
页面把每一条「原主体 → 改为」连同行列号列出来 —— 改了就要留痕。

`/extract` 的表格区块把一张表拆成三层证据摆在一起：

1. 网格：每个格子按裁决结论着色（改值 / 格式归一 / 一致 / 未采纳）
2. 明细：每个被复核的格子都给出「程序读数 → 模型读数 → 结论 → 置信度 → quote 回读」
3. 物证：模型实际读的那张裁图（`/cell-crop/...` 直接返回像素）

第 3 条是关键 —— 没有那张图，「视觉裁决」就只是一句自述。
裁图按 `pages/cells/<doc_id>/` 分目录存放：早期平铺存放时，
不同文档的同页同格会互相覆盖，证据图会指向别的文档（且不报任何错）。

### 现场流程：把材料丢进一个文件夹，当场跑

赛题要求「现场可实时处理」。这是一份实测过的两阶段流程
（工具：`tools/demo_run.py`，仓库里已备好一份可直接用的 `demo_materials/`）。

① 材料目录的组织方式 —— 一个目录同时喂给三个需求：

```
<材料目录>/
  raw/      年报 / 公告 PDF          → R1 结构化提取（递归查找 .pdf）
  drafts/   研究报告草稿 .md / .txt   → R5 纠错核查
  comps/    可比公司快照 .json        → R4 **必需**
  market/   市场利率缓存 .json        → R4 **必需**
```

* 没有 `raw/` 时，PDF 直接放在 `<材料目录>/` 下也可以。
* 没有 `drafts/` 时 R5 会退化成「自动合成一份含已知错误的演示草稿」：
  流程照跑，但覆盖率与准确率失去意义（脚本会当场提示）。
* `comps/` 与 `market/` 容易漏。少了它们 R4 会以
  `CompsDataError` 显式失败 —— 宁可失败，也不让报告里出现
  看起来正常、实际是编造的倍数。实测就是先漏了这两个目录才发现的。

② 两条命令 + 起台：

```bash
# 赛前预热：把材料跑一遍并落盘（真实模型；实测 185 页年报约 18 分钟 / ¥0.96）
python tools/demo_run.py --data demo_materials --warm

# 现场运行：同一个 run 名 + --resume，秒级返回
python tools/demo_run.py --data demo_materials --live

# 起台，默认展示这一轮
python -m web.app --run live
```

③ 为什么必须两阶段 —— 实测数据：

| 档 | 实测 | 说明 |
|---|---|---|
| 赛前预热（`full` 全流程） | 1101 秒 / 份（185 页、854 次模型调用、¥0.96） | 大头是第 3 层 VLM 整页扫描与单元格裁决 |
| 现场（`--resume`，已完成 run） | 0.9 秒、0 token | 命中缓存，跳过已完成阶段 |
| Web `/process` 当场重解析新材料 | 608 ms | 真的从头跑，但只做预览、不落库成 run |

关键机制：缓存按 run 存（`runs/<run_id>/cache/llm.jsonl`）。
所以"换个 run 名重跑"永远是冷启动；必须同一个 run 名 + `--resume` 才能命中。

> 注意：`--live` 那一刻发生了什么：它跳过已完成的阶段
> （输出里会打印「断点续跑：已完成 N 个阶段」），
> 也就是说现场那一秒并没有重新做解析，展示的是赛前那次的结果。
> 它验证的是「同材料同配置 ⇒ 同一 run 目录 ⇒ 产物一致、可续跑」。
> 若评委要看当场重新解析，用 Web 的 `/process` 拖进去 —— 那才是真的从头跑。

> 注意：**不要在现场跑冷启动解析。** 实测：同一份材料两次独立冷跑，
> 事实库不会一样 —— 单格模型读数的差异会传导到整张表的候选产出
> （000722 的 85 张表里有 69 张的裁决内容不同；见
> `docs/VALIDATION_ROUND18_DEMO_FLOW.md` 第七节）。
> 这正是「赛前预热、现场复用」这套流程存在的理由。

④ 两条硬约束（都是实测踩出来的，`tools/demo_run.py` 会主动检查并警告）：

1. 预热之后直到现场结束，不要改动 `configs/`。
   实测教训：曾为提速把 `tables.adjudicate` 临时改成 `false` 跑了一轮，之后还原 ——
   那一轮 `replay --strict` 直接报「不可复现」，因为 manifest 里的
   `agent_config_hash` 记的是当时的配置，而 replay 用当前配置重算。
2. 一个 run 名同时只能有一个进程在写。
   实测教训：两个 `--warm` 进程同时写 `runs/live`，缓存被穿插追加
   （569 行里 168 个键被写了两次，行距 26–58 行），回放取到的不是产物当时用的
   那个答案 —— 一次本可复现的运行被判「不可复现」。
   现在 `Loop` 会写 `runs/<run_id>/.lock`（记 pid），发现别人在写就当场警告；
   缓存也改成首次写入者胜，并把「被覆盖过几次」计入 `overwritten_slots`。

3. 阶段失败时，换一个新的 run 名重跑，不要原地 `--resume`。
   原地重跑某个阶段会留下孤儿产物：上一轮渲染的裁图仍在盘上、仍被
   `manifest.outputs` 记着，而重跑的阶段不会再产出它们 → 回放报「回放未产出」。
   本轮只堵住了"新散件被误收"，孤儿清理尚未做。

⑤ 可复现性目前可声称的边界（措辞保守）：

| 对象 | 结论 |
|---|---|
| `runs/r4-seg`（确定性 + 快照输入） | `replay --strict` = 可复现。该运行的产物不在本机，需按 B 组命令重建后才能复核；本机现存同类产物在 `runs/web-20260927-123902` |
| `runs/annual41-seg`（旗舰运行，943 页 / 1050 条事实） | 750 项可复现 / 1 项不可复现。唯一不一致是 `channels/table_adjudications.json` 里一句错误文本：原始那次模型调用重试三次失败，失败的调用没有响应缓存，离线回放重现不了它。下游 `facts/*` 全部一致（那一格本来就没产出事实）。报告里会打印「原始运行状态为 partial，本次不一致是预期结果」。这一行是当时那次运行的记录，该运行的产物不在本机，要按 B 组命令重建后才能复核 |
| `agent run full` 在同一次预热的 run 上（`--resume`，含被跳过的阶段） | 已逐字节验收：模拟「跳过 `extract_text` 的续跑」，`facts.json` / `build_stats.json` / `facts_table.json` / `evidence.html` / `facts.xlsx` 五项产物与完整跑逐字节相同 |
| `--live --resume` 在已完成 run 上 | 0.9 秒，跳过全部阶段，不重算任何东西 |

> 注意：第十八轮实测到一个会静默毁掉结果的缺陷，已修并留了回归测试：
> `extract_text` 是唯一把「权威页面原文」注册进内存证据库的阶段，
> 而 `--resume` 跳过它就等于把库清空 —— `build_facts` 随后找不到任何
> 「单位：万元」，把每一行都按"无单位"拒掉，交出 0 条事实、退出码 0、
> 不报任何错（实测 1050 → 0，而 `channels/*.json` 逐字节相同）。
> 现在块级几何与报表标题会落盘成 `channels/page_layout.json`，
> 下游入口自动从产物把内存库灌回来，并且一页原文都没有时直接报错。

⑥ 材料发现的规则（`pipelines/r1_extract/common.py`）：
只认 `.pdf`（`SUPPORTED_SUFFIXES`），递归查找，
`--data` 可指目录或项目根（相对路径按项目根解析，绝对路径原样用）。

### 三个核心设计取舍

1. 只读产物，不重算任何数字。页面上的每个值都直接取自 `facts.json`
   等产物文件。演示台若能自行「美化」数字，现场看到的就与评审复现的
   不是同一份数据了 —— 这一条由
   `tests/test_web.py::test_facts_match_artifact_file` 守着。

2. 无前端构建链、无 CDN 依赖。 FastAPI + Jinja2 服务端渲染 + 手写 CSS。
   断网也能完整演示，契合「封闭或半封闭数据环境」要求。

3. 容错优先。缺哪份产物就显示空状态与补救命令，不抛 500。
   现场演示最怕的不是数据少，而是页面崩。

### 现场演示建议流程（约 4 分钟）

1. `/library` —— 铺开材料：N 份真实公告，其中 M 页是必须 OCR 的扫描件（30 秒）
2. `/extract` —— 点开一个扫描页，展示三层通道对比与路由判定理由（60 秒）
3. `/extract` —— 再点开一个表格页，展示单元格级裁决：程序读出的
   `583,96⏎5.66` 被模型归一为 `583,965.66`，附模型看到的那张裁图（45 秒）
4. `/facts` —— 点一条 VLM 读出的数字，展示左图右文、原文高亮、置信度构成（90 秒）
5. `/valuation` —— 看敏感性热力图，说明假设如何影响结论（40 秒）
6. `/runs` —— 当场执行 `agent replay --strict`，展示可复现（30 秒）
7. `/process` —— 现场拖入一个新 PDF，实时跑出三层结果（30 秒）

> 实测：一份 350KB 的公告在做完三层解析后 608 ms 返回结果
> （文本层 + 表格 + 路由判定全部现场计算；OCR 是唯一 CPU 瓶颈，因此限量）。

## 三个需求的技术亮点

### R1 数据结构化提取

三层解析引擎 + 逐页路由

每一页先做纯确定性预扫描（字符数、乱码率、文本/图像覆盖率、表框线段密度），
再按 `configs/routing.yaml` 决定走哪条路径：

| 路由 | 触发条件 | 处理方式 | 基础置信度 |
|---|---|---|---|
| `A_text_only` | 有效字符 ≥ 200 且乱码率 < 5% | 文本层直取 | 0.95 |
| `B_scanned` | 字符 < 50 且图像覆盖 > 60% | OCR + VLM 双路对读 | 0.80 |
| `C_garbled` | 乱码率 > 15% | OCR + VLM 双路对读 | 0.75 |
| `D_table` | 表框线段 ≥ 40 | 三引擎表决 + 逐格裁决 | 0.90 |
| `E_mixed` | 其他 | 文本层为主 + 局部图像补强 | 0.85 |

每次路由决策的理由都写入 `trace.jsonl` —— 「为什么这一页走 OCR」永远有据可查。

防幻觉的四条铁律（提示词要求 + 代码闸门双保险）：

1. VLM 只允许输出页面上看得见的字符串，禁止改写/换算/四舍五入
2. 强制 `quote` 回读校验 —— 声称的原文片段必须能在页面文本中找到，否则整条拒收
3. 禁止 VLM 做算术 —— 它说 "12,004.50"，换算成 "1.20亿元" 是代码的事
4. `cannot_determine` 是合法且被鼓励的输出 —— 宁缺勿错

别名匹配的仲裁算法（实测踩坑后重构）：

朴素做法（对每个指标别名做独立正则）会踩两个坑：
- 「占公司总股本比例 12.40%」中的别名「总股本」匹配到 12.40%，把占比当成股数
- 「归属于母公司股东的净利润」与「净利润」并列时，短别名抢走了归母那一行的数值

解法是以数值为中心、最近且最长的别名胜出，并按别名长度降序做全局区间仲裁：
「归母净利润」比「净利润」长，因此先声明、先获胜。

为什么不直接相信拼接的文本：`get_text("dict")` 返回的块顺序是 PDF 内容流的
写入顺序，与阅读顺序不一致。用拼出来的文本会导致 quote 定位漂移、期间推断丢失。
因此权威页面文本一律用 `get_text("text")`，块排序结果只用于 Web 展示。

表格分支：结构重建 + 算术校验 + 单元格级视觉裁决

| 步骤 | 做法 | 实测 |
|---|---|---|
| 区域识别 | 线段连通分量（近似共线 + 投影重叠，容差 4pt）。分段绘制的框线也能连起来；多个表格不会被合并 | 55/55 页识别成功 |
| 单元格取文 | CJK 折行直接相连、数字前保留换行 | 避免「唐人神集团股 份有限公司」这类别名断裂 |
| 算术校验 | 认合计标签（不是认"最后一行"），纵向/横向双向试探，分项只取紧邻连续数值段 | 无合计线时如实报告"无从校验" |
| 单元格裁决 | 只对可疑格调用 VLM：算术不平涉及的行列 > 换行切断 > 异常长 > 空格子 | 三档预算见 `configs/tools.yaml` |
| 覆盖闸门 | ① quote 回读 ② 位置确认 ③ 置信度 ≥0.7 ④ 几何佐证（该 bbox 内页面上真实印着的字必须支持模型读数） | 四条全部满足才允许改值；无文本层时改用 OCR 行框顶上 |
| 双路互证 | 同一条数值若被确定性路径与模型路径独立得到，置信度 +0.05 | 加分项写进 `confidence_breakdown`，可逐项复算 |

两个反直觉的实测结论（详见 `docs/P0_VALIDATION.md` §6）：

* 「算术不平」这个信号很强，但覆盖率极低 —— 55 张真实公告表格里只有
  2 张带「合计」标签。股权变动表、对外担保表根本没有合计概念。
  因此主力触发条件不是算术，而是几何特征排序（422 个碎格）。
* `arith.ok == True` 不等于"校验过"。没有合计线的表 `ok` 也是 `True`，
  代码里必须同时看 `checked`，否则把"没查过"当成"查过且没问题"。

还有一条最贵的教训：坐标换算错了不会报错。
裁图函数曾按「PDF 用户空间原点在左下」做 y 翻转，
而 PyMuPDF 的 `page.rect` / `get_text()` 用的是原点左上、y 向下。
于是每次裁图都上下镜像：第 1 行的格子裁出第 22 行的内容，
模型读出它看到的东西，三道自述闸门全部放行 ——
一次运行 184 个复核格里 80 个被错误"改值"。
定位靠的是 `search_for` 权威坐标 + `clip` 渲染真值，
修复后新增的几何佐证闸门（模型无法影响的事实）成为第四道防线。

### R4 自动化估值建模

- 只消费 R1 的事实库，不读取任何原始文档 —— 这从结构上保证三处数字一致
- 纯确定性计算：DCF 与敏感性分析不调用任何 LLM，因此结果 100% 可复现
- 每个假设逐条标注「事实 / 推论 / 观点」，由 `Assumption` 模型强制执行：
  无事实来源的假设必须显式标注为主观判断，否则构造失败
- 6 条勾稽断言（A1–A6）独立重算，任一 FAIL 即阻断出报告
- 缺辅助数据时断言标记 `SKIPPED` 而非静默跳过，并在报告中列出验证覆盖率
- 输出：估值区间（而非单点）、敏感性热力图、龙卷风图、Excel 模型工作簿

### R5 研究报告纠错核查

不用「让大模型通读找错」，而是用事实库做确定性比对。

| 类型 | 检查内容 | 判定方式 |
|---|---|---|
| E1 单位 | 万元↔亿元、%↔小数、量级差 10⁴/10⁸ | 换算到统一量纲后比对 |
| E2 估值倍数 | 分母口径、时点错配、市值口径、EV 未扣净债 | 从事实库独立重算 |
| E3 统计口径 | 合并vs母公司、归母vs扣非、单季vs累计 | 每条事实带 `caliber` 标签 |
| E4 引用 | 数字无来源、来源不符 | 数字→事实库反查 |
| E5 算术 | 同比/环比算错、占比算错、前后矛盾 | 独立重算 |

误报控制（官方明确考察）的三道防线：

1. 派生指标豁免：增速/占比/比率类数字不适用「查来源」判定，交给 E5 重算
2. 口径判定防陷阱：「归属于母公司股东的净利润」中的「母公司」不等于
   「母公司报表口径」—— 若误判，每条归母指标都会被报成口径错误
3. 同位置优先级抑制：同一处若已有 E1/E5 这类确定性数值错误，
   不再重复报 E3/E4 —— 后者往往是前者的副作用

`tests/test_audit.py::test_no_false_positives_on_clean_draft` 是误报回归基线：
一份完全正确的草稿必须产生零发现，任何规则改动引入误报都会让 CI 立刻失败。

真实评测集实测（`docs/VALIDATION_ROUND5_R5.md`，3 份人工核对草稿、8 条注入错误、11 条陷阱）：

```
真正例 TP = 4    假正例 FP = 0    假负例 FN = 4
Precision = 1.0000    Recall = 0.5000    F1 = 0.6667
```

零误报 —— 报出来的每一条都经得起人工复核。剩下的漏报集中在两类：
① 「口径未说明」这类表述规范问题（规则判不了）；
② 表格同一列里的两期数据错配（需要把表格结构信息引入 R5，当前只看文本流）。

这个诚实的短板比一个好看的平均分更有用：它明确指出了下一轮该做什么。

## 可复现性是怎么做到的

| 层次 | 机制 |
|---|---|
| ID 稳定 | 所有 ID 由内容哈希派生，不依赖页码或顺序 |
| 响应缓存 | `sha256(provider+model+params+messages+schema+prompt_sha)` → 响应 |
| 环境指纹 | `manifest.json` 记录输入文件哈希、prompt 版本哈希、skill 版本哈希、模型配置、代码配置指纹 |
| 运行参数 | `manifest.json` 还要记录影响产物的运行参数：`data_dir` / `doc_limit`(`--limit`) / `upstream_facts_run`(`--facts-run`) / `provider` |
| 全量追踪 | `trace.jsonl` 逐条记录**文件访问**、模型调用、工具调用、断言结果、逐页路由、阶段与错误。文件访问逐条带相对路径 + 读/写/列目录 + sha256 + 所属阶段（见下文「受控数据环境」） |
| 逐字节比对 | `agent replay --strict` 离线重放并比对全部产物哈希 |
| 无随机性 | 所有 LLM 调用 `temperature=0`；计算层用 `Decimal` 无浮点误差 |

`agent replay` 在离线模式下不发出任何网络请求：缓存缺一条就直接判定为不可复现。

> 注意：**运行参数必须进 manifest** —— 这是两次真实假警报换来的教训。
> `--limit 1` 试跑和 `run r4_valuation --facts-run <其他run>` 都曾被 replay 判为
> 「不可复现」，原因不是产物不稳定，而是回放用了不同的参数重跑
> （前者处理了全部文档，后者找不到事实库）。
>
> 这类假警报比不做校验更糟：复现报告一旦开始出错，人就会学会忽略它，
> 那时「不可复现」也不会被发现。回归测试见
> `tests/test_harness.py::test_replay_reproduces_run_with_limit_and_facts_run`。

## 受控数据环境

赛题要求「在封闭或半封闭数据环境中运行」，我们的实现：

- 离线开关：默认禁止出网；`--offline` 下缓存未命中直接报错而非静默降级
- 产物中禁止出现绝对路径（避免泄漏用户名等环境信息）
- 图片以 base64 内联传给模型，不依赖外网可访问的 URL
- **读写闸门**：`data/` 只读、只写当前 `runs/<run_id>/`，由运行时强制而不靠约定

### 文件访问是怎么记录的（赛题四类事件之一）

每个读写点位都经由本 run 的 `FileGuard`（`RunContext.guard()`），出口是
`Tracer.file_access()`，于是 `trace.jsonl` 里逐条留下：

| 字段 | 内容 |
|---|---|
| `path` | **相对路径** —— 绝对路径会把本机用户名写进交付物，`FileGuard._log` 统一转换 |
| `mode` | `read` / `write` / `list` |
| `path_sha256` | 读到的内容哈希，或写入落盘后的文件哈希 |
| `stage` | 该次访问所属的业务阶段，取自编排层的当前阶段 |

闸门本身也是强制的：越出 `read_roots`（当前材料目录 + `configs/` + 本 run 与上游
facts run 目录）或 `write_roots`（当前 run 目录）的读写会当场抛 `SandboxViolation`。
`read_roots` 里**故意不含** `PROJECT_ROOT` —— 写上它等于什么都能读。

有一类访问不走 `read_text`/`write_text`：PyMuPDF 的 `fitz.open`、matplotlib 的
`savefig`、PIL、openpyxl 都在 C 扩展或第三方库里自己 open 文件，`FileGuard`
包不住。对这些点位用 `FileGuard.record()` —— 校验 + 留痕，但**不代劳 I/O**。
这样做的理由是可复现性：改写这些调用可能让产物的字节数变一个字节，
而一个字节之差就是哈希不匹配、replay 判不可复现。

「完整」不是一句自我评价，它有一条可跑出来的判据，写在
`tests/test_harness.py::test_end_to_end_full_pipeline_mock` 里：跑一次真实
full run，然后（a）每条 `file_access` 的路径必须是相对的、必须带 sha256、
必须归到计划里真实存在的业务阶段；（b）**磁盘上每一个产物都必须有对应的
`write` 记录** —— 少一个就说明有一条写路径没走 guard。当前实测：
一次 mock 全流程 71 条 `file_access`（37 读 / 34 写），盘上 34 个产物零遗漏。

> 边界要说清：闸门管的是**流水线**的读写。工具注册表是另一个入口
> （MCP / Agent 循环按名调用 `table.detect` 这类工具），它的调用记在
> `tool_call` 里（带工具名与参数哈希）；本项目跑一次 run 时，流水线是
> 确定性地直接调用底层函数，不经注册表，因此两类记录不重不漏。

四类事件都有出处：`tool_call`（工具注册表出口统一打点）、`assertion`（断言）、
`routing`（逐页路由）、`llm_call`、`file_access`、`stage`、`error`。
另有两道可独立复核的旁证：`facts/documents.json` 登记每份输入材料的
`rel_path` + `sha256` + 页数，`manifest.json` 登记全部产物的哈希。

> ⚠️ **历史 run 的读数是 0。** `runs/web-*` 产生于 2026-10-17 接入编排层之前，
> 它们自己的 `trace.jsonl` 里 `file_accesses` 就是 0 —— 「运行与复现」页照实报
> 这个数，不会替它们宣称已记录。`runs/demo` 已按新代码重跑，读数是 71。
> 想把任一份旧 run 换成四类齐全的，重跑即可（`--mock` 离线、约 6 秒、不花钱）：
> `python -m agent.cli run full --mock --run-id demo --quiet`。

- `test_verdict_never_overwrites_without_gates` —— 未过闸门的模型读数
  一律不得覆盖程序读数。这是安全攸关的判定表，因此判定逻辑被拆成

- `test_no_false_positives_on_clean_draft` —— 一份完全正确的草稿必须产生
  零发现。任何规则改动引入误报，CI 立刻失败。
- `test_vlm_attribution.py::test_gate_rejects_share_count_assigned_to_ratio_metric`
  —— 股数被归到百分比指标必须被拒。这类错误数值读对了但指标名不符，
  会让整个指标的数据被污染。
- `test_templates_avoid_dict_method_name_collisions` —— 静态扫描模板，
  禁止 `{{ x.values }}` 这类写法（Jinja2 会解析成 dict 方法而非同名键）。
  这类错误编译期发现不了，只在渲染到那一行时才炸。
- `test_end_to_end_is_reproducible` —— 先用 `agent replay --strict`
  验证逐字节回放，再验证跨运行的语义等价。两个层次不能混淆，
  详见 `docs/DESIGN_NOTES.md`。
- `test_panel_js.py::test_the_rail_actually_runs_in_a_browser` —— 唯一一条
  **执行页面 JavaScript** 的测试。此前四个渲染门都只拿到 HTML 字符串，
  于是「渲染正确」与「能用」之间那一层没有任何检查：控制台右栏一直停在
  `未连接` 而所有门全绿（详见 `docs/DESIGN_NOTES.md` 5.5）。
  它断的不是「接口有数据」，是「页眉那行离开了初始值」——
  初始值恰好就是故障的样子。
- `test_panel.py::test_the_rail_cannot_be_hidden` —— 唯一一条**看 CSS** 的测试。
  右栏那个「收起」键把整条右栏（含它自己）藏了，`localStorage` 一记就再也
  找不回来。它断的是结构而不是像素：右栏还在、按钮不在、`rail-off` 在样式与
  页面脚本里都不在 —— 少任何一条，这扇单向门都装得回来。
- `test_harness.py::test_journal_marks_every_stage_start_and_nothing_else` ——
  钉住「逐步记录里多出来的是哪种行」。阶段边界是右栏唯一的新数据，多记一种
  （比如阶段内的 `warn`）不会让任何测试变红，只会让右栏慢慢被淹掉；
  所以要有一条断**逐字的记录序列**的测试。

## 工程实现记录

`docs/DESIGN_NOTES.md` 记录了开发过程中实际遇到并修复的问题，包括：

- 中文金融文档的别名冲突陷阱（「占公司总股本比例」不是「总股本」）
- `get_text("dict")` 的顺序 ≠ 阅读顺序（导致 quote 定位漂移）
- bbox → 像素的 y 轴翻转搞反（裁图整体上下镜像，导致 75 次错误"改值"）
- `ResponseCache` 定义 `__len__` 后空缓存变成 `False`，导致缓存静默失效
- `except Exception` 把代码 bug 一起吞掉：产物空数组、阶段仍报 success
- 只靠模型自述的闸门等于没有闸门（quote 回读 / 位置确认 / 置信度全部失效）
- 时间戳如何让「可复现」在机器校验层面不成立，以及两个层次的正确区分
- R5 误报控制的四处具体修复（派生指标豁免、口径判定防陷阱、同位置抑制、量纲族隔离）
- 断言 SKIPPED 与 FAIL 的语义区分，以及为什么它关系到学术诚实
- 页面渲染正确 ≠ 页面能用：四个渲染门都不执行 JS，右栏因此坏了一整轮没人发现
- 页面看得见 ≠ 页面点得动：那个「收起」键把整条右栏连同自己一起藏了，
  而状态又记在 `localStorage` 里 —— 点一下就是永久的，刷新也回不来。
  这一层（CSS 与交互后果）至今没有任何自动门，是用户在真机上点出来的；
  连着的第二个是 `body` 上一条没配居中的宽度上限，超宽屏上空白全堆在右边
- 控制台的说明文字写成了「带解释的散文」（如「③ 每步在干什么 · 用时 / 模型调用 /
  花费 / 这一步自己的计数 · 跑完后刷新看到全部」）—— 读者要的是读数，不是
  作者对自己页面的解说；页面上的话与页面文件里的注释是同一件事的两种写法，
  一起收掉，理由搬进 `docs/DESIGN_NOTES.md`（5.7）

这份文档对团队协作与答辩准备都有直接价值。

## 已知限制

1. OCR 引擎需单独安装：`pip install rapidocr-onnxruntime`。未安装时，
   若存在必须依赖 OCR 的页面（扫描件/乱码页/表格页），管线会显式失败并给出安装指引，
   不会静默降级为空结果；若仅图文混排页需要补强，则降级并记录缺口。
   （本作品的实测数据均在已安装该引擎的前提下取得。）
2. OCR 数字召回约 89–93%：即约每 10 个数字有 1 个需要第三层 VLM 兜底。
   这是三层架构存在的直接理由，不是可以忽略的细节。
   数字边界完整性约 83%（相邻数字会粘连），已新增专门的检测与触发规则。
3. 可比公司数据来自公开接口，但只覆盖 A 股同业（详见 `docs/VALIDATION_ROUND7_COMPS.md`）：
   倍数由 `tools/fetch_comps.py` 从公开接口取真实行情与年报财务数据后自算
   （`pe = 总市值 ÷ 归母净利`、`pb = 总市值 ÷ 归母权益`），并与人工核对真值比对通过才落盘。
   三项已知缺口：① EV/EBITDA 留空 —— 它需要现金与有息负债，
   而这两项没有可靠的结构化公开来源，宁可留空也不用编的数充数；

    那张表的列头年份归属。

16. 模型内部假设之间的一致性此前未做检查（2026-09 第十一轮修复）：

21. 卡了六轮的资本开支终于接通（2026-09 第十四轮）：
    601857 的真实资本开支 269,089 百万元（9.39% 收入）从第六轮起一直取不到。
    根因是 p7 五年摘要表没有自己的表头，2025/2024/2023 三个年份的值被
    全部标成 `2025A`，三条候选置信度/口径/单位全同 —— 而 `275,849 > 269,089`，
    "取最大值"必然取到 2024 年的数（实测把 DCF 从 18.1 打到 4.98）。

    解法：年份其实印在同一张表的脚注里（`截至 2021 年 12 月 31 日、…
    2025 年 12 月 31 日`），配合两处独立证据确定的排版约定
    「数据列从左到右 = 年份从新到旧」，即可确定列到期间的映射。

    落地过程中又查出三个各自独立的坑：

    1. 脚注被算成"数据列" —— 脚注里的 `12` `月` `31` `日` 也是"数字"，
       把数据列从 5 撑到 18。已修（`_footnote_row_start` 排除脚注行 +
       `_majority_data_columns` 把判据从"任一行有数字"收紧为"多数行有数字"）。
    2. 年份与数据列取自同一网格 —— 排除脚注后年份也被排除了，
       而年份就在脚注里。已修（加 `year_grid`：数据列取脚注前、年份取整表）。
    3. 年份在整表里出现两次（期间表头行 + 脚注），共 10 个，
       而判据要求"恰好等于数据列数 5" → 永远不成立。
       已修：按去重后的个数判等。

    最终的守卫判据是「期间碰撞」—— 同一个期间落到两个不同的数据列上。
    两个列代表两个年份，不可能共享一个期间，所以碰撞就说明映射坏了。
    这个判据只在 4 / 987 张表上成立，而目标表在其中：
    收紧判据只去掉误报、没有去掉正例。

    效果：capex 候选 3 条 → 1 条（就是正确的 `269,089`），
    R4 终于用上事实值 9.39%，`gaps` 清空，
    DCF ¥19.4316 → ¥14.0394，与相对估值的差距 67% → 21%
    （十轮以来最窄）。真值比对 9/4/5 无退化，`needs_review` 不变。
    可用 `R1_YEAR_SEQ=0` 一键回退对照。

22. 资产负债表恒等式是唯一一条跨指标的硬约束（2026-09 第十五轮）：
    R4 逐指标独立选候选，于是出现这样的组合 ——

    ```
    total_assets      2,827,777,000,000
    total_liabilities 1,028,453,000,000
    equity_total              7,300,000   ← 七百三十万
    ```

    恒等式残差 1.8 万亿，而没有任何闸门报警 —— 因为每个指标单看都合法
    （7,300,000 元确实印在年报的某张表里）。单看任何一个指标都发现不了
    "三个数来自不同口径"，只有 ``总资产 = 总负债 + 所有者权益`` 能。

    修法是联合选择，两步缺一不可：

    1. 在候选里枚举满足恒等式的三元组（硬约束）——
       实测 601857 的候选里有 18 组满足，它们都是真实报表；
    2. 在自洽的三元组里取资产最大的那组 ——
       合并（集团）口径的资产必然 ≥ 其母公司/子公司口径。

    "先过滤、再排序"是关键：未经滤时"取最大"会被垃圾大数俘获
    （本轮实测过：000722 的 17 条总资产候选里有一条比真值还大的垃圾值，
    加上"取最大"之后选中的正是它，比不改更糟）。

    效果：601857 的 `equity_parent` 从 1,586,061,000,000 修正为
    1,799,548,000,000，恒等式精确闭合（1,028,469 + 1,799,548
    = 2,828,017 百万 = 总资产），`illustrative_only` 由 `True` 回到 `False`；
    000722 的 2025A 三项精确命中真值。

    > **2026-10-10 补记（两条，都与口径有关）**：
    >
    > 其一，「000722 的 2025A 三项精确命中真值」是相对于**当时**的真值
    > 得出的，而当时真值取的是**母公司**口径（3,797,417,361.30 /
    > 364,789,378.77 / 3,432,627,982.53）。真值已于 2026-10-10 改为
    > 合并口径（3,547,820,309.72 / 357,822,681.50 / 3,189,997,628.22），
    > 所以这句话需要在新真值下重验，不能直接读成"选中了集团数"。
    > 详见 `docs/VALIDATION_ROUND15_BALANCE_IDENTITY.md` 的订正。
    >
    > 其二，上面第 2 步"自洽三元组里取资产最大的那组"，理由是
    > "合并（集团）口径的资产必然 ≥ 其母公司口径" —— 这条前提**不成立**：
    > 000722 就是个反例，母公司资产总计 3,797,417,361.30 大于合并的
    > 3,547,820,309.72（母公司对子公司的长期股权投资在合并时被抵销）。
    > 因此"取最大"只是**在多数样本上**倾向集团口径，不是口径保证；
    > 真正能定口径的仍是每张表的 `statement_scope`，而它目前对
    > 合并/母公司交错表标反（见第 23 条末尾）。

    > 顺带记一个新确立的区分：`tools/verify_truth.py` 测的是
    > 「库里有没有这个值」（抽取层），R4 的选择键决定「选了哪一个」
    > （选择层）。本轮修好了后者，而前者的数字不会变 ——
    > 不写清楚这个区分，「数字没变」就会被误读成「没修好」。

23. 报表表头的继承键必须带口径（2026-09 第十六轮修复）：
    `doc_header` 原先是按文档单键存的，而年报里合并表与母公司表的页序
    会交错（实测 000722 p73–p77）：

    ```
    ★表头 p73 表0  合并资产负债表
      续表 p74 表0  合并资产负债表
      续表 p75 表0  母公司资产负债表      ← 同页下方又起一条新报表
    ★表头 p75 表1  母公司资产负债表
      续表 p76 表0  母公司资产负债表
    ```

    p75 表1 一建表头就把 p73 的覆盖了，于是合并表的续表继承到母公司表的
    表头，列→期间映射随之错位：上期列（3,777,520,118，是**母公司**报表
    2024 年的资产总计；合并表的上期资产总计是 3,441,060,747.63）
    被标成 2025A，与本期列挤进同一期间 —— 2024A 因此只剩一张子公司汇总表
    的杂项，恒等式凑不出自洽三元组。

    修法：键改成 （文档, 口径），第二维直接用 `scope_hint` ——
    它本来就是"这张表属于哪条报表"的判据，而表头继承问的正是同一个问题，
    两者天然一致，不需要新判据。

    效果：全库 `needs_review` 209 → 179（−30） ——
    它们此前是因期间映射错位被冲突守卫误标的；目标公司 601857 的
    DCF 与四项事实假设完全不变。

    > 仍未解决的那一层：p74/p76 的行被归到了 `parent_only`，
    > 而它们装的是合并表的数。这是报表归属错标，与本条修的
    > 表头继承是两个独立问题。
    >
    > 试过修它，被实测否决：`scope_by_overlap` 的比较键是纵坐标，
    > 而年报里大量续表是整页高的（标题必落在表格矩形内部），
    > 于是 p73 的合并标题算成负 gap 被惩罚、p75 的母公司标题反而赢 ——
    > 看起来是明确 bug。改成"整页高的表按文档顺序取最近前置标题"之后：
    > `needs_review` 179 → 177（只少 2 条），而 000722 的 2024A
    > 从"有自洽三元组"变成完全没有数据，净效果为负。
    >
    > 原因：口径与期间两个映射在续表上互相纠缠 —— `carry_header`

## 技术验证报告

`docs/P0_VALIDATION.md` 记录了全部实测数据与结论，包括：

- 图片 token 折算实测：1001 token/页 → 100 页全页裁决 ¥0.48，成本不构成约束
- 视觉 JSON 稳定性：合法率 100%（但首次运行时是 0% —— 原因是提示词没给字段名，
  这是必须记录的教训）
- OCR 准确性受控退化实验：以电子版 PDF 渲染图 + 文本层为真值，
  测出字符准确率 95–98%、数字召回 89–93%，并对 20 页真实盖章扫描件做了人工逐字核对
- 思考模式破坏可复现性：官方文档确认思考模式下 `temperature` 不生效，
  因此产出数字的角色一律关闭思考（顺带降本 69%）
- 「可复现」的三层含义：输入层 / 环境层 / 产物层，
  验证过程中四次「不可复现」警报的原因各不相同

后续三轮的验证报告见上文「分轮验证记录」。四轮的共同结论是：
形态类闸门（单位归一化、量纲族校验、quote 回读、算术重算）拦不住两类错误 ——
取错科目（净利润冒充 EBIT）与跨表单位分歧（现金放大 100 倍）。
拦住它们的是依赖指标语义的合理性判据（EBIT 率 ≤80%、货币资金 ≤ 资产总额）。
本项目因此把"每新增一条假设推导，就配一条量级合理性闸门"作为工程约定。

> 第十轮把 D&A 换成了事实库真值 7.53%，结果 DCF 从 15.21 涨到 22.54 ——
> 改成更准的数据却让估值变贵，而且全程不报错。
> 根因在 `FCFF = EBIT×(1−税率) + D&A − capex − ΔNWC`：
> 模板 capex 只有 6%，低于 7.53%，于是 `D&A − capex` 变成 +1.53% 收入的正贡献。
> 会计含义上这等于假设公司不重置正在折旧的资产，即清算 ——
> 一个做 DCF 的模型在"永续经营"前提下同时假设"不重置资产"，是自相矛盾的。

> 而列号本身就是错的（表头 12 格 / 数据 5 格，两套结构毫无共同之处）。

### 核心模块自查（评审可直接复现）

赛题要求提交「智能体编排框架、Tool、Prompt、Skill、MCP、数据处理和日志记录等核心模块」。
下列命令逐项给出可验证的证据：

```bash
python -m agent.cli tools      # Tool：N 个工具，含副作用/确定性/成本声明
python -m agent.cli prompts    # Prompt：N 个提示词，含版本与 SHA256
python -m agent.cli skills     # Skill：加载 SKILL.md 并校验其绑定真实存在
python -m agent.cli mcp --self-test   # MCP：真实子进程 + 完整协议往返
python -m agent.cli audit <run>       # 日志：人类可读的运行审计报告
python -m agent.cli contracts         # 数据处理：数据契约导出为 JSON Schema
```

`agent skills` 与 `agent mcp` 有两点值得说明：

- `agent skills` 会校验技能文档里声明的工具与提示词是否真实存在。
  文档写「绑定工具 `table.check_arithmetic`」而代码里该工具被改名时，
  运行期不会有任何报错 —— 这类「文档描述了不存在的系统」的问题，
  在这里会被直接报出来（`tests/test_prompts_and_skills.py` 是硬断言）。
- `agent mcp --self-test` 真的启动子进程走完协议
  （initialize → tools/list → tools/call → 错误路径 → 接入工具注册表 → 落追踪），
  对端是仓库自带的 `tools/mcp_demo_server.py`（纯标准库、离线可跑）。
  MCP 工具接入后与自有工具同构，但元数据按最保守方式声明
  （`side_effect=network`、`determinism=nondeterministic`）——
  我们无法保证第三方服务器是纯函数，因此不会把它用在可复现路径上。
  另外，MCP 子进程只继承白名单环境变量，拿不到 `DEEPSEEK_API_KEY`
  （`tests/test_mcp.py::test_server_cannot_see_api_key` 端到端验证了这一点）。
