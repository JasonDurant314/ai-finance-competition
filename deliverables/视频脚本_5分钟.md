# 项目介绍视频脚本（≤ 5 分钟）

> 交付要求（通知 P6）：初赛视频为 MP4、时长 ≤ 5 分钟、≤ 500 MB，
> 随项目计划书一并提交。本脚本按 4 分 50 秒编排，留 10 秒余量。
>
> 录制原则：只演示能当场跑出结果的东西。
> 需要 API Key、需要二十分钟的冷启动解析，一律不进视频 ——
> 视频里出现的每个画面都在赛前预热好的 run 上实时操作。

---

## 一、录制前准备（约 30 分钟，一次性）

```bash
# ① 预热演示材料（真实模型；约 18 分钟/份，见 README「现场流程」）
python tools/demo_run.py --data demo_materials --warm --run-id live

# ② 起台（默认展示预热好的这一轮）
python -m web.app --run live

# ③ 自检：确认复现结论是绿的（否则视频里会翻车）
python -m agent.cli replay live --strict
python tools/web_smoke.py --in-process
```

录制环境要求

| 项 | 要求 |
|---|---|
| 浏览器 | 全屏（F11），缩放到 110%，隐藏书签栏 |
| 分辨率 | 1920×1080，录制帧率 30 fps |
| 终端字号 | 16pt 以上（评审要看清命令与输出） |
| 终端编码 | 本项目脚本已自动切 UTF-8，中文与 ✓ 正常显示 |
| 网络 | 断开也无妨（演示全程走本地产物与缓存） |

> 注意：**两条硬约束**（`tools/demo_run.py` 会主动检查）：
> 预热之后直到录完不要改动 `configs/`；同一个 run 名只能有一个进程在写。
> 违反了会得到一次假的「不可复现」。

## 三、口播稿（照着念，语速约 250 字/分钟）

### 0:00–0:22　开场

> 金融 AI 最危险的问题，不是"不会算"，而是看起来算对了。
> 比如这张表里的数字被折成了两行，模型读成了五万八，不是五十八万 ——
> 程序不报错，阶段状态是 success，报告看起来一切正常。
> 我们的项目，就是让这类错误无法静默通过。
> （画面：标题卡 → 一行错误数字被红框圈出）

### 0:22–1:05　选题与系统总览

> 我们参加了选题一、四、五：数据结构化提取、自动化估值建模、研究报告纠错核查。
> 这三个不是三个孤立功能，而是一条质量链：
> 先把受控材料变成带原文锚点的事实库，估值和核查都只消费这个事实库，
> 不重复解析文档 —— 所以"事实库准不准"是一个可以被单独检验的问题。
> 底层是我们自研的 Agent Harness：编排、工具、提示词、技能、MCP、追踪与复现，
> 全部自研，没有用第三方编排框架。
> （画面：架构图，光标依次扫过 agent / domain / pipelines / web）

### 1:05–1:55　R1：三层解析 + 逐页路由

> 这是本次演示用的材料：四份真实年报，共 943 页。
> 打开解析页，可以看到每一页走了哪条通道、以及为什么：
> 有文本层的直接取字；没有文本层的扫描件走本机 OCR；
> 关键字段再交给多模态裁判。
> 注意这里的路由理由是算出来的：字符数、乱码率、覆盖率、线段密度 ——
> 不是模型猜的，也不是我们写死的。
> （画面：`/library` 停留 8 秒 → `/extract` 切到一张扫描页，高亮"路由判定理由"）

### 1:55–2:35　R1：表格单元格级裁决（本项目的技术亮点）

> 这张表程序读出来是 583,96 加一个折行的 5.66。
> 模型给出的读数是 583,965.66 —— 但我们不因为它说得对就采信：
> 每一次改写都必须由模型无法影响的几何事实背书：
> 折行位置、数字连续性、量纲一致性、网格对齐。
> 而这张图，就是模型当时看到的那张裁图 ——
> 没有它，"视觉裁决"就只是一句自述。
> （画面：三层证据并排：网格着色 → 明细 → 物证裁图）

### 2:35–3:15　R1：溯源核验

> 随便点一个数字，比如这个由模型读出的营业收入。
> 左边是原文，命中片段被高亮；右边是这条事实的全部属性：
> 页码、行号、bbox、来源层、置信度构成。
> 这一页还回答了评委一定会问的一个问题：这些数字是算出来的还是模型读出来的？
> 屏幕这一轮（`web-20260927-123902`）里，确定性路径 295 条、模型路径 61 条，
> 占 82.9% / 17.1% —— 能从原文结构直接定位的，不交给模型读。
> 但请看这一栏：模型读到的 54 个取值里，被确定性路径独立复现的只有 2 个。
> 所以我们不讲"双路互证保证了质量" —— 那 52 个没有任何独立校验，
> 才是最需要人工抽检的地方。这条限制写在页面上，不用等评委来问。
> （画面：`/facts`，高亮原文 + 置信度面板 + 抽取路径构成）
>
> 注意：**口播数字必须与屏幕一致**：上面三个数取自本页首屏「重点考察④」那一行，
> 是当场这个 run 现算的。不要念旗舰运行（`annual41-seg`）的
> 87.7% / 12.3% —— 那是另一次运行的数字，仓库里没有它的 `runs/` 目录
> （重建命令见 `docs/REVIEWER.md`），屏幕上也不会出现。
>
> 注意：**这一段的材料与选题口径要注意（评委可能追问）**：本段演示跑在
> `web-20260927-123902`，输入是年报 —— 而通知 p2 给选题 1 点名的
> 材料是「非标准化公告、扫描文件和复杂表格」，年报是选题 2 的材料。
> 我们选的选题是 1（见 `docs/COMPETITION_FIT.md` §4.1），所以这里有个
> 材料错配：演示的是溯源核验能力（这个能力本身与材料无关），
> 但材料用的不是选题 1 点名的那一类。
> 如果评委追问或时间允许，可以切到 `ann77-20260927`（77 份真实公告、
> 923 页、765 条事实、三类字段质押 31 / 中标 30 / 股权变动 46）——
> 启动参数加 `--r1-run ann77-20260927` 即可，本页会自动改念那一轮的
> 数字（首屏是现算的，不会串）。两个 run 只能念一个，不要混读。

### 3:15–3:50　R4：估值与假设

> 估值不是"让模型写一段话"，而是一条显式的链条：
> 事实 → 假设 → 模型 → 区间 → 敏感性。
> 每条假设都标注了属性：绿色是事实（能追到具体表格单元格），
> 齿轮是一致性调整，蓝色是观点。
> 折现率由 CAPM 逐项推导，无风险利率来自带来源和日期的市场数据缓存。
> 这张图是双因素敏感性热力图 —— 哪两个假设最影响结论，一眼能看到。
> （画面：`/valuation`，先扫假设表，再停在热力图与龙卷风图）

### 3:50–4:20　R5：报告纠错核查

> 核查这一环，是拿一份研究报告草稿去对照事实库：
> 数字、单位、口径、引用、估值倍数，五类错误逐条查。
> 每条发现都给三样东西：错在哪、正确值是多少、依据是什么，
> 而且能一键生成批注版草稿，编辑拿到就能改。
> 我们对误报的要求是硬的：一份完全正确的草稿必须零发现 ——
> 这条由测试守着，改规则一旦引入误报，测试立刻失败。
> （画面：`/audit`，错误清单 → 修订对照表 → 批注版草稿）

### 4:20–4:40　可复现性（赛题明文要求）

> 最后是可复现性。我们现在当场跑一次回放：
> 它不调用任何模型，离线重跑整条链路，然后逐字节比对产物。
> （终端输入 `python -m agent.cli replay live --strict`，等待 2–3 秒）
> 结论是可复现 —— 三十多个产物，哈希全部一致。
> 需要说明的是，现场这一秒并没有重新解析，它验证的是
> "同材料同配置 ⇒ 同一个 run 目录 ⇒ 产物一致、可续跑"。
> 要看当场重新解析，用演示台的"现场上传"页，拖一份新文件进去。
> （画面：终端输出 `**结论：✅ 可复现**`，再切到 `/runs` 页看环境指纹）

### 4:40–4:50　收尾

> 这个项目做了十八轮真实数据验证，修掉三十四处缺陷，
> 也留下八条没有解决的问题，连同根因和影响一起写在文档里。
> 我们认为，一个能说清自己边界的系统，比一个声称什么都对的系统更值得信任。
> （画面：收尾卡，列出三行数字：18 轮验证 / 34 处缺陷 / 8 条未解决）

## 四、录屏操作清单（照着做就不会卡）

| 步骤 | 命令 / 操作 | 预期 |
|---|---|---|
| 1 | `python -m web.app --run live` | 起台，默认展示预热 run |
| 2 | 浏览器打开 `http://127.0.0.1:8000/analyze` | 收件目录清单 + 开始分析按钮（写入口，可作为开场镜头） |
| 3 | 依次点击 `/library` → `/extract` → `/facts` → `/valuation` → `/audit` → `/runs` | 每页停留 5–20 秒 |
| 4 | `/process` 拖入一份新 PDF（可选，只做预览） | 约 0.6 秒返回三层结果 |
| 5 | 终端：`python -m agent.cli replay live --strict` | 输出 `✅ 可复现` |
| 6 | 终端：`python tools/reproduce_all.py --quick` | 11 步全绿（可剪进 3 秒快放） |

> 注意：**不要在录像里点 `/analyze` 的「开始分析」**：真实模型跑一份年报要十几分钟，
> 视频里只能拍到等待。要展示"一键启动"，点一下按钮、拍到阶段进度表启动即可，
> 然后切到赛前预热好的 run（`/library?run=live`）继续讲结果。

## 五、导出与检查

| 项 | 值 |
|---|---|
| 容器 / 编码 | MP4 / H.264 |
| 分辨率 / 帧率 | 1920×1080 / 30 fps |
| 时长 | ≤ 5:00（本脚本 4:50） |
| 体积 | ≤ 500 MB（1080p 屏幕录制 5 分钟通常在 150–300 MB） |
| 音频 | 若用口播，保证人声清晰；若不方便配音，用字幕 + 轻音乐，信息量不减 |
| 文件命名 | `队名_项目名称_项目介绍视频.mp4` |

导出后自检三条

1. 全程看完一遍，确认没有出现报错红字、没有弹出 API Key 提示；
2. 确认 `replay` 那一段的输出里确实有 `✅ 可复现` 字样（不要靠解说代替画面）；
3. 确认视频里出现的每个数字，都能在本仓库文档里找到出处
   （清单见 `docs/REVIEWER.md` 与 `docs/VALIDATION_INDEX.md`）。

## 六、备用方案（现场时间紧或出意外）

* 只讲三件事：错误无法静默通过（裁决 + 物证）、每个数字可溯源、运行可复现。
* 不演示也可以：`runs/<run_id>/` 下的产物 HTML 可以直接当静态证据展示
  （`facts/evidence.html`、`audit/annotated_draft.html`）。
* 不要现场冷启动：同一份材料两次独立冷跑，事实库不会完全一样
  （单格模型读数差异会传导到整张表的候选产出）。这正是"赛前预热、现场复用"
  这套流程存在的理由。
